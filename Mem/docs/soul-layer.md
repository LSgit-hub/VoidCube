# 灵魂层

## 1. 定位

本文定义 Mem 为 VoidCube 的灵魂层。

它回答五个实际问题：

- 这个系统中的灵魂是什么
- 记忆与治理如何在 Mem 内部共存
- 灵魂层的记忆管家与监督者治理角色意味着什么
- 哪些输入和输出属于灵魂层
- 灵魂侧治理如何与网关、CLI 和执行器关联

## 2. 定义

在 VoidCube 中，灵魂不是：

- 当前进程
- 当前模型上下文
- 当前活跃主体

灵魂是跨主体替换而持久存在的长生命周期身份与治理基底。

如今，Mem 已经承担了关键的灵魂职责：

- 长期记忆
- 身份连续性
- 演化历史
- 主体谱系
- 切换与回滚记录
- 治理决策

因此 Mem 不只是记忆后端，而是系统的身份与治理核心。

在当前的 VoidCube 架构中，这种灵魂侧治理并非为自身而存在，而是为了支撑面向用户的系统对更好的 Agent 主体进行持续改进、替换与安全激活。

另一个基线框架现在也很重要：

- VoidCube 充当母系统
- 双主体槽位充当两个子 Agent 实例
- Mem 不把整个母系统交付给用户
- Mem 帮助母系统决定哪个改进后的子 Agent 可以面向用户

## 3. 内部角色

灵魂层最好被理解为同一 Mem 域内的三个内部角色。

### 3.1 记忆核心

负责持久状态：

- 用户长期记忆
- 代理长期记忆
- 宪章规则
- 演化事件
- 主体切换历史
- 回滚历史

### 3.2 治理引擎

负责结构化的治理决策。

在当前阶段，它主要是确定性的，而非完全由模型驱动。

它评估：

- 某个 shell 主体是否可以成为 `candidate`
- 某个 `candidate` 是否可以进入 `probe`
- 某个 `probe` 主体是否可以成为 `active`
- 当前的切换是否应当回滚
- 某个已退役主体是否可以回收为 `shell`
- 某个排队中的自我演化任务是否可以被批准、延期、取消或暂停

这是灵魂层内部的核心治理角色。

### 3.3 治理审计存储

负责保留灵魂侧的可追踪性：

- 评审请求
- 决策
- 执行结果
- 观察窗口观察
- 回滚原因

当前实现已经把治理历史写入灵魂侧存储。

## 4. 模式

Mem 有两个主要的运行角色：

- 记忆管家
- 监督者治理

它们不是两个独立的系统，而是同一灵魂层的两项职责。

用 VoidCube 架构术语来说，它们共享同一个 API-B 治理与记忆域。

历史文档常称之为 `Memory Mode` 和 `Governor Mode`。在当前基线中，运行时应被理解为一个具有共享灵魂侧记忆/治理域的持续后台治理系统，而不是两个由时间窗口驱动的模式。

这也解释了为何系统这一侧使用单独配置的模型/API 能力：

- Agent 侧的工作模型处理任务执行和短期工作记忆
- Mem 侧的模型处理长期记忆压缩、组织、解读和治理决策

## 5. 记忆管家角色

### 5.1 目的

灵魂层的基线职责。

### 5.2 职责

- 写入长期记忆
- 搜索长期记忆
- 压缩历史
- 更新身份描述
- 保留演化档案
- 为治理使用准备记忆侧摘要

### 5.3 典型输入

- `memory_write`
- `memory_search`
- `memory_update`
- `identity_update`
- `history_compress`

### 5.4 约束

该角色不得直接批准：

- `probe` 进入
- `active` 晋升
- 回滚
- 已退役主体回收

它可以摘要事实，但不得取代治理。

## 6. 监督者治理角色

### 6.1 目的

每当系统进入主体治理或自我演化治理场景时，该治理角色即承担职责：

- 候选评审
- 探测批准
- 主体切换
- 回滚
- 切换后观察
- 自我演化任务规划
- 执行放行 / 延期决策

### 6.2 当前实施方向

在当前阶段，监督者治理正在以结构化协议而非自由形式的模型人格成形。

目前已实现的路径包括：

- 双主体槽位
- 结构化探测报告
- 确定性切换批准
- 活跃主体指针更新
- 每个主体槽位隔离的运行时
- 自动观察窗口监督
- 观察后自动回收或回滚
- 用于自我演化治理的明确任务状态

这意味着灵魂侧治理已经以可执行协议的形式存在。

### 6.3 典型输入

- `body_upgrade_request`
- `health_review_request`
- `switch_request`
- `rollback_request`
- `post_switch_review`
- `self_evolution_plan_request`
- `execution_review`

### 6.4 典型输出

- `approve`
- `reject`
- `approve_with_watch`
- `rollback_required`
- `defer`
- `cancel`
- `pause`
- `request_more_evidence`

### 6.5 约束

该治理角色必须：

- 产生结构化输出
- 保留证据摘要
- 保留可审计性
- 把判断与机械执行分离

该治理角色不得直接执行主体动作。它负责决策，由确定性的执行器去执行。

## 7. 治理能力要求

VoidCube 确实需要灵魂侧治理能力。

并非强制要求一个脱离协议、独立且自由形式的监督者模型。

当前推荐的结构是：

- `Mem` = 灵魂层
- `Governor Engine` = 灵魂层内必需的治理能力
- `LLM` = 大脑 / 工作推理 / 可选的治理推理支持

因此，架构上的要求并不是“必须存在一个作为第四存在的特殊监督者人格”。

实际的要求是：

- 治理权威必须存在，
- 它必须存在于灵魂侧域中，
- 它必须可审计安全，并且
- 它必须与机械执行保持分离。

该治理权威主要服务于一个升级目标：

- Agent 主体及其未来的替代

它主要不是先自我升级记忆系统、执行器或网关。

## 8. 可选的未来推理器

模型辅助的治理推理器日后仍可出现，但它应分层置于确定性治理器之上，而不是取代治理协议。

推荐的未来拆分：

- `Governor Engine`
  - 确定性的
  - 协议安全的
  - 切换、回滚和执行窗口决策的主要权威
- `Governor Reasoner`
  - 可选的模型辅助分析
  - 用于模糊情形
  - 用于规则提议、异常解读和长期演化分析

这使身份连续性锚定在协议上，而不是锚定在模型漂移上。

## 9. 灵魂的输入与输出

### 9.1 输入

灵魂层输入应是结构化事件，而不是松散的散文。

推荐的来源：

- 活跃主体
- 候选主体
- 网关
- 生命周期执行器
- 自学习系统

在实践中，这些源于主体的事件仍应可归属于一个具体的子 Agent 槽位，该槽位拥有自己隔离的 `worktree`、`runtime`、`logs` 和元数据。

对于源于用户的操作，CLI 应通过网关或受控协议进入，而不是成为第二个治理真相源。

### 9.2 最小请求形态

请求应包含：

- `request_id`
- `mode`
- `event_type`
- `body_id`
- `source_actor`
- `summary`
- `evidence`
- `constraints`
- `timestamp`

### 9.3 最小响应形态

响应应包含：

- `decision`
- `confidence`
- `risk_level`
- `reasoning_summary`
- `required_actions`
- `watch_window_hint`
- `writeback_events`

## 10. 保留给监督者治理的决策

只有监督者治理可以决定：

- 某个主体是否可以进入 `probe`
- 某个 `probe` 主体是否可以成为 `active`
- 是否需要回滚
- 某个已退役主体是否可以回收
- 某次主体切换是否保持身份连续性
- 某个已规划的自我演化任务是否可以进入执行

这些决策不得由以下对象做出：

- 仅活跃主体
- 仅网关
- 仅 CLI
- 仅执行器

## 11. 自动治理状态

当前架构支持将自动治理状态作为监督者治理的一部分。

其当前形态是：

- 切换批准会创建一个观察窗口
- 治理状态触发一个后台观察窗口任务
- 该任务在观察期内评估健康状况
- 若健康且窗口干净地到期，则回收已退役主体
- 若不健康，则自动触发回滚
- 在自我演化治理周期中，治理还可以放行、延期、取消或暂停排队中的工作

这是项目中灵魂侧自我调节的第一个实用形态。

## 12. 运行时中已反映的当前灵魂事实

在当前阶段，以下事实已在实现中得到体现：

- 活跃主体指针
- 每个槽位的启动目标
- 每个槽位的运行时身份
- 探测报告持久化
- 治理历史持久化
- 自动观察窗口结果记录
- 治理决策与执行器动作分离

这很重要，因为灵魂层不再只是概念性的，如今它已部分体现在可执行协议中。

## 13. 结论

作为灵魂层的 Mem 如今最好被定义为：

- 记忆器官
- 身份器官
- 治理器官

监督者并不是必需的第四层形而上学层次。

但灵魂侧治理是必需的架构能力。

在当前架构中，这一能力由与 Mem 对齐的治理协议承载：

- 记忆核心
- 确定性治理器
- 审计历史
- 观察窗口监督
- 回滚权威
- 执行窗口决策

若日后出现模型辅助的治理推理器，它应是对这一基础的增强，而不是替代。
