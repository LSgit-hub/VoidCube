# 查询规划器 v0.2

## 1. 目的

本文定义现有查询接口之上的一层规划层。

MemAI v1 已经暴露了强大的结构化查询，例如：

- `point_query`
- `range_query`
- `theme_evolution`
- `active_arcs`
- `chapter_summary`
- `evidence_trace`

这些对于系统集成和精确的工具化很有用，但仍要求下游调用方知道该用哪种查询类型。

查询规划器的目的是让调用方用自然任务语言提问，并让 MemAI 决定：

- 运行哪些查询操作，
- 以何种顺序，
- 如何合并它们的输出，
- 如何让回答保持证据有界且对不确定性敏感。

## 2. 设计目标

查询规划器应把如下请求：

- “这个月项目发生了什么变化？”
- “检索工作的当前状态如何？”
- “还有哪些未解决的阻塞影响主线？”
- “在回答之前我应记住哪些稳定的约束？”

转化为结构化的检索计划。

规划器不应：

- 取代核心查询引擎，
- 绕过证据处理，
- 静默虚构无依据的结构，
- 变成一个无法解释其决策的不透明代理。

## 3. 架构中的位置

规划器位于查询引擎之上、最终回答组装之下。

建议的流程：

```text
用户请求
-> 查询规划器
-> 查询计划
-> 查询引擎执行
-> 证据感知的回答组装器
-> 最终响应
```

它应使用现有的查询层，而不是重复实现检索逻辑。

## 4. 核心原则

规划器是检索编排器，而不是摘要器。

它的职责是决定：

- 检索哪些信息，
- 优先采用哪种结构，
- 何时需要更多证据，
- 何时停止并承认不确定性。

摘要步骤应在规划和检索之后进行，而不是在规划器内部。

## 5. 规范输入

建议的规划器输入形态：

```json
{
  "request": "这个月记忆系统发生了什么变化？",
  "reference_time": "2026-03-31T00:00:00Z",
  "detail_level": "standard",
  "include_evidence": true,
  "max_results": 8,
  "mode": "default"
}
```

### 输入字段

- `request`：自然语言检索请求
- `reference_time`：可选的当前时间锚点，用于相对时间短语
- `detail_level`：brief、standard 或 deep
- `include_evidence`：最终组装是否应暴露证据引用
- `max_results`：软性输出上限
- `mode`：规划器姿态，如 default、audit 或 conservative

## 6. 规范输出

建议的规划器输出形态：

```json
{
  "plan_type": "timeline_summary",
  "intent": "summarize_recent_changes",
  "steps": [
    {
      "step_type": "range_query",
      "arguments": {
        "time_start": "2026-03-01T00:00:00Z",
        "time_end": "2026-03-31T23:59:59Z",
        "topic": "memory-system"
      },
      "reason": "请求询问一段有界近期内发生的变化。"
    },
    {
      "step_type": "evidence_trace",
      "target_source": "top_main_arc",
      "reason": "响应应保持证据感知。"
    }
  ],
  "answer_strategy": "timeline_first",
  "requires_audit_note": false,
  "uncertainty_flags": []
}
```

## 7. 规划器职责

规划器应执行五项任务：

1. 识别意图
2. 推断时间范围
3. 选择检索原语
4. 选择回答策略
5. 在规划置信度有限时附加不确定性说明

## 8. 意图类别

v0.2 的首个切片应支持一个小而明确的意图集。

### `summarize_recent_changes`

当请求询问一段时期内发生了什么变化时使用。

优先原语：

- `range_query`
- 可选的 `chapter_summary`
- 可选的 `evidence_trace`

### `trace_theme`

当请求询问某一主题如何演变时使用。

优先原语：

- `theme_evolution`
- 可选的 `range_query`
- 可选的 `evidence_trace`

### `inspect_current_state`

当请求询问当前哪些处于活跃、停滞或未解决状态时使用。

优先原语：

- `active_arcs`
- 可选的 `range_query`

### `explain_memory`

当请求询问某条摘要或结论的来源时使用。

优先原语：

- `evidence_trace`

### `retrieve_stable_context`

当请求询问持久偏好、事实或约束时使用。

优先原语：

- 未来的 `profile_lookup`
- 未来的 `fact_lookup`
- 可选的 `memory_audit`

### `audit_or_dispute`

当请求询问先前版本、矛盾或不确定记忆时使用。

优先原语：

- `evidence_trace`
- 未来的 `memory_audit`
- 未来的冲突感知画像检索

## 9. 时间范围解析

规划器应保守地解析时间表达。

示例：

- “今天” -> 以 `reference_time` 为中心的时点或短区间
- “本周” -> 有界的周区间
- “本月” -> 有界的月区间
- “最近” -> 软性的近期区间，视系统策略而定，可能是最近 14 或 30 天
- “历史上” -> 宽范围或章节级策略

当请求缺少明确的时间跨度时：

- 如果措辞暗示如此，优先采用当前状态或主题检索
- 否则附加不确定性说明，而不是静默编造一个任意的窗口

## 10. 实体与主题抽取

规划器应从请求中识别轻量级的检索锚点：

- 主题
- 实体
- 主体
- 记忆类型
- 状态目标，如 active、stalled、blocked、unresolved

首个切片可用基于规则的抽取来实现：

- 关键词词典
- 简单的别名映射
- 来自已知主题和实体的精确短语匹配

在日后加入可选的 LLM 规划之前，这应保持可解释且确定性。

## 11. 步骤选择规则

### 11.1 何时使用 `range_query`

在以下情况优先使用 `range_query`：

- 请求包含有界的时期
- 用户询问“发生了什么变化”
- 用户询问近期进展或进度

### 11.2 何时使用 `theme_evolution`

在以下情况优先使用 `theme_evolution`：

- 用户询问“X 是如何演变的”
- 请求以某一跨时间的主题或实体为中心

### 11.3 何时使用 `active_arcs`

在以下情况优先使用 `active_arcs`：

- 用户询问当前状态
- 用户询问活跃、停滞、休眠或未解决的工作

### 11.4 何时使用 `chapter_summary`

在以下情况优先使用 `chapter_summary`：

- 请求的时间跨度很大
- 用户请求阶段级或历史性概览
- 时间跨度太宽，无法仅靠场景/脉络密集的叙述来覆盖

### 11.5 何时使用 `evidence_trace`

在以下情况优先使用 `evidence_trace`：

- 用户询问“为什么”
- 用户请求证据支持
- 规划器处于审计模式
- 回答使用了应保持可核查的强主张

## 12. 回答策略

规划器应明确选择一种回答组装策略。

建议的初始策略：

### `timeline_first`

用于近期变化和有界摘要。

输出姿态：

- 先呈现已观察的进展
- 其次是主要脉络和转折点
- 最后是证据和不确定性

### `theme_first`

用于纵向的主题演变。

输出姿态：

- 变化的时间线
- 当前状态
- 主要转折点

### `state_first`

用于当前状态或阻塞检查。

输出姿态：

- 活跃脉络
- 停滞或未解决的脉络
- 开放问题

### `audit_first`

用于争议、修订或来源检查。

输出姿态：

- 当前主张
- 先前版本
- 冲突分支
- 证据链

### `stable_context_first`

用于未来的画像/事实记忆请求。

输出姿态：

- 稳定的约束、偏好和事实
- 仅在需要时提供时间线上下文

## 13. 不确定性处理

规划器应在以下情况产生不确定性说明：

- 时间范围无法干净地解析
- 请求混合了多种意图
- 没有任何查询原语明显占优
- 可用的检索信号过于薄弱

标志示例：

```json
{
  "uncertainty_flags": [
    "time_window_is_implicit",
    "request_has_multiple_possible_intents"
  ]
}
```

这些标志日后应帮助下游回答组装产生诚实的措辞。

## 14. 规划器模式

建议的初始模式：

### `default`

- 均衡的规划
- 证据感知但简洁

### `conservative`

- 更窄的检索
- 更强的不确定性说明倾向
- 避免组合过多查询类型

### `audit`

- 最大化可追踪性
- 优先呈现证据和取代可见性
- 仅在附有明确警告时纳入存在争议或薄弱的记忆

## 15. 规范步骤 Schema

建议的步骤形态：

```json
{
  "step_type": "range_query",
  "arguments": {},
  "reason": "为何选择此查询",
  "required": true,
  "optional": false,
  "consumes": [],
  "produces": ["range_summary"]
}
```

字段语义：

- `step_type`：检索原语
- `arguments`：精确的查询参数
- `reason`：人类可读的理由
- `required`：最终回答是否依赖此步骤
- `optional`：当上游结果薄弱时，计划是否可跳过此步骤
- `consumes`：此步骤所需的前序输出标识符
- `produces`：带标签的输出产物

## 16. 示例计划

### 示例 A：近期变化

请求：

- “这个月项目发生了什么变化？”

计划：

1. 解析当前月的边界
2. 运行 `range_query`
3. 若存在强主线脉络，则对顶部结果运行 `evidence_trace`
4. 以 `timeline_first` 组装

### 示例 B：主题演变

请求：

- “到目前为止，检索是如何演变的？”

计划：

1. 抽取主题 = retrieval
2. 运行 `theme_evolution`
3. 若时间线密度较低，可选运行宽泛的 `range_query`
4. 以 `theme_first` 组装

### 示例 C：当前阻塞

请求：

- “还有哪些未解决的阻塞影响主线？”

计划：

1. 运行 `active_arcs`
2. 过滤出停滞、阻塞或未解决的模式
3. 可选地在近期时段运行 `range_query` 以获取支撑性进展
4. 以 `state_first` 组装

### 示例 D：解释某条摘要

请求：

- “这个结论从何而来？”

计划：

1. 若可用，识别目标记忆 ID
2. 运行 `evidence_trace`
3. 以 `audit_first` 组装

## 17. 与画像和事实记忆的交互

一旦 v0.2 加入画像/事实记忆，规划器还应识别如下请求：

- “我应记住哪些偏好？”
- “回答前有哪些稳定约束适用？”
- “用户的语言偏好是否已经改变？”

在这些情形下：

- 稳定记忆检索应先于时间线检索进行
- 时间线检索仅作为支撑性上下文使用

这就是规划器应为每个请求明确选择回答策略、而不是一律假设时间线优先的原因。

## 18. 失败规则

规划器应保守地失败。

糟糕的规划器行为包括：

- 用户询问近期有界时期时却选择了宽泛的历史摘要
- 编造一个请求中没有依据的主题
- 对审计导向的问题遗漏证据规划
- 把混合意图的请求当作无歧义来处理

偏好的失败姿态：

- 生成更窄的计划
- 附加不确定性标志
- 仅在绝对必要时请求一次有限的澄清

## 19. 基准测试指导

增加规划器专用的测试夹具族，例如：

- 近期时段摘要请求
- 主题演变请求
- 当前状态请求
- 审计与来源请求
- 混合意图的模糊请求
- 画像/事实检索请求

建议的指标：

- intent_classification_accuracy
- temporal_scope_accuracy
- query_step_selection_accuracy
- evidence_step_recall
- uncertainty_restraint

## 20. 最小可行 v0.2 切片

若首个可用的规划器能够做到以下各项，即已足够：

- 分类 4 到 6 种常见意图
- 解析简单的时间短语
- 使用现有查询原语生成明确的计划
- 解释每个步骤为何被选中
- 为模糊请求附加不确定性标志

这些最初都可以用启发式方法实现。

## 21. 建议的实施顺序

1. 定义规划器的输入和输出 schema
2. 增加基于规则的意图分类器
3. 增加时间范围解析器
4. 增加步骤选择规则
5. 增加回答策略选择
6. 增加不确定性标志
7. 增加规划器基准测试夹具
8. 日后考虑可选的 LLM 辅助规划

## 22. 成功标准

当调用方无需了解 MemAI 的内部查询分类法即可有效使用系统时，规划器即告成功。

这意味着调用方可以这样提问：

- “发生了什么变化？”
- “什么仍然处于活跃状态？”
- “这是如何演变的？”
- “我应记住什么？”
- “这从何而来？”

而 MemAI 能将其转化为保持结构化、证据感知且可审计的检索行为。
