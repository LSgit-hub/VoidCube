# 画像与事实记忆 v0.2

## 1. 目的

本文定义 MemAI v0.2 的第一个非时间线记忆层。

v1 系统擅长通过以下结构组织历史发展：

- `Event`
- `Scene`
- `Arc`
- `Epoch`

然而，许多持久记忆并非天然以有界时间的片段来表达。例如：

- 稳定的用户偏好，
- 持续的项目约束，
- 长期的术语定义，
- 明确的身份陈述，
- 跨多个场景仍然有效的持久事实断言。

v0.2 的目标是为这些条目增加一个结构化的记忆族，同时不削弱现有时间线链以时间优先的设计。

## 2. 设计目标

新层应让系统记住：

- 跨时间仍然成立的事物，
- 用户或项目一贯偏好的事物，
- 指导未来工作的定义或规则，
- 已被纠正、争议或替换的事实。

它不应：

- 取代时间线链，
- 从稀疏信号推断人格特质，
- 把一次性陈述变成稳定的身份主张，
- 静默覆盖先前的事实状态。

## 3. 核心概念

画像与事实记忆是一个并行的记忆族，而不是 `Event -> Scene -> Arc -> Epoch` 内部的新步骤。

这意味着：

- 时间线记忆回答：“发生了什么，以及它是如何演变的？”
- 画像/事实记忆回答：“现在哪些内容应被稳定地知晓？”

这两层应互相引用，但它们服务于不同的检索目的。

## 4. 记忆类型

v0.2 应从一个名为 `ProfileMemory` 的单一共享类型族开始，并带有一个必填的子类型字段：

```text
preference | identity | constraint | definition | fact
```

这样既能保持初始实现小巧，又允许差异化的行为。

### `preference`

用于持久性的用户或项目偏好。

示例：

- 偏好中文回复
- 偏好简洁摘要
- 偏好证据优先的回答

### `identity`

仅当被直接陈述或有强证据时，才用于明确的自我描述角色或持久身份事实。

示例：

- 用户是项目负责人
- 助理充当记忆管家

### `constraint`

用于操作规则、护栏或不可协商的项目约束。

示例：

- 不得静默改写历史
- 证据必须保持可见
- 提供方兼容性必须进行回归测试

### `definition`

用于稳定的术语或概念映射。

示例：

- 主线意味着在结构上居于核心的长期发展
- 纪元意味着章节级别的历史时期

### `fact`

用于在单一时刻之外仍然有用的持久断言。

示例：

- 启发式后端是默认选项
- LLM 后端是可选项
- 状态更新是增量式的，而非完全重建

## 5. 规范形态

建议的初始形态：

```json
{
  "id": "profile_001",
  "type": "profile_memory",
  "memory_kind": "constraint",
  "subject": "project",
  "predicate": "requires",
  "value": "证据优先的检索",
  "summary": "该项目要求证据优先的检索，而非缺乏依据的抽象。",
  "confidence": 0.92,
  "certainty_state": "observed",
  "status": "active",
  "valid_from": "2026-03-22T00:00:00Z",
  "valid_to": null,
  "evidence_refs": ["turn_001", "scene_001"],
  "source_turns": ["turn_001"],
  "parent_timeline_refs": ["scene_001", "arc_001"],
  "supersedes": [],
  "conflict_refs": [],
  "created_at": "2026-03-22T00:00:00Z",
  "updated_at": "2026-03-22T00:00:00Z",
  "last_reviewed_at": "2026-03-22T00:00:00Z"
}
```

## 6. 字段语义

- `id`：不可变记忆标识符
- `type`：固定为 `profile_memory`
- `memory_kind`：子类型分类器
- `subject`：该记忆所指向的实体、行为者或范围
- `predicate`：规范化关系标签
- `value`：当前断定的值
- `summary`：人类可读的复述
- `confidence`：对断言的置信度
- `certainty_state`：断言的认知状态
- `status`：生命周期状态，如 active、dormant、superseded
- `valid_from`：断言开始生效的时间
- `valid_to`：断言停止生效的时间（若已知）
- `evidence_refs`：支撑性的来源引用
- `source_turns`：直接支撑的 Turn（若可用）
- `parent_timeline_refs`：衍生出该事实记忆的时间线记忆
- `supersedes`：同一逻辑事实的旧版本
- `conflict_refs`：与此相冲突的并行断言

## 7. 新增认知状态

画像/事实记忆应引入一个新的公共字段：

```text
certainty_state = observed | inferred | disputed | pending_verification | confirmed
```

### `observed`

直接由明确的来源材料支持。

### `inferred`

由重复或结构性证据支持，但仍带解读成分。

### `disputed`

与另一个处于活跃状态的断言冲突。

### `pending_verification`

看似合理，但尚不足以进行默认检索。

### `confirmed`

已观察并在多个来源或修订中得到强化。

这一字段日后很可能需要推广到记忆系统的更多部分，但 v0.2 可以先从这里开始。

## 8. 抽取规则

### 8.1 正向抽取准则

仅当以下至少一项为真时才创建画像/事实记忆：

- 来源明确陈述了一个稳定的偏好、角色、约束或事实
- 同一主张在多个 Turn 或场景中反复出现
- 该主张反复主导下游决策
- 该主张即使脱离原始局部场景仍然有用

### 8.2 负向抽取准则

不要为以下内容创建画像/事实记忆：

- 短暂的情绪
- 没有重复的一次性愿望
- 未被采纳的假设性想法
- 缺乏依据的性格结论
- 孤立的情绪表达
- 没有强化支持的弱暗示偏好

### 8.3 升级阈值

一个稳妥的初始启发式：

- 一次明确的强陈述即可创建 `preference`、`constraint` 或 `definition`
- `identity` 和更敏感的 `fact` 记忆应要求更强的支持或重复证据

## 9. 与时间线记忆的关系

画像/事实记忆不应破坏规范的包含链。

相反，它应通过引用连接到时间线记忆：

- `parent_timeline_refs`
- `evidence_refs`

建议的行为：

- 事件和场景仍是抽取来源
- 脉络和纪元可强化画像/事实的置信度
- 画像/事实记忆可在相关时与时间线查询结果一并呈现

## 10. 修订与冲突规则

### 10.1 取代

当较新的记忆取代同一逻辑事实的较旧断言时使用 `supersedes`。

示例：

- 旧：偏好详细解释
- 新：现在偏好简洁回复

旧记录应保持可审计，而不是被删除。

### 10.2 冲突

当两个存续中的断言无法同时被视为当前有效时使用 `conflict_refs`。

示例：

- 一条记忆说用户偏好中文
- 另一条说用户现在在代码评审会话中偏好英文

这可能在日后通过修订解决，但不应立即被抹平。

### 10.3 有效期窗口

`valid_from` 和 `valid_to` 应能表达对时间敏感的事实，例如：

- 临时的偏好变化
- 仅在某一阶段适用的项目约束
- 随时间变化的角色转变

## 11. 查询接口

建议的 v0.2 查询新增：

### `profile_lookup`

返回某一主体或范围的当前稳定记忆。

请求示例：

```json
{
  "query_type": "profile_lookup",
  "subject": "user",
  "memory_kinds": ["preference", "identity"],
  "include_disputed": false
}
```

### `fact_lookup`

返回某一项目、个人或实体的稳定事实和约束。

### `memory_audit`

返回同一逻辑断言的活跃、已取代和存在争议的版本。

## 12. 检索行为

默认检索应：

- 优先 `confirmed` 和 `observed`
- 仅当置信度足够时才纳入 `inferred`
- 除非请求审计模式，否则隐藏 `disputed`
- 默认在简洁回答中隐藏 `pending_verification`

组装时间线回答时，相关的画像/事实记忆可附加在单独的分区下，例如：

```json
{
  "stable_context": [],
  "timeline_result": {}
}
```

这样可避免把“发生了什么”和“什么仍然成立”混在一起。

## 13. 存储策略

建议的初始实现：

- 把画像/事实记忆与持久状态文件一并存储
- 将其作为与 events/scenes/arcs/epochs 分离的集合保存
- 保留对时间线 ID 和来源 Turn 的引用

建议的顶层状态划分：

```json
{
  "version": 1,
  "result": {
    "turns": [],
    "events": [],
    "scenes": [],
    "arcs": [],
    "epochs": [],
    "profiles": []
  }
}
```

## 14. 基准测试指导

v0.2 应为画像/事实记忆增加专门的测试夹具族：

- 重复偏好的抽取
- 一次性偏好的不抽取
- 明确约束的捕获
- 术语定义的捕获
- 事实之间冲突的创建
- 从旧事实到新事实的修订
- 拒绝创建缺乏依据的性格记忆

关键指标：

- profile_precision
- fact_precision
- dispute_detection
- overreach_restraint
- revision_traceability

## 15. 最小可行 v0.2 切片

若初始实现能够做到以下各项，即已足够：

- 抽取明确的 `preference`、`constraint` 和 `definition` 记忆
- 将其保持在线包含链之外
- 支持明确的取代
- 暴露一个用于当前有效画像/事实检索的小型查询接口
- 保留证据链接和可审计性

## 16. 首个切片的非目标

首个 v0.2 切片暂时不应尝试以下全部事项：

- 完整的本体学习
- 人格建模
- 概率图推理
- 没有明确策略的自动冲突解决
- 仅依赖 LLM 的复杂抽取流水线

首个切片应保持保守、可解释并以证据为界。

## 17. 建议的实施顺序

1. 添加 `ProfileMemory` 的 schema 定义
2. 扩展持久状态存储
3. 为明确的偏好、约束和定义实现启发式抽取
4. 为当前有效的画像/事实检索增加查询支持
5. 增加修订和冲突处理
6. 增加基准测试夹具
7. 日后再增加可选的基于 LLM 的抽取

## 18. 成功标准

当 MemAI 能够清晰回答以下两类问题时，本设计即告成功：

- “这个项目随时间发生了什么？”
- “系统现在应记住哪些稳定的偏好、约束和事实？”

没有这一层，MemAI 主要仍是一个时间线系统。
有了这一层，它开始成为一个更完整的长期记忆框架。
