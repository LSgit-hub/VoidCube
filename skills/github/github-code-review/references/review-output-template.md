# 代码审查输出模板

将此作为 PR 审查摘要评论的结构。复制并填写各个部分。

## 用于 PR 摘要评论

```markdown
## 代码审查摘要

**结论：[批准 ✅ | 需要修改 🔴 | 已审查 💬]**（[N] 个问题，[N] 条建议）

**PR：** #[number] — [title]
**作者：** @[username]
**修改文件：** [N]（+[additions] -[deletions]）

### 🔴 严重问题
<!-- 合并前必须修复的问题 -->
- **file.py:line** — [描述]。建议：[修复方案]。

### ⚠️ 警告
<!-- 应该修复但不严格阻塞的问题 -->
- **file.py:line** — [描述]。

### 💡 建议
<!-- 非阻塞的改进、风格偏好、未来考虑 -->
- **file.py:line** — [描述]。

### ✅ 看起来不错
<!-- 指出做得好的地方 — 正面反馈 -->
- [做得好的方面]

---
*由 Voidcube Agent 审查*
```

## 严重程度指南

| 级别 | 图标 | 使用场景 | 阻塞合并？ |
|-------|------|-------------|---------------|
| 严重 | 🔴 | 安全漏洞、数据丢失风险、崩溃、核心功能损坏 | 是 |
| 警告 | ⚠️ | 非关键路径的 bug、缺少错误处理、新代码缺少测试 | 通常是的 |
| 建议 | 💡 | 风格改进、重构想法、性能提示、文档缺失 | 否 |
| 看起来不错 | ✅ | 清晰的模式、良好的测试覆盖、清晰的命名、明智的设计决策 | 不适用 |

## 结论决策

- **批准 ✅** — 零严重/警告项。仅有建议或全部通过。
- **需要修改 🔴** — 存在任何严重或警告项。
- **已审查 💬** — 仅观察（草稿 PR、不确定的发现、信息性）。

## 用于内联评论

在评论前加上严重程度图标以便快速扫描：

```
🔴 **严重：** 用户输入直接传递给 SQL 查询 — 使用参数化查询防止注入。
```

```
⚠️ **警告：** 此错误被静默吞掉。至少应该记录它。
```

```
💡 **建议：** 这可以用字典推导式简化：
`{k: v for k, v in items if v is not None}`
```

```
✅ **不错：** 这里很好地使用了上下文管理器 — 确保异常时清理资源。
```

## 用于本地（推送前）审查

在推送前进行本地审查时，使用相同的结构，但作为消息呈现给用户而不是 PR 评论。跳过 PR 元数据头部，直接从严重程度部分开始。
