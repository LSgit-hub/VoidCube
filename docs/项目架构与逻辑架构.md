# VoidCube：全天候感知型自主智能体系统

更新日期：2026-07-27

> 本文采用“产品理论 + 当前代码映射”的写法。第一部分描述 VoidCube 想成为的系统，第二部分明确当前源码已经实现、部分实现和尚未实现的内容。不能从代码证明的能力不会被写成“已有”。

## 一、项目定位

VoidCube 的目标不是一个等待用户输入的命令行脚本，而是一个可以持续观察运行环境、理解用户任务、维护长期记忆、在治理约束下提出自主任务的智能体系统。

理论上的核心实体称为“星子”：它代表具备持续上下文、记忆、价值约束和主动判断能力的监督者人格。星子不是另起一个与 Supervisor 并列的 Agent 进程，而是由 Supervisor、Memory/MemAI 和 API-B 共同承载的产品人格。

```text
星子（理论实体）
  = Supervisor（感知、判断、治理）
  + Memory/MemAI（长期记忆与经历）
  + API-B（后台理解与压缩）
  + Gateway scene/activity（运行态观察投影）
```

工具 Agent 是星子的执行躯体：它负责与用户对话、调用工具、执行代码和提交结果。Supervisor 不应直接获得工具的操作系统权限；它通过治理任务把“应该做什么”交给 API-A 执行面。

星子具有两个互斥模式：

- `daily_companion`：系统启动后的常态。星子全天候运行，以语音服务用户，周期读取 VoidCube 内部事件，理解用户正在通过 API-A Agent 完成什么目标，并在证据充分且确有帮助时提醒。
- `auto_evolution`：用户通过 `/auto` 显式进入。星子暂停伴侣职责和用户行为感知，只消费 Auto 会话的冻结 evidence packet 与自身治理信号，专注记忆整理、自学习、自计划和受治理的身体进化；用户通过 `/auto-q` 退出后回到日常模式。

因此，`/auto` 不是“星子是否运行”的总开关，而是星子从日常伴侣切换到自主进化的模式开关。

### 1.1 单所有者与身份边界

VoidCube 当前是单机、单所有者系统，不建立人类用户注册、账号、登录或多用户权限体系。三个容易混淆的概念必须分开：

- `GATEWAY_AUTH_TOKEN`、`service_token` 和 `session_token` 只认证内部服务或 CLI 会话，防止本机其他进程伪造 Memory actor；它们不识别人类用户；
- `owner_id=local-user` 与 `workspace_id=default` 是固定的本地数据作用域，不是用户表、账号 ID 或租户系统；
- 本机所有者声纹模板只用于在音频进入 STT 前过滤背景声音、其他说话人和误触发，不创建账户，也不承担登录认证。

## 三、整体架构

VoidCube 当前由六个逻辑组件构成。前三个是已经可以独立运行的服务，后三个分别是 Agent、Supervisor 和交互扩展。

```text
                         ┌─────────────────────────────┐
                         │         用户 / 外部 UI        │
                         └──────────────┬──────────────┘
                                        │ CLI / HTTP
                         ┌──────────────▼──────────────┐
                         │ Gateway 神经中枢（6000）      │
                         │ 注册、路由、活动、双泳道、trace│
                         └──────┬───────────┬───────────┘
                                │           │
                /mem/*          │           │ /supervisor/*
        ┌───────────────────────▼─┐   ┌─────▼────────────────────┐
        │ Memory Service（6001）   │   │ Supervisor（6002）        │
        │ Tier1/Tier2/MemAI/治理史 │   │ API-B/内生驱动/任务治理    │
        └─────────────────────────┘   │ 内嵌 Execution Facade      │
                                      └─────┬──────────────────────┘
                                            │ Adapter
                                      ┌─────▼──────────────────────┐
                                      │ Execution / Body runtime    │
                                      │ probe、升级、切换、观察、回滚 │
                                      └─────────────────────────────┘

        API-A Agent（CLI、工具、代码和自主任务执行）
          -> mem Provider -> Gateway -> Memory/Supervisor/Executor
```

当前代码层的最短记忆调用链是：`AIAgent -> mem Provider -> Gateway /api/mem/* -> Memory Service -> MemAI`。

### 1. 神经中枢网关（已有）

代码实现：`systems/gateway/internal_gateway.py:InternalGateway`。

已实现职责：

- `/register`、`/health/{service_id}` 服务发现和健康状态；
- `/api/{path}` 统一代理；服务类型前缀为 memory `/mem/`、supervisor `/supervisor/`、executor `/executor/`；
- `/v1/chat/completions`、`/v1/agent/query` Agent 入口；
- session 租约、活动计数、scene 聚合和 trace 查询；
- `user_chat` 与 `supervisor_task` 两条活动泳道；
- 代理时保留查询参数和重复键。

需要修正的理论描述：

- Gateway 有服务路由和活动投影，但“蓝绿切换”实际由 Body registry/slot 生命周期实现，不是 Gateway 自己完成代码切换；
- `GATEWAY_AUTH_TOKEN` 配置后，服务注册与 CLI session 注册必须通过 Gateway 根鉴权；注册成功后 Gateway 为服务/session 签发独立凭证，Memory 代理据此注入可信 `memory_actor`；
- 上述“注册”只表示内部服务或 CLI session 获取进程凭证，不存在人类用户注册流程；
- 状态推送目前不是 WebSocket，Supervisor UI 使用 HTTP + Server-Sent Events（`EventSource('/ui/events')`）。

### 2. 长期记忆系统（已有）

代码实现：`systems/memory/memory_service.py`、`systems/memory/domain.py`、`systems/memory/promotion.py`、`systems/memory/recall.py`、`systems/memory/tier1_to_tier2_bridge.py`、`Mem/src/memai/`。

已实现职责：

- Tier 1：SQLite sessions、turns、turn archive，保存近期原始对话；
- Tier 2：MemAI Event、Scene、Arc、Epoch 结构化记忆；
- `/recall` 混合召回 Tier 1、Tier 2、Profile 和 archive；
- 召回计划、多语言概念词、时间提示、去重、动态权重和字符预算；
- Tier 1 -> Tier 2 质量门禁、压缩审计、回链和维护；
- Profile 显式事实捕获、supersedes、撤销和 tombstone；
- 治理事件仓库、备份、语义索引和生命周期维护。

需要修正的理论描述：

- 当前不是单一“星子数据库 + 表前缀”的 `agent_* / stellar_* / shared_*` 设计；
- 当前隔离键是 `owner_id + workspace_id`，同一 Memory Service 的表由 scope 过滤保护；
- 当前产品只有一个本机所有者；`owner_id=local-user` 是固定存储作用域，不是人类用户实体；
- 没有代码证明存在 `v_agent_activity` 这一 SQL 视图。星子感知 Agent 活动的实际来源是 Gateway activity、Agent scene、Supervisor observation input 和治理事件；
- Supervisor 的任务 JSON 是可恢复投影，长期治理真相在 MemAI `GovernanceEventRepository`，不是独立 `task_queue.db`。

### 3. Agent（执行躯体，已有）

代码实现：`run_agent.py:AIAgent`、`cli.py`、`agent/`、`tools/`。

Agent 通过 API-A 执行用户任务：

- CLI 接收文字、附件和 slash 命令；
- `api_request.py` 构造 OpenAI-compatible Chat Completions 请求；
- `stream_response.py` 装配文本、推理、工具调用和 usage；
- `ToolExecutionCoordinator` 完成 schema、审批、并发调度、结果顺序和中断；
- `context_engine/context_compressor` 管理上下文压力和恢复；
- `turn_finalization` 完成消息、诊断、Session 和 Memory 写回；
- tools environment 支持 local、docker、podman、ssh、modal、singularity、daytona 等后端；
- Body runtime 支持 candidate、probe、激活、观察窗口和 Git lineage 回滚。

“Agent 无状态”需要精确表述：Agent 不拥有跨会话长期事实真相，但会持有会话消息、游标、客户端和当前工具回合等可恢复工作状态；这些状态不能被描述成完全无状态服务。

### 4. 监督者/星子核心（已有，仍在扩展）

代码实现：`systems/supervisor/supervisor.py`、`endogenous_drive.py`、`planning_runtime.py`、`autonomous_chain_store.py`。

内部模块对应关系：

| 理论模块 | 当前实现 |
| --- | --- |
| 感知引擎 | `get_runtime_observation_input`、Gateway activity/scene、trace、Memory 证据和身体状态组装 |
| 内生驱动器 | `EndogenousDriveEngine`、need/intent/signal/reflection 和 proposal |
| 任务管理器 | `AutonomousChainStore`、任务状态转换、claim、execution request 和恢复 |
| 价值观引擎 | 当前由 Supervisor 配置模型、cognition charter、prompt policy、Governor 和程序护栏共同承担；没有可单独加载的 `values.json` 引擎 |
| 主动提醒决策器 | `_judge_daily_companion_evidence` + `_normalize_companion_judgement`；低置信度或帮助收益不足时强制静默 |
| 状态推送模块 | `/ui/state` + `/ui/events` SSE；不是 WebSocket |
| 执行委托 | Supervisor -> VoidCubeExecutionFacade -> Adapter；任务通过 Gateway `supervisor_task` 泳道交给 API-A |

Supervisor 已增加明确的 `stellar_mode` 状态机，没有复制第二个 Agent 进程：

```text
服务启动
  -> daily_companion
       ├─ 周期读取内部事件
       ├─ 等待/响应用户语音
       └─ 有充分证据时提供帮助或提醒

/auto
  -> auto_evolution
       ├─ 停止日常用户感知与伴侣提醒
       ├─ 运行现有自主链路
       └─ 自学习、自计划、记忆整理、Body 进化

/auto-q
  -> 中断或收口 Auto 任务
  -> daily_companion
```

日常伴侣循环与现有 Auto 内生驱动可以复用 observation、Memory client、API-B client、trace 和 UI 投影，但必须采用不同的输入过滤、prompt、任务类型和记忆 namespace。日常循环不得向 AutonomousChainStore 投放自进化任务；Auto 启动时停止伴侣循环和语音会话，并由 `perception_scope=autonomous_only` 强制清洗用户请求、会话数量、最近元数据和通用错误计数，只保留自身治理、记忆维护、Body runtime 与 API-A 自主执行泳道的必要信号。

Supervisor 的职责边界是“判断和治理，不直接执行”：

- 判断是否值得做、证据是否足够、风险如何控制；
- 决定观察、延后、批准、暂停、拒绝或需要用户同意；
- 任务状态变化必须先追加治理事件；
- 由 API-A 自主执行组件和 Execution 完成实际工具/身体副作用；
- 结果写回 Mem、任务投影和下一轮 observation。

### 5. 语音交互模块（单轮与持续监听已实现）

现有实现位于 `systems/voice/`，Supervisor 提供 `/voice/status`、`/voice/microphone`、`/voice/owner-template`、`/voice/session/start`、`/voice/session/interrupt`、`/voice/continuous/start` 和 `/voice/continuous/stop`。链路为：录音 -> 本机所有者声纹匹配 -> STT -> 唤醒词门控 -> `/companion/message` -> TTS -> 可中断播放。伴侣对话通过 Gateway 写入 `companion` 域；原始录音和合成临时文件默认在 `finally` 中删除。

持续模式以短音频段循环进行声纹认证和 STT，只有出现配置的唤醒词（默认“星子”）或处于短暂唤醒窗口时才调用 API-B。进入 Auto、用户中断、关闭麦克风和 Supervisor 退出都会停止监听任务与播放。主动提醒通过同一 TTS/中断通道播报，并服从免打扰、冷却和语音开关。当前声纹仍不是生产级模型；分段 STT 唤醒适合作为状态机基线，后续应替换为成本更低的本地唤醒检测，同时保持“只存模板、不存原音”的合同。

### 6. Web UI 拟人化界面（主要控制已接入）

Supervisor 内置 UI 运行时位于 `systems/supervisor/ui_runtime.py`，提供 `/ui`、`/ui/state` 和 `/ui/events`。它可以展示 supervisor、agent、executor、任务、scene、活动和自主门控状态。

当前没有独立 `web_ui/` 包或 WebSocket 客户端，但 Supervisor 内置 UI 已提供 2D 小屋、角色、状态投影、语音控制和主动提醒策略面板。它通过 `/ui/state` 快照与 `/ui/events` SSE 更新；提醒策略通过 `/companion/reminder-policy` 读写 canonical `VOIDCUBE_HOME/config.yaml`，不使用浏览器本地状态。动画状态不能反向写入 Supervisor 真相库。

## 四、双 API 分配策略

| 角色 | API 槽位 | 当前用途 | 代码边界 |
| --- | --- | --- | --- |
| 工具 Agent | API-A | CLI 对话、工具调用、代码生成、自主任务执行 | `run_agent.py`、`agent/*`、自主执行组件 |
| 星子/Supervisor | API-B | 感知整理、内生判断、治理建议和审查 | `systems/supervisor/*` |
| 记忆智能处理 | API-B | Tier 1 -> Tier 2 抽取、压缩、Scholar、维护判断 | `Mem/src/memai/*`、Memory Service |

API-A/API-B 是职责槽位，不是固定模型名。两者可以来自同一 Provider，但必须拥有独立的配置、凭据归属、超时/重试和审计语义。所有现役请求统一使用 OpenAI-compatible Chat Completions，不允许不同模块各自探测协议或偷偷切换回退协议。

## 五、三域记忆隔离方案

### 5.1 当前实现

```text
同一 Memory Service
  ├─ sessions / turns / archive       Tier 1
  ├─ compressed memories               Tier 2
  ├─ profile memories / tombstones
  ├─ governance events
  └─ recall traces / feedback / indexes

所有读写按 owner_id + workspace_id + memory_domain 过滤
服务端按 Gateway 注入的 `memory_actor` 推导可读/可写域。API-A session 凭证固定映射为 `api_a`；Supervisor 服务凭证默认映射为 `stellar_companion`，可在受限能力集合内使用 `stellar_auto` 或 `governor`；Executor 固定映射为 `execution`。客户端正文中的 actor 会被丢弃并覆盖。
Agent 通过 mem Provider -> Gateway -> Memory API
Supervisor 通过 Gateway/Memory API 读取治理与活动证据
```

Agent 与星子不是靠表名隔离，而是靠 scope、`memory_domain`、固定 actor 权限矩阵、服务端 SQL 条件和索引边界隔离。当前隔离适用于受 Gateway 管理的内部调用；Gateway 身份注入完成后才适合对不可信网络宣称服务级强隔离。Agent 的召回上下文是本轮临时上下文，不会因为被注入 prompt 就自动写回成为新的记忆。

### 5.2 已实现方案：在现有 scope 上增加三个记忆域

不建议使用三套数据库，也不建议仅依赖表名前缀。更稳妥的方案是在现有 `owner_id + workspace_id` 隔离基础上增加强制的 `memory_domain`，仍由同一个 Memory Service 统一备份、迁移、索引和召回：

| memory_domain | 内容 | 写入者 | 读取者 |
| --- | --- | --- | --- |
| `agent_interaction` | 用户与 API-A 的对话、工具结果、任务产物和会话事实 | AIAgent | AIAgent；日常星子只读经过筛选的摘要/证据 |
| `companion` | 用户与星子的语音语义、提醒结果、用户目标理解、伴侣关系和偏好 | 日常星子 | 日常星子；API-A 默认不可读 |
| `evolution` | Auto 模式的自学习、自计划、实验、治理、Body lineage 和复盘 | Auto 星子/Supervisor | Auto 星子、Governor、Execution；日常星子和 API-A 默认不可读 |

`shared` 不应作为第四个任意写入域。当前实现通过 `memory_promotion_refs` 完成显式提升：来源记忆不移动，Memory Service 只创建带 `source_type`、`source_domain`、`source_memory_id`、`target_domain`、`reason`、`approved_by`、`approval_ref` 和生命周期的只读引用。Recall 需要使用目标域权限，再由服务端按精确源 ID 解引用；返回结果与 recall trace 同时携带提升引用和源证据，不会在目标域复制正文。

允许方向是固定策略而不是调用方自由声明：

| 来源 | 目标 | 用途 |
| --- | --- | --- |
| `agent_interaction` | `companion` | 将已确认的用户目标或长期事实提升为伴侣可持续使用的知识 |
| `evolution` | `companion` | 将经过批准的 Auto 结论提升为日常伴侣可用知识 |

`companion -> agent_interaction` 被禁止，避免语音关系和私密偏好泄露给 API-A；任何域 `-> evolution` 都被禁止，避免实时用户内容污染 Auto。只有 `governor` 和 `memory_maintenance` 可以创建或撤销提升引用。

### 5.3 按模式规定读写矩阵

| 调用方/模式 | `agent_interaction` | `companion` | `evolution` |
| --- | --- | --- | --- |
| API-A 用户会话 | 读写 | 禁止 | 禁止；只有当前获批任务的 execution request 可作为临时输入 |
| 星子日常模式 | 只读、按近期/目标筛选 | 读写 | 禁止 |
| 星子 Auto 模式 | 只读 Auto 会话冻结的 evidence packet 和自身治理信号，不读实时用户活动 | 禁止 | 读写 |
| Memory 维护 | 按域独立压缩、衰减和索引 | 按域独立 | 按域独立 |
| Governor/Execution | 禁止直接读取用户对话 | 禁止 | 读取获批任务、lineage 和审计证据 |

这个矩阵解决三个污染问题：

1. API-A 不会看到星子的私密语音关系记忆；
2. 日常星子能够理解用户与 API-A 的长期目标，但不能修改 API-A 的历史；
3. Auto 模式的自言自语、计划和失败实验不会进入用户长期记忆，也不会影响日常陪伴，除非经过明确提升。

### 5.4 召回与压缩规则

- Gateway 从已认证服务/session 凭证注入 `memory_actor`，再把请求转发给 Memory；调用方只提交业务字段和 `source_domains`，不能通过正文或查询参数伪造 actor；Memory Service 继续按固定矩阵验证 actor 与 domain；
- Tier 1、Tier 2、Profile、semantic/lexical index、recall trace 和 feedback 都必须携带 domain；
- Tier 1 -> Tier 2 只能在同一 domain 内压缩，禁止跨域自动聚类；
- `companion` 可以保存用户目标、沟通偏好和已确认关系事实，不保存 API-A 的完整工具输出；
- `evolution` 保存任务、证据、实验和 lineage，不保存实时语音对话；
- Auto 的权威 `mem_governance.jsonl` 与观察投影 `governor_history.jsonl` 都显式携带 `memory_domain=evolution`；旧记录由原子迁移补齐字段，事件数量和 AutonomousChainStore 恢复顺序保持不变；
- Auto 启动时冻结一个最小 evidence packet，运行期间不继续感知用户输入；
- `/auto-q` 后先收口 evolution 任务，再恢复 companion 的周期游标，不能把 Auto 期间积累的内部内容批量注入日常记忆。
- 跨域召回必须命中状态为 `active` 且未过期的提升引用；撤销、过期或源记忆删除后立即停止解引用；
- `POST /promotions` 创建引用，`GET /promotions` 查询审计记录，`POST /promotions/{promotion_id}/revoke` 撤销引用；跨进程调用仍通过 Gateway `/api/mem/*` 转发。

三域隔离已经覆盖 sessions、turns/archive、Tier 2、Profile、tombstone、recall trace/feedback、deletion audit、FTS、semantic index、Tier 1 -> Tier 2 候选批次和跨域提升引用。历史行通过单向迁移归入 `agent_interaction`。提升记录随 Memory SQLite 统一备份和导出，源记忆删除会撤销关联引用；当前不存在任意共享写入桶。

## 六、运行模式与状态转换

产品只定义两个互斥的星子模式，语音开关是日常模式的交互设置，不是第三种人格模式：

| 模式 | 触发条件 | 星子行为 | 用户交互 | 当前状态 |
| --- | --- | --- | --- | --- |
| `daily_companion` 日常模式 | 系统启动或 `/auto-q` 完成收口 | 全天候周期读取 VoidCube 内部事件；目标/行为证据完整且变化时调用 API-B；默认静默；响应文本、单轮语音、持续唤醒和策略门控后的主动播报 | 通过语音与星子沟通；继续通过 CLI 使用 API-A；Web UI 控制声纹、麦克风、会话和提醒策略 | 交互与主动提醒闭环已实现，生产环境仍需校准声纹和延迟 |
| `auto_evolution` Auto 模式 | 用户执行 `/auto` | 停止伴侣辅助、主动提醒、语音会话和伴侣循环；内生驱动使用冻结 evidence packet，并清洗实时用户活动输入 | 用户与星子各自工作；可用 `/auto-q` 中断并返回日常模式 | 模式切换和输入隔离已实现 |

日常模式的周期判断遵循“默认沉默”：

1. 周期只读取 Gateway、API-A 会话摘要、任务状态、Memory 和 trace 等内部事件；
2. 先判断用户当前在做什么及目标是什么；
3. 如果用户意图不清楚，继续观察，不猜测、不提示；
4. 如果没有发现目标偏差、风险或明确可提供的帮助，继续等待；
5. 只有证据足够且打扰收益高于成本时，生成可解释提醒；
6. 用户语音可以随时发起直接对话，不需要等待周期提醒。

模式切换必须是原子状态转换：进入 Auto 前停止日常周期和语音主动输出；退出 Auto 时中断或持久化当前任务、停止 Auto worker，再恢复日常游标和语音服务。两种周期任务不得同时运行。

自主任务的状态主链是：

```text
planned -> approved -> running -> completed/failed
             │           │
             │           ├─ retry/paused/awaiting_review
             └─ awaiting_user_consent（身体切换）
```

`approved` 的实际含义是 API-B 已移交、API-A 可以 claim，并不代表已经执行完成。自主任务必须满足：

- 任务变化先写 GovernanceEventRepository，再发布 AutonomousChainStore 投影；
- API-A 与用户请求分别使用 `supervisor_task` / `user_chat`；
- 真实工具副作用通过 Execution Facade/Adapter 和工具审批；
- 门控关闭时可中断、可解释、可恢复，不静默丢失进度；
- 身体升级必须经过用户明确同意，不能仅凭 API-B 判断激活。

## 七、组件交互流程

### 1. 用户通过 CLI 与 Agent 对话（当前已实现）

```text
用户文本/附件
  -> VoidCube CLI
  -> AIAgent（API-A）
  -> 一次或多次 Chat Completions
  -> ToolExecutionCoordinator（如有工具调用）
  -> CLI 流式渲染
  -> Memory Tier 1 写回
```

### 2. Agent 请求记忆（当前已实现）

```text
AIAgent prefetch / mem_search
  -> mem Provider
  -> Gateway /api/mem/*
  -> Memory Service /recall
  -> Tier 1 + Tier 2 + Profile + archive
  -> 相关性/时间/去重/预算排序
  -> 临时上下文注入 Agent
```

### 3. 星子生成自主任务（当前已实现，默认关闭）

```text
Gateway activity + Memory + body + recent traces
  -> Supervisor observation input
  -> EndogenousDriveEngine
  -> need / intent / signal / reflection / proposal
  -> GovernanceEventRepository
  -> AutonomousChainStore
  -> Gateway supervisor_task
  -> API-A pull/claim/execute
  -> Memory + Supervisor writeback
```

### 4. 身体升级和回滚（当前已实现）

```text
improvement report + Git lineage
  -> candidate slot
  -> probe
  -> Governor review
  -> awaiting_user_consent
  -> Executor activate
  -> watch window
  -> recycle retired slot 或 restore rollback commit
```

### 5. 用户语音提问（单轮或持续监听）

```text
麦克风 -> 音频指纹 -> STT -> Gateway -> Supervisor/API-B
  -> 回复文本 -> TTS -> 扬声器
  -> companion 域 turn pair
```

这条流程同时支持可中断单轮会话和显式启停的持续监听。持续模式按短片段认证并转写，未命中唤醒词的文本不会进入 API-B。主动提醒使用相同的 TTS 播放和中断资源；STT 需要配置 OpenAI-compatible audio transcription endpoint，TTS 默认使用可选 `edge-tts`，采集依赖可选 `sounddevice + numpy`，播放依赖 `ffplay`。

## 八、Web UI 设计要点

### 当前可用的 UI 合同

- `/ui`：Supervisor 内置状态页；
- `/ui/state`：一次性 JSON 状态快照；
- `/ui/events`：SSE/EventSource 增量事件；
- `GET /companion/reminder-policy`：读取当前生效的主动提醒策略和托管状态；
- `POST /companion/reminder-policy`：校验并持久化主动提醒总开关、TTS、冷却和免打扰时段；
- 状态来源包括 scene、activity、autonomous gate、任务、Agent lane、Memory 和 Executor。

当前选择继续使用“`/ui/state` 快照 + `/ui/events` SSE”。VoidCube 是单机、服务端单向推送为主的界面，SSE 已能覆盖状态更新，浏览器会自动重连，快照还能在丢事件后恢复一致状态。语音控制、模式切换和提醒策略等低频上行操作继续使用普通 HTTP POST；只有未来出现高频双向媒体控制时才需要引入 WebSocket。

提醒策略保存到以下 canonical 配置，不覆盖 Provider、Memory 或 Supervisor 的其他字段；环境变量仍拥有更高启动优先级。托管安装通过该接口只读，必须回到包管理器配置修改。

```yaml
supervisor:
  service_runtime:
    companion_proactive_reminder_enabled: true
    companion_proactive_reminder_tts_enabled: true
    companion_proactive_reminder_cooldown_seconds: 900
    companion_proactive_dnd_start: "22:00"
    companion_proactive_dnd_end: "08:00"
```

### 理论 UI 的扩展方向

可以把星子拟人化界面分为四个只读投影：

1. 感知灯：当前 observation、活动来源和数据新鲜度；
2. 记忆柜：Memory recall、压缩和治理事件状态；
3. 任务沙盘：planned/approved/running/awaiting consent；
4. 身体状态：active/candidate/probe/watch/rollback。

语音对话、模式切换和主动提醒按钮必须调用现有 Gateway/Supervisor 路由，不能由前端直接写 SQLite 或直接激活 Body。未来若改为 WebSocket，应保留 `/ui/state` 的可恢复快照作为断线重连基线。

## 十、关键设计约束

### 已由当前代码和测试守住的约束

- Gateway 是跨进程调用 Executor 的唯一标准入口；Supervisor 进程内部通过 `VoidCubeExecutionFacade`。
- `AIAgent -> mem Provider -> Gateway /api/mem/* -> Memory Service -> MemAI` 是统一记忆接入链。
- Agent 不拥有长期身份、治理裁决或跨会话事实真相。
- 任务状态变化必须先追加治理事件；`AutonomousChainStore` 是投影。
- 并行结果按模型原始顺序写回，工具中断必须到达实际 worker。
- 自主链路门控初始为关闭；当前 `/auto` 是临时启用开关，`/auto-q` 是对应的临时停用开关。
- MemAI 固定从仓库共享 `Mem/src` 加载，不随 Body 槽位切换。
- 退役集成在运行代码、可加载技能和 wheel 中保持零入口。

### 已由代码实现、仍需生产校准的约束

- 音频指纹认证、可中断会话和原始音频默认不落盘已实现；端到端延迟和真实用户阈值仍需实机校准；
- 主动提醒具备可解释证据与默认静默门槛；pending 队列、自动 TTS、冷却、免打扰、语音关闭等待和 Gateway 活动审计已实现；
- 感知仅限 VoidCube 内部事件，不读取桌面窗口、其他进程、键盘、原始屏幕或系统监控；
- `agent_interaction`、`companion`、`evolution` 三域记忆、Gateway 凭证、actor 注入、应用层访问矩阵和只读跨域提升引用已实现；生产部署必须配置随机 `GATEWAY_AUTH_TOKEN`，测试环境可显式使用无根令牌的本地模式；
- UI 沿用 SSE + snapshot，控制操作使用 HTTP；主动提醒策略已持久化到 canonical Supervisor 配置，托管模式保持只读；
- 日常模式与 Auto 模式互斥，模式切换需要原子停止/恢复周期 worker；Auto evidence packet 和实时用户活动过滤已实现；
- Auto 自主进化只允许 Body candidate/probe/consent/watch/rollback 治理链，星子不能直接覆盖活动身体。

## 十二、已确认的产品决策

1. 星子由 Supervisor + Memory/MemAI + API-B 承载，不创建第二个独立 Agent 进程。
2. 星子全天候运行，但具有互斥的日常伴侣和 Auto 自主进化模式。
3. 系统启动进入日常模式；`/auto` 进入 Auto，`/auto-q` 收口任务后回到日常模式。
4. 日常模式只感知 VoidCube 内部事件；意图不清或没有目标偏差时保持沉默。
5. 语音是日常模式主入口，也是用户在使用 API-A CLI 工作时与星子沟通的独立通道。
6. Memory 使用单服务、单备份体系，并在现有 scope 上增加三域强隔离。
7. Auto 模式不履行伴侣职责，不持续感知用户行为，只处理冻结证据上的自学习、自计划和进化任务；当前由 Auto evidence packet 和 `autonomous_only` 输入边界实现。
8. UI 继续采用 snapshot + SSE，暂不引入 WebSocket。
9. 自主进化只能经过 Body candidate/probe/consent/watch/rollback 治理链。

## 十三、下一阶段建议

1. 用本机所有者的真实录音建立声纹评估集，校准误拒率/误受率；必要时替换当前轻量派生特征，但保持“只存模板、不存原音、不建立用户账号”的合同。
2. 将当前“分段 STT 检测唤醒词”替换为本地低功耗唤醒检测，减少网络请求、延迟和持续监听成本。
3. 为 `evolution -> companion` 提升引用增加 Web UI 审计视图，让用户查看来源、批准原因、有效期和撤销状态。
4. 将临时 Gateway 根令牌替换为操作系统凭据存储中的生产密钥，并补充轮换与服务重注册流程。
