# 全链条报告：API-B 内生驱动 → API-A 代理执行 → Mem 记忆写入

> 审查范围：监督者(API-B)内生驱动产出 → 任务队列/治理/派发 → API-A 拉取并执行(含子代理) → 执行成果回写 → Mem 双层记忆写入。
> 方法：4 个子代理分段静态审查源码，逐项定位 `文件:行号` 并确认触发条件，未运行系统、未改动代码。
> 结论先行：**链条在三个关键接缝处断裂或会静默丢数据**——成果回写、状态所有权、记忆落地。下面先给最危险的跨段故障链，再分段列问题，最后给修复优先级。
>
> **2026-06 修订（全天候执行语义）**：监督者改为全天候自动执行，时间窗口(原 00:00-06:00)与"等用户空闲"硬门控已移除（详见《voidcube架构基线》§6）。受此影响的条目已就地标注 `[已随全天候改造修订]`：执行窗口跨夜问题(2-4.2)作废；时区 bug(2-4.1)不再影响 gating（用户代理已废、`last_user_request_at` 无活 feeder，该 gate 本就失效），idle 时间改为任务产出时间 不在保留弃用代码。

## 0. 执行摘要

整条链路能在"理想路径"(无并发、无抖动、LLM 健康、不重启)下走通。但一旦引入真实环境的并发、网络抖动、进程重启、LLM 降级，会暴露三类系统性缺陷：

1. **成果不落地**：API-A 执行学习/改造任务后，产出的 findings / 实现摘要**既不回写 supervisor、也不进记忆**——回写 payload 只有成败标志，记忆钩子又不覆盖主回合(段3 H4 + 段4 1.1)。自进化闭环的"成果"环节实际是断的。
2. **所有权/状态脱节**：任务的 owner 判定依赖 gateway 的"全局唯一 active session"，而它是 last-writer-wins，双 CLI 并存或 gateway 抖动时会误判孤儿、误恢复、回写撞上非法状态转换，导致**双执行 + 回写静默丢失**(段2 2.1/2.2/3.1 + 段3 H1/H2/H3)。
3. **假活跃 / 假成功**：`memory_active` 只看"压缩规则跑过"、派发结果"非已知错误即成功"——多个健康/成功信号反映的不是真实状态(段4 6.1 + 段2 6.2)。（注：原列的 idle 时区 bug 2-4.1 已随全天候改造降级，见上方修订说明）

按数量：高severity 14 项、中 20 项、低/观察 9 项。其中**段2(派发交接)与段4(记忆写入)是重灾区**。

## 1. 最危险的跨段故障链（复合风险）

这些是单段问题叠加后放大的真实事故场景，优先级最高。

### 故障链 A：双 CLI + gateway 抖动 → 任务双执行且成果丢失

```text
段2-2.2  gateway _active_cli_session_id = 非idle最后写入者（last-writer-wins）
   │     user_chat CLI 推 scene → 抢走 active，supervisor_task CLI 的 owner≠active
   ▼
段2-3.1  恢复逻辑发现 owner≠active（或 gateway 不可达时 active="") → 误判孤儿
   │     → 任务重置 approved → 被重新拉取
   ▼
段3-H2   原 CLI 其实还在执行/刚完成，回写 completed 撞上已被改写的状态
段2-1.4  approved→completed 非法转换抛 ValueError（500）→ 回写静默失败
   ▼
结果：同一任务两个 CLI 执行；先完成者的成果回写丢失；最终可能被记 failed
```

**触发**：常态——只要"用户在用主 CLI" + "AUTO 在跑监督者任务" + 任一次 gateway 5xx/超时。
**根因**：active-session 与 task-owner 耦合(段2-2.2)、恢复在不确定时采取激进策略而非保守跳过(段2-3.1)。

### 故障链 B：执行成功 → 成果蒸发

```text
段3-H4   AUTO 任务由主 agent 经 _pending_input 直接执行，不走 delegate_task
   │     → delegate_tool 的记忆钩子(on_delegation)不触发
   ▼
段3-H4   回写 supervisor 的 payload 只含 decision/reason/context，不含 final_response
   ▼
段4-1.1  gateway 的 _record_agent_interaction_to_tier1 只在 response_text 非空时写
   │     而该值恒为空 → agent 成果从不进 tier1
   ▼
结果：findings/实现摘要只留在 conversation_history，supervisor 拿不到、记忆里没有
```

**触发**：每一个正常完成的 learning / body_improvement 任务。
**根因**：成果回流路径压根没接上(段3-H4 与段4-1.1 是同一个洞的两端)。

### 故障链 C：看起来在学习，其实空转

```text
段4-1.1  执行成果未进 tier1（见故障链 B）
   ▼
段4-2.2  tier1 溢出路径仍按龄过滤 → 近期 turn 撑爆 max_turns 也不下沉
段4-6.1  memory_active 只看"压缩规则被调用过"，no-op 也刷新 last_run
   ▼
段4-3.1  LLM 健康只在启动检查一次，降级后不回升
   ▼
结果：UI 显示"记忆活跃 ✅"，实际成果没进来、压缩在空跑、LLM 可能早已降级
```

**触发**：LLM 启动时不可用 / 高频写入 / 长时间运行。
**根因**：多个健康信号反映"代码在跑"而非"数据真的写成功了"。

### 故障链 D：CLI 崩溃 → 任务永久悬挂

```text
段3-H3   崩溃重启后恢复只"认领"owner，不重新注入 prompt → 任务不再执行
段3-M1   30 分钟超时在真正长回合/卡死时不触发（poll 被 _agent_running 挡住）
段2-4.3  agent_pull 任务 metadata 写的是 execution_started_at，兜底查 executed_at → 兜底跳过
段2-3.2  恢复只比对 session 相等，不消费 gateway 已算出的 lease stale 标志
   ▼
结果：owner CLI 死了但 session 未过 1h TTL 时，任务卡死 running，无人清理
```

**触发**：CLI 静默退出/断网/卡死。
**根因**：三套兜底机制(30min 超时、孤儿恢复、lease stale)各有盲区且互不补位。

## 3. 修复优先级建议

按"影响面 × 修复成本"排序。前 4 项是杠杆最高的——小改动、堵大洞。

### P0（先修，多为小改动堵大洞）

1. **2-4.1 时区统一**（一行，已降级）：`datetime.now()` → `datetime.utcnow()`（或统一 aware UTC）。`[全天候改造后]` 这不再是 gating 致命 bug（用户 idle 已不 gating），但仍影响 idle 时间展示与 `last_agent_work_at` 派生判定的精度，仍建议修。
2. **段3-H4 + 段4-1.1 成果回流断裂**（接通一条链）：回写 payload 带上 `final_response`(截断)，并在 AUTO 完成分支显式写记忆。这是自进化闭环"成果"环节缺失的根因，不修则整套学习/改造产出蒸发。
3. **2-3.1 恢复在不确定时保守化**：`_fetch_gateway_active_cli_executor` 失败时**跳过恢复**，而非把 active 当空。一行判断之差，杜绝"gateway 抖动→全量误恢复→双执行"。
4. **4-6.1 + 4-3.1 健康信号说真话**：`memory_active` 基于"最近周期实际写入条数>0 且 llm_healthy"；LLM 健康改周期复检。否则所有人(含 UI、内生驱动)被"假活跃"误导。

### P1（所有权与状态机解耦）

5. **2-2.1 / 2-2.2 active-session 与 task-owner 解耦**：恢复判定基于 owner session 自身的 lease 存活，不依赖"全局唯一 active session"。
6. **2-1.1 cycle 加 asyncio 锁** + **2-1.4 回写前锁内校验当前态**，非法转换返回明确冲突码而非 500，让 CLI 据此放弃。
7. **段3-H1 / H2 / H3 回写可靠性**：快速退出复用 force-quit 的回写+清理；回写成功后才清本地状态、失败带退避重试；恢复时重放 prompt 或主动回写 failed。
8. **2-6.1 governor 重通知**：health-check 重注册时一并重推 governor 模式。

### P2（记忆写入的事务性与幂等）

9. **4-5.1 确定性 ID**：Event/Scene/Arc ID 用内容/source_turns 哈希派生，使重复压缩成为幂等 upsert（同时缓解 4-2.1/4-4.2）。
10. **4-2.1 压缩写库单事务** + **4-2.2 溢出路径放宽按龄过滤**（改 FIFO/relevance 强制压缩最旧批）。
11. **4-3.2 降级模式不丢数据**：产不出 Event 的 turn 不标记已压缩，或强制保留原文。
12. **4-1.2 / 段3-M4 停止静默吞异常**：关键写入失败至少 warn+计数，回写失败不清空任务状态。

### P3（一致性与可维护性，非正确性）

13. 段1 的 judged/outcome 作用域对齐(1-H2)、只读评估副作用收敛(1-H1)、observation 允许集两层统一(1-M2)。

## 4. 一句话结论

链路的"控制流"基本成立，但"数据流"在三处接缝漏：**成果回不来、所有权对不齐、健康信号不可信**。其中性价比最高的是 P0 的几项——一条成果回流链 + 一处保守恢复 + 两个健康信号修正（+ 已降级的时区统一），能消掉本报告里大半高危故障链。建议先做 P0 并各自补回归测试，再按 P1→P2 推进；P3 与既有的内生驱动收敛工作合并节奏。
