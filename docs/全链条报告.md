# 全链条报告：自主链路与用户链路边界审查

更新日期：2026-07-04

> 本报告按本轮最新语义重新生成，不沿用已删除的历史全链条报告或历史问题清单作为判断来源。

## 1. 审查基准

本报告按最新《voidcube架构基线》审查全执行链路。当前最高优先级语义如下：

- **自主链路**：API-B 内生驱动自主感知、判断并生成治理投影 / 任务；Web 监控展示 API-B 的状态、反馈、任务治理和自主任务回报；API-A 自主执行面（当前表现为由 `/auto` 临时门控的最小迷你 CLI / 子代理通道）拉取并执行 `self_learning` 与 `body_improvement`；成果写入 Mem；下一轮 API-B 内生驱动读取、管理和再判断。
- **用户链路**：用户使用主 CLI 调用 API-A 主 Agent 运行，走 `user_chat` 泳道，服务用户当前请求。
- **硬边界**：自主链路和用户链路必须互不抢占、互不覆盖、互不解释成同一个 CLI 模式。`/auto` 与 `/auto-q` 只是当前自主链路的临时启停开关，不是主 CLI 的用户交互模式。Web 监控只监控展示 API-B 的动作、状态、反馈、任务治理和自主任务回报，不成为用户聊天入口。

## 2. 结论

设计方向基本符合要求，但此前文档存在三个语义偏差：

1. **链路命名不够硬**：已有 `user_chat / supervisor_task` 双泳道和 `/auto` 临时门控说明，但没有把“自主链路 / 用户链路”作为一等架构边界，容易让后续实现把 `/auto` 开关继续理解成主 CLI 的一种模式。
2. **执行面表述偏粗**：多处写成“活跃 Agent 执行学习任务”，容易误解为用户主 CLI / 主 Agent 被后台任务复用。最新语义应写成 API-A 自主执行面执行，由最小迷你 CLI / 子代理通道承载，并与用户主 CLI 隔离。
3. **Web 监控边界偏宽**：旧表述说 Web UI 是“所有任务统一可观测窗口”，容易扩张成监控用户链路或聊天内容。最新语义应限定为 API-B 观测面，只展示 API-B 动作状态与自主任务回报。

## 3. 对最新语义的链路对齐

### 3.1 自主链路

```text
API-B / Supervisor 内生驱动
  → 自主感知用户、系统、记忆、身体、治理状态
  → 形成 judgement / need / intent / governance output
  → 将适合 API-A 执行的创造类投影放入任务列表
  → API-A 自主执行面（最小迷你 CLI / 子代理通道）pull 任务
  → 执行 self_learning / body_improvement
  → 将学习成果、替身改进报告、任务 outcome 写入 Mem
  → 下一轮 API-B 读取 Mem 与任务历史继续判断
```

符合点：

- 任务生产者归 API-B / Supervisor。
- 任务执行者归 API-A 自主执行面，不归 API-B。
- 成果闭环归 Mem，再被 API-B 读取。
- Web 监控只展示 API-B 侧状态和自主任务回报。

### 3.2 用户链路

```text
用户
  → 主 CLI
  → API-A 主 Agent (`user_chat`)
  → 工具 / 临时上下文 / 必要记忆访问
  → 主 CLI 输出
```

符合点：

- 用户链路不依赖自主链路治理存储。
- 用户主 CLI 不承担自主任务执行槽。
- `/auto` 开关不得影响主 CLI 输入或主 Agent 交互。

## 5. 当前对齐后的架构判断

按最新语义，VoidCube 的全执行链路应被理解为“双链路共享底座”：

- 用户链路保证用户当前交互稳定、直接、优先。
- 自主链路负责 API-B 内生判断、API-A 自主学习/改进、Mem 闭环和 Web 可观测。
- 两者共享 API-A 能力域和 Mem，但必须通过 `user_chat / supervisor_task`、主 CLI / 最小迷你 CLI、用户输出 / API-B Web 观测这三层边界隔离。

因此，当前设计在目标方向上是成立的；主要问题不是缺组件，而是旧文档和部分命名仍可能把“自主链路”误读成“主 CLI 的另一种运行模式”。本轮已经把这层语义写入基线，后续应优先清理代码和 UI 文案中的旧叫法，避免兼容逻辑再次长成主逻辑。
