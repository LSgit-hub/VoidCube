# VoidCube 开发与验证

更新日期：2026-07-20

## 环境准备

项目要求 Python 3.11 或更高版本。开发依赖和版本范围以 `pyproject.toml` 为唯一来源：

```bash
python -m venv .venv
python -m pip install --upgrade pip
python -m pip install -e ".[all,dev]"
python -m pip check
```

发行版本只在 `VoidCube_cli.__version__` 定义；`pyproject.toml` 通过 setuptools
动态元数据读取该属性。修改版本时不得在 CLI、横幅、locale 或文档中再写第二份版本常量。

如果已有虚拟环境缺少 `build` / `pytest-asyncio`、pytest 版本超出 `pyproject.toml` 的范围，或无法执行下列命令，应先重新同步开发依赖。当前开发 extra 支持 pytest 8.x 与 9.x。不要通过修改测试命令掩盖环境漂移。

准备合并依赖、打包或安装入口改动时，运行全新环境验收：

```bash
python scripts/verify_clean_install.py
```

脚本会在系统临时目录创建虚拟环境，安装 `.[all,dev]`，设置独立的
`VOIDCUBE_HOME`，禁用用户 site 与 `PYTHONPATH`，随后执行 `pip check` 和 smoke。
该检查需要网络解析依赖；无论成功或失败，默认都会清理临时环境和根目录 setuptools 产物。

## 运行态诊断

在源码仓运行完整配置与运行态诊断：

```bash
python voidcube.py doctor
```

安装发行包后也可使用 `VoidCube doctor`。其中 `body_registry` 为 `INFO` 表示槽位尚未初始化或 registry、slot meta、物化清单和 active pointer 结构健康；为 `ERROR` 表示结构已初始化但存在损坏或角色不一致，需要先修复对应 violation，再启动身体升级或切换流程。doctor 只读取并报告状态，不会自动改写槽位。

Supervisor 默认在同一进程内挂载 Execution Service 的 `/executor/*` 路由，并以 `executor` 类型向 Gateway 注册；不会额外启动 Executor daemon。其 `/executor/health` 与 Supervisor 根 health 使用相同的身体完整性报告。`status=degraded` 仍返回 HTTP 200，表示服务进程可达但 `body_runtime.violations` 存在结构问题；运维检查不能只看状态码，也不能因为 degraded 自动重启进程。

真实进程链路可通过以下命令验收：

```bash
python voidcube.py serve start
python voidcube.py body status
python voidcube.py serve stop
```

`body` 命令默认读取 `systems.config` 的 Gateway host/port（默认 `127.0.0.1:6000`），不维护第二份端口。需要临时连接其他 Gateway 时，选项必须放在子命令前，例如 `python voidcube.py body --gateway-url http://127.0.0.1:6123 status`。

## 测试层级

### Smoke

日常修改的第一层反馈，覆盖统一启动器、发行包契约、Phase 1 自主闭环、
本地附件解析、Agent 消息清洗、worktree 提交成果检测和工具注册分发：

```bash
python -m pytest -m smoke -q
```

Smoke 通过只说明关键骨架未发生明显回归，不代替受影响模块测试。

### 受影响模块

按修改边界运行对应文件或目录，例如：

```bash
python -m pytest tests/test_gateway_activity.py -q
python -m pytest tests/test_supervisor_runtime_wiring.py -q
python -m pytest Mem/tests -q
```

新增测试应使用 `pytest.ini` 已声明的标记。只有稳定、无外部凭据、无网络依赖且能提供关键骨架反馈的测试才应加入 `smoke`。

### 全量回归

合并核心链路修改或准备发布时运行：

```bash
python -m pytest -q
python -m pytest Mem/tests -q
```

涉及 Gateway、Supervisor 或 Executor 注册/转发时，再运行隔离进程链路测试：

```bash
python -m pytest tests/test_live_executor_chain.py -q
```

该测试在临时 Git repo 和临时端口启动真实 Uvicorn 服务，损坏临时 active manifest 后验证 `/api/executor/health` 与 `/api/executor/body/registry` 的 `degraded` 传播，结束时自动停止服务并删除临时数据。

主仓测试集规模较大，不应以较短命令超时当作测试失败；CI 或本地执行器需要给出足够时间并保留最终摘要。

## 构建验收

```bash
python scripts/build_wheel.py
```

这是仓库唯一的正式 wheel 构建入口。脚本只清理根目录下的 `build/` 与当前发行包
egg-info，防止 setuptools 从旧 `build/lib` 把已经删除的模块重新带入发行包；构建后会双向核对
wheel 中的 Python 模块、Mem 提示资源和 CLI locale JSON 与当前源码，出现无源码文件或漏打包文件都会失败。

构建后应在临时虚拟环境安装 wheel，并至少验证：

```bash
voidcube --version
python -c "import agent, tools, systems, VoidCube_cli, VoidCube_core, memai"
```

`tests/test_packaging_contract.py` 校验打包声明、清理边界和源码到 wheel 的一致性算法，
但不能代替实际执行构建脚本与安装 wheel。

## 提交前检查

```bash
git status --short
python -m pytest -m smoke -q
python -m pytest <受影响测试> -q
```

涉及架构边界、持久化协议、身体治理或自主链路时，还需要确认：

- 代码仍符合 `docs/voidcube架构基线.md`
- 当前行为已同步到对应文档和 `docs/全链路问题清单.md`
- 被替代的旧分支、别名、提示和测试已删除，或兼容期限与删除条件已明确记录
