# State Boundary

## 1. 文档定位

本文档定义 VoidCube 的状态归属边界。

总架构以 [voidcube架构基线.md](./voidcube架构基线.md) 为准。本文只回答：

- 哪些状态必须由 Mem 作为权威来源
- 哪些状态由网关维护为运行时操作状态
- 哪些状态可以只存在于 body runtime
- 哪些状态可以临时生成但必须回写
- 身体切换时哪些状态应继承、哪些不应继承

核心原则：

**凡是影响身份连续性、长期记忆、治理裁决、演化解释或回滚决策的状态，都不能只保存在 body runtime 或 Agent 本地。**

## 2. 状态分类

VoidCube 状态分为四类：

- Mem 权威状态
- 网关操作状态
- Body runtime 缓存状态
- 临时生成但必须回写状态

其中最重要的区分是：

- Agent 内部记忆属于 body runtime / 工作层
- Mem 长期记忆属于长期权威层

Agent 内部记忆可以帮助当前任务执行，但不能替代 Mem 成为身份、治理和长期解释的来源。

## 3. Mem 权威状态

以下状态必须由 Mem 或受控长期存储作为权威来源。

### 3.1 身份连续性状态

- 个体身份描述
- 长期目标
- 宪法与原则
- 自我约束
- 长期用户偏好
- 历史经验总结

### 3.2 长期记忆状态

- 用户长期信息
- 历史任务经验
- 压缩后的长期记忆对象
- 跨会话关键上下文
- Agent 产出的学习结论
- 需要进入长期治理判断的事实材料

### 3.3 演化与治理状态

- body 谱系
- body 版本历史
- 候选体差异摘要
- probe report 摘要
- 切换审批记录
- 回滚记录
- watch-window 结论
- 执行器执行结果
- 失败升级记录

### 3.4 状态转换审计

- body state 变化事件
- probe lease 发放事件
- active lease 转移事件
- 监督者裁决事件
- active body pointer 变更历史
- gateway activation 变更历史

这些状态可以在执行过程中由执行器、网关、Agent 或监督者生成，但权威归档位置必须是 Mem 或明确的长期存储。

## 4. 网关操作状态

以下状态适合由网关维护为运行时操作状态：

- 当前 active body 路由目标
- 当前 active body activation
- 服务注册表
- 服务健康状态
- 当前流量 draining 状态
- 在途请求数
- 临时切流锁
- 最近用户请求时间
- 最近 Agent 工作时间
- 最近记忆任务时间
- 最近自提升活动时间

网关操作状态的原则：

- 网关负责实时协调
- Mem 负责历史解释
- 影响治理判断的网关状态必须可被记录或重建

例如，当前路由目标可以由网关实时维护，但 active body pointer 变更历史和切换原因必须写回 Mem。

## 5. Body Runtime 缓存状态

以下状态可以只存在于 body runtime 或 Agent 本地缓存中：

- 进程内消息上下文
- Agent 内部临时记忆条目
- Agent 内部上下文压缩结果
- 当前轮工具调度状态
- 工具执行临时结果
- 请求级工作目录
- 临时文件
- 中间产物缓存
- 短期日志缓存
- 运行时连接句柄
- 当前槽位 runtime 下的 `sessions/`
- 当前槽位 runtime 下的 `cache/`
- 当前槽位 runtime 下的 `state/` 临时快照
- 当前槽位 `logs/` 中的普通诊断记录

这些状态可以丢失，可以重建，不构成身份死亡，也不应成为唯一长期真相。

## 6. 禁止 Body 独占的状态

以下状态不得只存在于 body runtime、Agent 内部记忆或本地文件中：

- 唯一长期记忆副本
- 唯一身份定义
- 唯一长期目标
- 唯一治理裁决依据
- 唯一演化历史
- 唯一切换记录
- 唯一回滚说明
- 唯一 probe 结果
- 唯一用户长期偏好

判断标准：

**如果某状态丢失会导致新 body 不知道自己是谁、为什么切换、如何回滚或如何解释历史，它就不能只属于 body。**

## 7. 临时生成但必须回写的状态

以下状态可以先由 Agent、执行器、监督者或网关生成，但必须回写 Mem：

- 升级提案
- 补丁说明
- 候选体差异摘要
- 构建来源说明
- 健康检查报告
- 关键任务回放结果
- 运行中发现的问题
- watch-window 观察结论
- 自动回滚触发原因
- 执行器动作结果
- 需要长期保留的用户事实
- 需要长期保留的技术经验

这类状态的规则是：

**生成于运行层，归档于 Mem。**

## 8. 切换时的状态处理

### 8.1 应持续继承的状态

身体切换后仍应持续有效：

- 身份定义
- 长期记忆
- 治理历史
- 当前有效原则
- 长期用户偏好
- body 谱系与版本历史
- 最近关键演化结论

这些状态由 Mem 提供连续性，不依赖旧进程存活。

### 8.2 不应直接继承的状态

身体切换时不应直接继承：

- 旧进程内上下文
- 旧工具临时缓存
- 旧请求级工作目录
- 旧 runtime 下未归档的 session/cache/state
- 旧连接句柄
- 未经整理的临时日志片段

这些状态最多用于诊断，不应直接成为新 active 的长期真相。

### 8.3 可选择性重放的状态

以下状态可按策略选择性重放：

- 最近任务摘要
- 最近用户会话摘要
- 健康检查基准样本
- 关键失败案例
- 受控回放任务

选择性重放必须明确标记来源，避免把测试或诊断上下文误写成长期身份事实。

## 9. 同步原则

### 9.1 写入原则

- body runtime 可以先保存短期工作态
- Agent 内部记忆可以先做任务内整理
- 一旦信息影响长期身份、跨会话延续、治理裁决或回滚判断，就必须写回 Mem

### 9.2 读取原则

- body 可以读取 Mem 下发的长期身份与记忆
- body 不得擅自覆盖 Mem 权威状态
- 需要变更长期状态时，应通过受控写入接口和治理记录

### 9.3 冲突原则

- Mem 权威状态优先于 body 本地缓存
- 网关操作状态优先于 body 自我判断的流量归属
- body registry / active body pointer 优先于单个 Agent 的自我声明

## 10. 实现检查清单

实现或审查某个功能时，可以用下面的问题判断状态归属是否正确：

- 这个状态丢了，是否影响身份连续性？
- 这个状态丢了，是否影响回滚？
- 这个状态是否会被监督者用于裁决？
- 这个状态是否需要跨会话存在？
- 这个状态是否只属于当前请求或当前进程？
- 这个状态是否能由 Mem、registry、gateway 或日志重建？

如果答案指向长期身份、治理、切换或回滚，该状态应写入 Mem 或受控长期存储。

如果答案只指向当前任务、当前请求或当前进程，它可以保留在 body runtime。

## 11. 设计结论

VoidCube 的状态体系不应是“所有东西都永久保存”，而应是分层保存：

- Mem 保存必须延续、必须解释、必须审计的状态
- 网关保存必须实时协调的操作状态
- body runtime 保存可以丢失、可以重建的短期工作状态
- 执行器和 Agent 生成的关键事实必须回写 Mem

只有这样，身体轮换才是低风险操作：body 可以替换，长期身份不丢；runtime 可以清理，治理历史不丢；Agent 可以升级，用户与系统的长期连续性不丢。
