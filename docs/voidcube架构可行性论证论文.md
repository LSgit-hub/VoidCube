# VoidCube 母体式双子 Agent 架构的可行性论证

## 摘要

本文基于 `voidcube架构基线.md`、`switch-protocol.md`、`project-architecture-analysis.md`、`phase-1-experiment-roadmap.md`、`body-runtime-runbook.md` 等文档，对 VoidCube 当前目标架构进行归纳与可行性论证。

本文的核心结论是：VoidCube 的目标架构在工程上是可行的，但它的可行性不来自“让一个 Agent 直接无限自改”，而来自一组更保守、更可验证的系统设计：单机多进程、网关中心化、长期记忆与治理收口、监督者只判断、执行器只执行、双子 Agent 槽位隔离、probe 验证、观察窗口与回滚。

换句话说，VoidCube 可以被理解为一个母体系统。它不把自己整体暴露给用户，也不直接热改当前正在服务用户的 Agent，而是在两个子 Agent 槽位之间交替培养、验证、切换与回收。用户最终接触到的始终只是当前活跃子 Agent；母体内部则负责记忆、治理、验证、切换和长期演化。

## 关键词

VoidCube；母体系统；双子 Agent；长期记忆；监督治理；执行器；蓝绿切换；自学习；自进化；单机多进程

## 1. 问题定义

VoidCube 要解决的问题不是普通 CLI 工具如何多开服务，也不是简单把一个 Agent 包装成常驻进程。它真正试图解决的是：

- 如何让 Agent 能持续变好
- 如何避免正在服务用户的 Agent 被直接热改而失效
- 如何让长期记忆不随执行体切换而丢失
- 如何让自学习结论进入治理链路，而不是直接变成危险执行
- 如何在候选 Agent 出问题时回滚
- 如何让用户服务优先于内部自提升

因此，VoidCube 的系统目标可以概括为：

**建立一个以长期记忆和治理为核心、以双子 Agent 槽位为升级对象、以网关和执行器为运行骨架的单机多进程母体系统。**

这个目标把“智能体自我升级”从一个不可控的抽象愿望，拆成了若干可验证的工程环节：

- 记忆是否连续
- 候选体是否隔离
- probe 是否通过
- 切换是否可控
- 回滚是否存在
- 执行是否受监督裁决约束

## 2. 架构命题

VoidCube 当前基线可以归纳为 7 个主要命题。

### 2.1 VoidCube 是母体，双身体是子 Agent

VoidCube 不应被理解为“CLI + 若干服务”的简单组合，而应被理解为一个母体系统。

在这个母体中：

- `slot-A` 和 `slot-B` 是两个子 Agent 槽位
- 当前 `active` 槽位服务用户
- 当前 `shell` 槽位用于候选改造
- 候选槽位进入 `probe` 后接受验证
- 验证通过后才可能成为新的 `active`
- 旧 `active` 进入 `retired`，用于观察窗口内回滚

这个设计的关键意义是：系统不直接修改正在服务用户的子 Agent，而是在另一具子 Agent 槽位中构造新候选体。

### 2.2 CLI 是用户入口，网关是内部神经中枢

用户视角下，CLI 是启动入口、人机交互入口和手动管理入口。

系统视角下，网关是内部核心能力的通信中枢，承担：

- 服务注册
- 活跃 Agent 路由
- 流量切换
- 活动事实记录
- 内部鉴权与追踪
- 用户任务与自提升任务区分

因此，CLI 和网关不是两种运行模式，而是两个不同层面的入口：

- CLI 面向用户
- 网关面向内部组件

这一区分消除了“本地模式 / 服务模式 / 双模式”的旧理解，也使后续服务化改造有统一方向。

### 2.3 Mem 是长期记忆与治理灵魂

Agent 可以拥有临时记忆、上下文压缩和短期会话整理，但这些都不等于长期记忆。

VoidCube 的长期连续性应由 Mem 承担：

- 长期记忆存储
- 记忆压缩
- 记忆总结
- 关联发现
- 演化记录
- 治理历史
- 监督裁决上下文

在基线中，记忆管理者与监督者不是完全分裂的两个系统，而是 Mem / API-B 能力链在不同时间窗口和权限上下文下的两种身份。

这使架构具备一个重要性质：

**身体可以替换，但灵魂不随身体迁移。**

### 2.4 监督者只判断，执行器只执行

这是 VoidCube 可控性的核心。

监督者负责：

- 规划任务
- 判断是否放行
- 判断是否推迟
- 判断是否取消
- 判断是否暂停
- 判断是否回滚

执行器负责：

- 准备槽位
- 标记 candidate
- 执行 probe
- 启停 Agent
- 切换 active 指针
- 回收 retired
- 执行回滚

这个边界的意义在于：模型可以参与判断，但实际动作必须落入确定性执行器。这样可以避免“模型既裁决又执行”带来的不可审计风险。

### 2.5 自学系统只生产证据，不直接上线

自学系统使用 API-A，负责：

- 技术采集
- 实验设计
- 验证执行
- 结论生成
- 建议提交

但它不直接：

- 修改 active Agent
- 发起切换
- 触发发布
- 绕过监督裁决

这让自学习成为治理输入，而不是执行权本身。

### 2.6 Agent 是主要升级对象

VoidCube 的核心升级对象不是 CLI、网关、执行器或记忆服务本身，而是子 Agent。

CLI、网关、Mem、执行器和自学系统都是支撑系统。它们共同服务的目标是：

**持续产出更好的 Agent，并稳定切换给用户使用。**

这让项目目标更收敛：先把 Agent 的可替换、可验证、可回滚做实，再谈更复杂的自我演化。

### 2.7 子 Agent 必须具备独立落盘结构

每个子 Agent 槽位应尽量拥有独立的：

- `worktree`
- `runtime`
- `logs`
- `meta`

这不是实现细节，而是治理前提。

如果候选体没有独立运行痕迹，就无法可靠验证它；如果旧体没有保留，就无法可靠回滚；如果 runtime/logs/meta 混在一起，就无法判断问题属于哪个子 Agent。

## 3. 可行性论证

### 3.1 该架构符合工程上的渐进实现原则

VoidCube 没有要求一次性实现完全自动的自进化生命体，而是先定义 Phase 1 最小闭环：

- 双槽位
- 候选体
- probe
- 切换
- 观察窗口
- 回滚

这个闭环是可以小步交付的。每一步都有明确状态、输入、输出和验收标准。

因此，架构不是只能停留在理论层，而是可以按以下顺序逐步落地：

1. 建立槽位注册表
2. 建立 `worktree/runtime/logs/meta` 隔离
3. 建立生命周期状态机
4. 建立治理请求与响应 schema
5. 建立 probe 检查
6. 建立 active 指针与网关切流
7. 建立观察窗口与回滚

这符合复杂系统先做最小安全闭环、再增强自动化程度的工程规律。

### 3.2 该架构降低了自我修改风险

直接让当前服务用户的 Agent 修改自己，是高风险设计。失败时可能出现：

- 当前服务中断
- 状态污染
- 记忆污染
- 无法回滚
- 无法判断失败原因

VoidCube 的双子 Agent 槽位把风险隔离到候选体：

- active 子 Agent 持续服务用户
- shell 子 Agent 被改造成 candidate
- candidate 只在 probe 阶段受控测试
- probe 通过后才可能切换
- 旧 active 保留为 retired

这相当于把“热自改”改造成“候选体构造 + 审查 + 受控切换”。这比直接自改更保守，也更符合高可靠系统的升级方式。

### 3.3 该架构保留身份连续性

Agent 作为执行体是可替换的。如果长期记忆绑定在某个 Agent 进程或某个运行目录里，那么切换身体就会破坏身份连续性。

VoidCube 把长期记忆和治理历史收口到 Mem，意味着：

- 子 Agent 可以替换
- 长期记忆不替换
- 治理历史不丢失
- 自学习结论不随进程消失
- 回滚记录可被后续使用

因此，VoidCube 的“连续性”不依赖某个永不停止的进程，而依赖长期记忆、治理历史和 active 指针共同维持。

这比“复制一个运行中的我”更可行。

### 3.4 该架构具备清晰的安全边界

架构中至少有 4 条关键安全边界：

- 用户入口边界：CLI 面向用户，内部服务不直接成为日常用户入口
- 记忆边界：Agent 临时记忆不等于 Mem 长期记忆
- 治理边界：监督者判断，执行器执行
- 身体边界：每个子 Agent 槽位独立管理

这些边界使系统的故障定位更清晰：

- 用户交互问题看 CLI
- 路由与活动事实问题看网关
- 长期记忆与治理历史问题看 Mem
- 状态迁移问题看执行器
- 候选体质量问题看 probe 和槽位日志

边界清晰是复杂系统可维护的前提。

### 3.5 该架构与现有实现已有对应关系

当前仓库并非从零开始。已有实现已经覆盖了可行性证明所需的关键骨架：

- `systems/gateway/internal_gateway.py`
  - 已具备服务注册、路由、活动事实和 body activation 的基础
- `systems/body_registry.py`
  - 已具备双槽位注册表、槽位元数据、active 指针和独立路径
- `systems/lifecycle.py`
  - 已具备治理批准后的生命周期状态迁移能力
- `systems/probe.py`
  - 已具备结构化 probe report
- `systems/governor.py`
  - 已具备确定性治理裁决语义
- `systems/execution/adapters.py`
  - 已开始承接执行器职责
- `plugins/memory/mem/governor_bridge.py`
  - 已能记录治理 review 和 execution outcome
- `systems/self_learning/service.py`
  - 已具备自学结论与建议提交的初级协议

这说明当前架构不是纯概念，而是已经具备第一阶段实验闭环的主要构件。

### 3.6 单机多进程是合理的第一阶段边界

VoidCube 当前不追求多主机分布式、一致性协议、容器编排或复杂多租户。这是合理选择。

原因是：当前最重要的问题不是水平扩展，而是职责收口与闭环验证。

单机多进程已经足以验证：

- CLI 是否只作为用户入口
- 网关是否能成为内部路由中枢
- Mem 是否能承载长期记忆和治理历史
- 执行器是否能消费裁决
- 双槽位是否能切换与回滚

只有当单机闭环稳定后，再考虑分布式扩展才有意义。

## 4. 现有实现对架构的支撑

根据当前文档与代码，VoidCube 已经具备以下可运行基础。

### 4.1 双槽位身体注册表

`BodyRegistry` 与 `BodySlotMeta` 已经能够表达：

- `active_slot`
- `shell_slot`
- `retired_slot`
- `watch_window`
- 槽位状态
- 槽位版本
- `worktree_path`
- `runtime_path`
- `logs_path`
- 最近 probe 结果

这为“两个子 Agent 独立管理”提供了落盘基础。

### 4.2 生命周期状态机

当前状态机采用：

- `shell`
- `candidate`
- `probe`
- `active`
- `retired`

并限制非法跳转，例如不允许从 `candidate` 直接变成 `active`。

这个状态机是可行性的关键，因为它把升级过程从自由流程变成可检查协议。

### 4.3 probe 与观察窗口

probe 阶段用于候选体受控验证，不接真实用户流量。

观察窗口用于新体切换后的稳定性确认。窗口内旧体不立即销毁，从而保留回滚能力。

这两个机制共同构成安全缓冲：

- 切换前有 probe
- 切换后有 watch-window
- 失败时可回滚

### 4.4 Mem 治理记录

`MemGovernorBridge` 会记录：

- review 请求
- slot meta
- governor response
- execution outcome
- registry 快照

这意味着治理不是一次性口头判断，而是可审计历史。

### 4.5 执行器适配层

`systems/execution/adapters.py` 已经开始把原本集中在 supervisor 中的动作抽离成执行边界，包括：

- Agent lifecycle
- Body lifecycle
- Body upgrade
- Legacy upgrade
- Memory maintenance

虽然仍有过渡痕迹，但方向已经与基线一致。

## 5. 主要风险与反驳

### 5.1 风险一：监督者仍可能越权

当前冲突审计指出，`supervisor` 中仍保留部分执行职责。这是现实风险。

但这不是架构不可行，而是过渡实现尚未完全退干净。已有执行器适配层说明迁移方向明确，后续只需要继续把直接执行职责剥离到 executor。

判断标准应是：

- supervisor / governor 只输出裁决
- executor 消费裁决并执行动作
- 执行结果回写 Mem

### 5.2 风险二：网关活动分类还不够细

如果网关不能区分用户请求、记忆维护、自提升规划、自提升执行，就无法可靠判断系统是否空闲。

这会影响 00:00-06:00 执行窗口与 10 分钟空闲规则。

解决方式是继续细化活动时间线，至少维护：

- `last_user_request_at`
- `last_agent_work_at`
- `last_memory_task_at`
- `last_self_evolution_activity_at`

该风险是实现补强问题，不推翻架构。

### 5.3 风险三：自学系统尚未完全独立

自学系统如果没有真正成为独立运行单元，就无法稳定产出结构化证据和建议。

但 Phase 1 并不依赖完整自学系统即可证明核心闭环。Phase 1 只需要证明：

- 候选体能构造
- 候选体能 probe
- 治理能裁决
- 执行器能切换
- 失败能回滚

自学系统可以作为 Phase 1 后的增强项继续推进。

### 5.4 风险四：自动进程热切换尚未完全闭环

运行手册指出，当前系统已经能更新注册表与启动目标，但“切换瞬间自动拉起恢复体进程并与网关流量完整联动”仍属于下一阶段集成工作。

这说明当前不是零人工平台，但不影响架构可行性。

因为可行性的最低证明是：

- 切换目标可确定
- 下一个 Agent 可从新 active body 启动
- 旧体可保留
- 回滚路径可表达

完整自动化是下一阶段成熟度问题。

## 6. 可验证性设计

VoidCube 架构的一个优势是可以被实验验证，而不是只能概念讨论。

建议采用 3 个验收场景。

### 6.1 正常升级场景

初始状态：

- `slot-A = active`
- `slot-B = shell`

流程：

1. 准备 `slot-B`
2. 标记为 `candidate`
3. 进入 `probe`
4. probe 通过
5. governor 批准切换
6. `slot-B = active`
7. `slot-A = retired`
8. 观察窗口通过
9. `slot-A = shell`

验证点：

- 不出现双 active
- `.body-active.json` 指向新体
- 旧体保留到观察窗口结束
- 治理历史完整记录

### 6.2 候选失败场景

初始状态：

- `slot-A = active`
- `slot-B = candidate/probe`

流程：

1. probe 失败
2. governor 拒绝
3. `slot-A` 继续服务
4. `slot-B` 回到可修复或 shell 状态
5. 失败原因写入 Mem

验证点：

- active 不受候选失败影响
- 候选失败有结构化报告
- 没有绕过 probe 的晋升

### 6.3 切换后回滚场景

初始状态：

- `slot-B = active`
- `slot-A = retired`

流程：

1. 观察窗口发现新体异常
2. governor 输出 rollback
3. executor 恢复旧体
4. `slot-A = active`
5. `slot-B` 退出正式工作态
6. 回滚记录写入 Mem

验证点：

- 回滚不依赖记忆迁移
- active 指针恢复正确
- 失败新体不继续接正式流量

## 7. 为什么该架构比旧理解更可行

旧理解容易把项目拆成“本地 CLI 模式”和“服务模式”，或者把 `systems/` 看成旁路实验。这会造成几个问题：

- CLI 被误当成主运行架构本身
- 网关无法成为内部事实源
- supervisor 继续兼任执行器
- Mem 被降级成普通记忆后端
- 子 Agent 无法成为正式升级对象

新基线更可行，因为它把系统目标收敛为一条主线：

**用户通过 CLI 使用当前 active Agent；母体通过网关、Mem、执行器、自学系统持续培养和切换子 Agent。**

这条主线使每个模块都有稳定位置：

- CLI 负责用户入口
- 网关负责内部路由
- Mem 负责长期记忆与治理
- 监督者负责判断
- 执行器负责动作
- 自学系统负责证据
- 子 Agent 负责实际工作

系统一旦按这个方向收口，复杂度不是消失了，而是被分配到了可以管理的边界内。

## 8. 结论

VoidCube 架构是可行的。

它的可行性建立在以下事实之上：

- 目标边界已经清晰：母体服务于子 Agent 的持续升级
- 组件职责可以分离：CLI、网关、Mem、监督者、执行器、自学系统、Agent 各有稳定位置
- 风险被隔离：候选体不直接接用户流量，active 不被直接热改
- 长期连续性有承载：Mem 保存长期记忆、治理历史与演化记录
- 执行可审计：监督者只判断，执行器只执行
- 回滚可表达：旧体在观察窗口内保留
- 当前仓库已有实现基础：body registry、lifecycle、probe、governor、execution adapter、Mem governor bridge 都已存在

因此，VoidCube 不应被理解为一套过度幻想化的“Agent 自我复制系统”，而应被理解为一套更稳健的“母体式 Agent 培养与切换系统”。

它真正要证明的第一件事也不是完全自动自进化，而是：

**在灵魂连续、用户优先、治理可审计、失败可回滚的前提下，安全地培养并替换一个子 Agent。**

只要 Phase 1 的双槽位闭环持续跑通，VoidCube 就具备继续向自愈、自学习和自进化推进的现实基础。
