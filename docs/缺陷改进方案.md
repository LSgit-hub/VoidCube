# VoidCube 行动可靠性缺陷改进方案

> 文档状态：已实施并完成阶段验收
> 方案版本：1.0  
> 编制日期：2026-08-12  
> 依据：GPT-5.6 内部可靠性审查报告及当前源码复核  
> 适用范围：工具执行、API-A 自主任务、会话持久化、Supervisor 恢复、后台进程和上下文压缩

## 1. 目标

本方案解决 VoidCube 当前无法稳定回答的三个问题：

1. 一个有副作用的动作究竟有没有被派发和执行。
2. 动作最终是成功、失败、取消、超时，还是结果未知。
3. 进程崩溃、租约失效或服务重启后，应该继续、对账、重试，还是禁止再次执行。

最终应形成以下可靠性闭环：

```text
任务认领与 fencing
        |
        v
动作写前登记 -> 实际派发 -> 结构化结果/证据 -> 状态提交
        |                |                  |
        +------ 崩溃恢复、对账与防重 <------+
```

本方案不是完成日志。除“现状核验”外，所有实施项当前均为待办，后续会话必须按阶段逐项实现和验收。

## 2. 现状核验

| 编号 | 报告结论 | 核验结果 | 当前风险 | 优先级 |
| --- | --- | --- | --- | --- |
| D-01 | 缺少持久化动作账本 | 成立 | 外部动作成功但结果未落盘时，重试可能造成重复副作用 | P0 |
| D-02 | 租约恢复可能双重执行 | 核心成立，但原报告描述过于绝对 | 已有 owner session 校验和迟到结果 reconcile，但没有单调 generation；会出现恢复卡死、身份复用或过期执行者污染状态的风险 | P0 |
| D-03 | 成功、失败和完成语义不统一 | 部分成立 | `ProcessRegistry` 会把非零退出码记为 `completed`；工具事件使用 `completed + is_error` 混合表达。部分 UI 已读取 `is_error`，自主 handoff 也不直接消费工具事件，因此并非所有下游都会误报 | P0 |
| D-04 | 后台行动重启后失忆 | 成立 | session、PID、输出、游标和通知消费状态只在内存中 | P1 |
| D-05 | 会话数据库可能重复并与 JSON 分叉 | 成立 | SQLite 逐条插入，中途失败后游标不前移，重试会重复；JSON 与 SQLite 同时承担事实来源 | P1 |
| D-06 | Supervisor 恢复失败仍可报告健康 | 成立 | 恢复异常只记 debug，健康状态不包含 recovery 结果，自主任务仍可能被认领 | P1 |
| D-07 | 上下文压缩会丢失动作证据 | 成立 | 原始工具结果会被裁剪，摘要失败时只保留静态占位，不能作为可靠行动记录 | P2 |

补充结论：checkpoint 只负责工作区文件回滚，不能替代动作账本；聊天记录和 LLM 摘要也不能作为外部副作用是否发生的权威证据。

## 3. 总体原则

### 3.1 单一事实来源

- 自主任务归属以持久化 lease generation 为准，session ID 只用于标识执行者。
- 外部副作用以 ActionJournal 和结构化 evidence 为准，不以聊天文本为准。
- 会话消息以 SQLite 为权威源，JSON 仅作为导出或兼容镜像。
- 后台进程以持久化 registry 元数据、进程身份和完成标记为准，不根据 PID 单独推断。

### 3.2 先阻止污染，再增强审计

fencing 必须早于通用 ActionJournal 实施。账本能记录旧 owner 做过什么，但单靠账本不能阻止旧 owner 覆盖新 owner 的结果。先建立 generation 校验，才能给后续动作账本提供可信的执行归属。

### 3.3 不把“没有结果”解释为失败

没有收到结果只表示 `unknown`。对不可幂等动作，`unknown` 必须先 reconcile，禁止直接自动重试。

### 3.4 渐进覆盖副作用面

ActionJournal 首期只接入会产生外部副作用的工具和执行适配器。纯读取工具继续使用轻量事件，不要求全部进入动作账本。

### 3.5 不保留长期双语义兼容

迁移可在存储读取边界临时识别旧值，但主逻辑只能使用新契约。每阶段完成后删除失效参数、旧状态分支、旧事件构造器和重复事实来源，避免后续会话把兼容逻辑重新当成主路径。

## 4. 目标契约

### 4.1 统一执行结果

建议在应用层建立唯一的执行结果契约，供同步工具、后台进程和远程执行适配器共同使用：

```text
ExecutionResult
  state: succeeded | failed | cancelled | timed_out | unknown
  exit_code: int | null
  error: StructuredError | null
  evidence: EvidenceRef[]
  retryability: safe | reconcile_first | forbidden | unknown
  started_at: datetime
  finished_at: datetime | null
```

约束：

- 正常退出且退出码为 `0` 才能映射为 `succeeded`。
- 非零退出码统一映射为 `failed`，同时保留原始退出码。
- 用户中断映射为 `cancelled`；超时映射为 `timed_out`。
- 进程、网络或服务崩溃导致无法证明结果时映射为 `unknown`。
- `completed` 可以继续作为自主任务生命周期的历史终态名称，但不得再作为“命令执行成功”的含义。
- 工具事件应有独立的成功、失败、取消、超时和未知终态，不再使用 `completed + is_error` 表达失败。

### 4.2 自主任务租约与 fencing

建议将执行租约设为任务的一等字段，而不是继续散落在 `metadata`：

```text
ExecutionLease
  generation: positive int
  attempt_id: uuid
  owner_session_id: string
  claimed_at: datetime
  heartbeat_at: datetime
  expires_at: datetime
  state: active | reconciling | released | expired
```

规则：

- 每次从可认领状态进入 `running` 时，在存储锁内原子地将 `generation + 1`。
- `attempt_id` 每次认领都重新生成；session ID 即使复用，也不能复用旧 attempt。
- 续租、完成、失败、取消、改进报告提交和证据绑定都必须携带 `(task_id, generation, attempt_id)`。
- 存储层使用 compare-and-set 拒绝旧 generation 或错误 attempt，返回明确的 `409 stale_execution_lease`。
- stale owner 不直接恢复到 `approved`；先进入 `reconciling`，确认动作状态后再决定接管、完成、失败或人工介入。
- 执行适配器派发副作用前再次验证 lease；ActionJournal 条目必须绑定 generation。

### 4.3 ActionJournal

建议使用 SQLite 保存动作、状态转换和证据，首期表结构至少包含：

```text
actions
  action_id, task_id, lease_generation, attempt_id
  tool_name, normalized_arguments, arguments_hash
  idempotency_key, risk_level, target_resource
  state, retryability, prepared_at, dispatched_at, finished_at
  error_code, error_summary, schema_version

action_transitions
  transition_id, action_id, from_state, to_state
  actor, occurred_at, reason, details_hash

action_evidence
  evidence_id, action_id, kind, payload_json
  content_hash, collected_at
```

状态机：

```text
prepared -> dispatched -> succeeded
                      -> failed
                      -> unknown -> reconciling -> succeeded | failed | unknown
prepared -> cancelled
```

规则：

- 派发前先提交 `prepared`，记录规范化参数和目标资源。
- 能使用服务端幂等键时，幂等键必须稳定且落盘后再发请求。
- `dispatched` 表示请求已经越过本地派发边界，不表示外部系统已成功。
- evidence 保存资源 ID、退出码、响应摘要、内容哈希或可验证引用，不保存未经裁剪的敏感凭证。
- `unknown` 动作根据 `retryability` 决定自动重试、先对账或禁止重试。
- ActionJournal 采用追加转换记录；动作当前状态可缓存，但必须能由转换历史核对。

### 4.4 会话消息存储

目标表必须具备稳定顺序和幂等约束：

```text
messages
  id
  message_id UUID UNIQUE
  session_id
  sequence_no
  ...现有消息字段
  UNIQUE(session_id, sequence_no)
```

新增 `append_messages_batch(session_id, messages)`，在同一数据库事务内完成：

1. 插入整批消息。
2. 更新 session 的 message/tool-call 计数。
3. 更新该 session 的持久化 flush 序号。
4. 任一步失败则整批回滚。

JSON 日志改为从已提交的 SQLite 消息导出或刷新镜像。恢复时不再比较两个来源并猜测哪个更新。

### 4.5 Supervisor recovery 状态

```text
RecoveryStatus
  state: pending | healthy | degraded | failed
  started_at, finished_at
  recovery_cursor
  last_successful_event
  error_code, error_summary
```

- 初始化 recovery 状态必须早于恢复调用。
- 恢复异常至少记录 warning/error，不再只写 debug。
- `degraded` 或 `failed` 时禁止自主执行 lane 认领新任务。
- `/health` 返回包含 recovery 的退化状态；`/ready` 在 recovery 未健康时返回非就绪。
- 存活检查和就绪检查分离，避免单纯 HTTP 进程存活被解释为可安全执行。

### 4.6 ProcessRegistry 持久化

持久化内容至少包括 session ID、命令摘要、cwd、task ID、kind、PID、进程创建身份、开始时间、状态、退出码、输出 spool 路径、输出游标、通知和消费状态。

本阶段不得承诺仅凭 PID 就能完整重新附着：

- 本地后台命令应通过稳定的 wrapper 将 stdout/stderr 直接写入有界 spool，并原子写完成标记。
- 重启后同时校验 PID、进程创建时间/可用身份和完成标记，防止 PID 重用误认。
- 无法验证身份或无法恢复控制能力时，标为 `orphaned` 或 `unknown` 并进入 reconcile。
- 远程执行只有在环境适配器提供持久化 resume token 时才能恢复；否则明确标记 `unknown`。
- spool 必须设置单任务上限、总容量上限和清理策略，不能无限增长。

### 4.7 上下文中的动作引用

上下文压缩只负责叙事信息，不承载权威动作证据。压缩前将工具结果映射为结构化引用：

```text
ActionRef
  action_id
  state
  target_summary
  evidence_refs
```

摘要失败时可以丢失叙事细节，但不能删除 ActionRef。需要查看原始结果时，从 ActionJournal 按权限读取并重新注入必要摘要。

## 5. 分阶段实施计划

每个阶段必须单独可合并、可测试、可回滚。禁止同时修改 ActionJournal、租约、消息数据库和进程恢复后再一次性交付。

### 阶段 0：建立回归基线

状态：已完成

工作项：

- 固化当前相关测试清单和关键故障用例。
- 为现有错误行为添加目标测试，但先明确标为待修复，避免继续把非零退出码 `completed` 固化为正确语义。
- 记录当前存储 schema 版本、任务快照格式和会话数据库样本。

验收标准：

- 能重复运行工具事件、进程、会话持久化和自主任务测试。
- 明确每项迁移前后的数据兼容边界。

### 阶段 1：统一执行状态与事件语义

状态：已完成

主要修改范围：

- `tools/process_registry.py`
- `VoidCube_app/tool_events.py`
- `run_agent.py`
- CLI/桌面端工具事件消费者
- 对应单元测试和集成测试

实施要点：

- 先建立 `ExecutionResult` 和唯一的退出码映射函数。
- 本地和远程后台命令共用同一映射，非零退出码写 `failed`。
- ToolEvent 增加明确终态，消费者按 kind/state 渲染，不再靠 `is_error` 二次猜测。
- 逐一核对 delegate、CLI block store 和桌面事件桥；迁移完成后删除旧 `completed(is_error=True)` 分支。
- 不改自主任务 `completed` 历史状态名称，只在边界显式转换。

故障测试：

- 本地退出码 `0`、`1`、`126`。
- 远程退出码 `0` 和非零。
- 启动异常、超时、用户 kill。
- UI/CLI 对失败、取消、超时的展示和持久化一致。

完成门：任何执行路径都不能把非零退出码标记为成功。

### 阶段 2：为 API-A 自主任务增加 generation fencing

状态：已完成

主要修改范围：

- `systems/supervisor/autonomous_chain_store.py`
- `systems/supervisor/autonomous_task_state.py`
- `systems/supervisor/autonomous_task_review_service.py`
- `systems/supervisor/autonomous_task_review_cycle_service.py`
- Gateway/API-A claim、续租和写回契约
- 自主链路并发与恢复测试

实施要点：

- 将 lease 建模为任务一等字段并进行快照 schema 迁移。旧任务首次读取时生成明确的未认领 lease 初值，不伪造正在执行的 generation。
- 新增存储层原子 `claim`、`renew`、`finalize`、`begin_reconcile` 操作，服务层不得通过多次 metadata 更新模拟事务。
- API-A 的每次续租、完成、失败、改进报告提交都必须携带 generation 和 attempt ID。
- orphan/stale 恢复从 `running -> reconciling` 开始；只有 reconcile 决议可以重新开放认领。
- 旧 owner 的迟到写回保留为审计事件，但不得改变任务最终状态。

故障测试：

- owner A 租约过期，owner B 接管后，A 尝试完成、失败、续租和提交报告均被拒绝。
- 相同 session ID 被重建时，旧 attempt 仍被拒绝。
- 两个 claim 并发时只有一个成功，generation 只增加一次。
- 服务在 claim 持久化前后分别崩溃，恢复结果确定。

完成门：不存在不携带有效 fencing 身份就能推进自主任务或提交执行产物的写路径。

### 阶段 3：事务化会话消息并确立 SQLite 权威源

状态：已完成

主要修改范围：

- `VoidCube_core/state.py`
- `agent/session_persistence.py`
- 会话恢复、搜索和 JSON 导出路径
- 数据库迁移与故障注入测试

实施要点：

- 通过版本化迁移创建带 `message_id`、`sequence_no` 和唯一约束的新表；按旧行 ID 顺序回填，同一事务内切换。
- 新增批量写 API，游标、计数和消息插入同事务提交。
- 重复批次重放必须幂等，不产生重复消息或重复计数。
- SQLite 提交成功后再刷新 JSON 镜像；JSON 写失败只影响导出健康，不回滚数据库事实。
- 完成迁移后删除内存 `_last_flushed_db_idx` 作为唯一正确性依据的旧逻辑。

故障测试：

- 批次第 N 条插入时故障，数据库保持整批未写。
- 提交成功但调用方未收到响应，重放同一批次不重复。
- JSON 写失败、进程重启和旧数据库迁移。
- 搜索、恢复和导出的消息顺序完全一致。

完成门：SQLite 中每个 session 的 sequence 连续且唯一，任何中途失败都不会产生部分批次。

### 阶段 4：引入副作用 ActionJournal

状态：已完成

主要修改范围：

- 新增独立的 action journal 领域模块和 repository
- 工具执行协调器及副作用工具注册元数据
- 外部 API、部署、推送、资源创建和受治理文件写入适配器
- reconcile 执行入口和审计查询接口

实施要点：

- 先建立工具副作用分类：`read_only`、`idempotent_write`、`non_idempotent_write`。未声明的工具默认不得按可安全重试处理。
- journal 写入失败时，副作用工具不得派发。
- 优先接入风险最高且具有稳定资源查询接口的动作，不要求纯读取工具进入账本。
- 对接阶段 2 的 generation；过期 lease 不能创建新的 `dispatched` 转换。
- 建立 `unknown` 扫描器和逐工具 reconciler，不提供“所有未知动作统一重试”的总开关。

故障测试：

- `prepared` 后崩溃但未派发。
- 外部请求成功后、本地成功证据写入前崩溃。
- 相同幂等键重复派发。
- 不可幂等动作进入 `unknown` 后被禁止自动重试。
- journal 数据库不可写时执行被阻断。

完成门：纳入首期范围的每个副作用动作都能通过 action ID 回答意图、派发、结果、证据和重试决策。

### 阶段 5：把 recovery 接入 health/readiness

状态：已完成

主要修改范围：

- `systems/supervisor/supervisor.py`
- `systems/supervisor/service_runtime.py`
- health/readiness 路由和自主 lane 门控
- 启动恢复测试

实施要点：

- recovery 状态在 Supervisor 组装时初始化为 `pending`。
- 将恢复游标、错误摘要和最近成功事件保存到运行状态。
- `degraded/failed` 关闭新 claim，但保留只读诊断和安全的人工恢复接口。
- `/health`、`/ready` 和日志使用同一 recovery 状态对象，避免三个判断分叉。

完成门：恢复失败时服务不会报告完全健康，也不会继续认领自主任务。

### 阶段 6：持久化 ProcessRegistry 与有界 spool

状态：已完成

主要修改范围：

- `tools/process_registry.py`
- 本地命令 wrapper 和远程环境恢复契约
- runtime 数据目录清理策略
- 跨实例恢复和重启集成测试

实施要点：

- 先持久化元数据和完成通知，再实现受支持环境的重新观察。
- 输出由执行 wrapper 直接写 spool，registry 读取 spool，不依赖仅存在于父进程内存的 pipe。
- 重启恢复必须验证进程身份；验证失败转为 `unknown/orphaned`。
- 完成通知使用持久化消费标记，保证至少一次发现、幂等消费。
- 清理策略只删除已终结且超过保留期的记录；不得清理 active/unknown 项。

完成门：新 registry 实例能列出旧 session，并对每项给出可证明的终态或明确的 unknown，而不是静默丢失。

### 阶段 7：让上下文压缩引用动作证据

状态：已完成

主要修改范围：

- `agent/context_compressor.py`
- 工具结果持久化和消息构造路径
- ActionJournal 查询投影
- 压缩与摘要失败测试

实施要点：

- 工具消息持久化 `action_id` 和最小 ActionRef。
- 裁剪大型工具文本时保留 ActionRef，不把退出码、资源 ID 和结果状态只交给 LLM 摘要。
- 摘要失败占位符必须列出被压缩区间内的 ActionRef。
- 按需重取证据时执行权限和敏感字段过滤。

完成门：多次压缩和摘要失败后，所有副作用动作仍可按 action ID 追溯。

## 6. 数据迁移与兼容策略

### 6.1 迁移要求

- 所有 schema 具有显式版本号。
- 迁移必须可重复调用，并在中途失败后安全重启。
- 写迁移前保留可识别的备份或原子替换点。
- 迁移测试使用真实旧版样本，不只测试空数据库。
- 新写路径启用后，旧格式只允许在单一读取/迁移入口出现。

### 6.2 清理要求

每阶段结束时检查并删除：

- 旧状态字符串映射散点。
- 旧 `completed + is_error` 构造和消费者分支。
- 以 metadata 模拟 lease 事务的代码。
- 逐条消息 flush 和双权威恢复逻辑。
- 无调用方的参数、兼容别名和临时迁移开关。

不得为了“可能还有旧调用方”无限期保留两套主逻辑。确需迁移窗口时，应注明删除条件并在同一阶段完成清理。

## 7. 验证策略

### 7.1 必须新增的测试类型

- 状态机单元测试：每个合法/非法转换和终态。
- 并发测试：双 claim、旧 owner 迟到写回、CAS 冲突。
- 故障注入：写前、派发后、外部成功后、本地提交前、批次中途。
- 重启测试：新 service/registry 实例读取旧持久化状态。
- 幂等测试：相同消息批次、action ID、idempotency key 重放。
- 契约测试：CLI、桌面端、Gateway、Supervisor 对同一执行结果解释一致。
- 容量测试：spool 上限、journal 增长和清理策略。

### 7.2 每阶段基础验证命令

必须使用项目虚拟环境：

```powershell
.venv\Scripts\python.exe -m ruff check <本阶段修改文件>
.venv\Scripts\python.exe -m pytest <本阶段相关测试> -q
.venv\Scripts\python.exe -m pytest tests/test_documentation_contract.py -q
git diff --check
```

修改涉及模型、鉴权、请求协议、技能或打包时，追加运行：

```powershell
.venv\Scripts\python.exe -m pytest tests/test_integration_policy.py tests/test_packaging_contract.py -q
.venv\Scripts\python.exe scripts/build_wheel.py
```

阶段 2、4、5 属于自主执行安全边界，除定向测试外还应运行 Supervisor、自主链路和 live executor 相关测试。最终全部阶段完成后运行完整 pytest、Ruff、文档契约、退役集成扫描、wheel 构建及真实 Podman 自进化链路验证。

## 8. 可观测性与运行指标

实施后至少暴露以下指标或结构化日志字段：

- `execution_result_total{state, tool}`
- `stale_lease_write_rejected_total`
- `lease_reconcile_total{outcome}`
- `action_unknown_total{tool, retryability}`
- `action_reconcile_age_seconds`
- `session_batch_retry_total`
- `process_registry_recovered_total{state}`
- `supervisor_recovery_status`

日志应包含 trace ID、task ID、action ID、generation 和 attempt ID，但不得记录凭证或完整敏感参数。

## 9. 回滚边界

- 代码回滚不能直接回滚已经发生的外部副作用；必须依赖 ActionJournal 的补偿或 reconcile。
- 数据库迁移回滚优先使用迁移前备份和只读降级，不执行破坏性降级写入。
- fencing 上线后不得回滚到接受无 generation 写回的 API，否则旧执行者会重新获得污染能力。
- 新事件契约上线后，CLI 和桌面端消费者必须同步发布；若消费者未就绪，应阻断阶段合并，而不是长期双发两套事件。

## 10. 下一次会话启动清单

下一次开始实施时按以下顺序执行：

1. 阅读本方案、`AGENTS.md`、`docs/voidcube架构基线.md` 和 `docs/开发与验证.md`。
2. 检查工作树和近期提交，确认本方案是否已有阶段被实施，禁止重复迁移。
3. 只选择一个阶段推进；默认从阶段 0/1 开始。
4. 先运行该阶段现有测试并记录基线，再修改实现。
5. 完成代码、数据迁移、故障测试、文档更新和残留兼容清理。
6. 达到该阶段完成门后再进入下一阶段，不跨阶段留下半成品接口。

建议首个实施任务：完成阶段 1，修复 `ProcessRegistry` 的非零退出码误报，并建立工具执行结果与事件终态的统一契约。该任务范围小、风险可控，也为后续 journal 和恢复状态提供统一语义基础。
