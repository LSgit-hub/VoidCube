# Body Lifecycle And Switch Draft

> 文档状态：历史讨论草稿。
>
> 当前正式规范以 [body-lifecycle.md](../body-lifecycle.md) 和 [switch-protocol.md](../switch-protocol.md) 为准。本文保留为连续叙事和早期设计思路参考，不作为最新实现验收入口。

## 1. 文档定位

本文件是身体状态机与切换协议的讨论草稿，用来把“本体/替身交替造身体”的核心思想串成一条完整叙事。

正式规范以以下文档为准：

- [body-lifecycle.md](../body-lifecycle.md)
- [switch-protocol.md](../switch-protocol.md)

按当前基线，这份草稿也应显式带上同一层理解：

- VoidCube 是母体系统
- 双身体槽位对应的是两个子 Agent
- 交替造身体，本质上是母体持续培养、筛选、切换子 Agent 的过程
- 用户最终只会接触当前活跃子 Agent

## 2. 核心设定

VoidCube 始终至少有两具身体槽位：

- 当前工作的本体
- 当前待塑形的替身空壳

也可以直接理解为：

- 一个正在服务用户的子 Agent
- 一个正在被母体培养和验证的子 Agent

典型情况为：

- 身体 A：`active`
- 身体 B：`shell`

然后 A 负责改造 B。B 通过审查后成为新本体，A 再退役并回收为空壳。

这形成一个交替造身体的闭环。

## 3. 身体状态机

当前草案采用 5 态：

- `shell`
- `candidate`
- `probe`
- `active`
- `retired`

其含义简述如下：

- `shell`
  - 空壳，不工作，不承载正式接入
- `candidate`
  - 已改造完毕，等待审查
- `probe`
  - 已获临时接入，仅用于测试
- `active`
  - 当前本体，正式工作
- `retired`
  - 旧本体，短时保留用于回退

## 4. 本体 / 替身交替规则

### 4.1 单活体原则

任一时刻只能有一个 `active` 本体。

### 4.2 空壳优先原则

本体不直接热改自己，而是优先改造另一具 `shell`。

### 4.3 交替回收原则

切换成功后，旧本体先变 `retired`，观察窗口结束后再回收到 `shell`。

### 4.4 灵魂不迁移原则

切换过程中不复制“灵魂”，而是：

- 灵魂保持连续
- 新身体获得接入权
- 网关改路由

## 5. probe 检查规则

`probe` 是整个协议的核心安全缓冲层。

候选体进入 `probe` 后，至少应检查：

- 进程能否稳定启动
- 配置能否正确加载
- 基础工具能否正常工作
- 关键任务回放是否通过
- 行为是否符合身份边界
- 是否存在明显回归

`probe` 阶段的原则：

- 允许测试
- 不允许正式接单
- 允许思考
- 不允许成为未审批本体

## 6. 切换协议草案

### 6.1 正常路径

1. 本体发现需要自愈或自进化
2. 灵魂层记录升级目标
3. 本体改造空壳
4. 新体进入 `candidate`
5. 灵魂层切入监督态
6. 候选体获得 `probe` 接入权
7. 完成健康检查与关键回放
8. 监督态批准
9. 网关切流
10. 新体成为 `active`
11. 旧体成为 `retired`
12. 观察窗口通过后旧体回收为 `shell`

### 6.2 失败路径

1. 候选体在 `probe` 阶段失败
2. 监督态拒绝放行
3. 候选体退出运行
4. 失败原因写入灵魂层
5. 本体继续工作
6. 候选体被修复或重置为 `shell`

### 6.3 回滚路径

1. 新体已成为 `active`
2. 观察窗口内发现重大异常
3. 监督态要求回滚
4. 网关停止向新体派发新流量
5. 旧体恢复为 `active`
6. 新体退出工作态
7. 回滚记录写入灵魂层

### 6.4 当前实现收敛方向

当前代码已经不只是“草案推演”，而是开始收敛到一套可运行协议：

- 监督态当前优先由 `Mem` 治理历史、确定性 `Governor Engine` 和生命周期执行器共同承担
- 切换批准后会同步更新 `active_slot`、`retired_slot`、`shell_slot`，并写入 `.body-active.json`
- 执行器启动 active body 时，不再依赖抽象概念，而是读取槽位 launch target 与 slot runtime/worktree 信息
- 每个槽位都拥有自己的 `worktree/`、`runtime/`、`logs/`
- agent 运行态会把 `sessions/`、`cache/`、`state/` 等痕迹写入当前槽位自己的 `runtime/`
- `approve_with_watch` 后会自动启动 watch-window 后台监督任务，而不是只靠手工触发评估
- watch-window 稳定到期后可自动回收旧体；若健康失败则可自动触发回滚

## 7. 一个最重要的判断

对 VoidCube 来说，切换身体不是“把运行中的我复制到另一个目录”，而是：

- 保持灵魂层不变
- 构造新身体
- 给新身体临时接入
- 审查合格后改授正式接入权

因此，身体切换的难点不应被理解为“复制进程”，而应被理解为：

- 如何隔离候选体
- 如何定义接入权
- 如何做安全切流
- 如何定义回滚窗口

## 8. 对单仓库实现的启发

即使只用一个仓库，也可以形成双体交替：

- 一个源码主仓库
- 两个运行槽位
- 两份独立 runtime 目录或 worktree
- 一个共享灵魂层
- 一个统一网关

也就是说：

- 仓库是身体模板来源
- 槽位才是身体实例

这样就能把“单仓库”和“多身体交替”统一起来。

如果再按母体-子体结构说得更明确一点：

- 仓库是母体培育子 Agent 的模板来源
- 槽位才是子 Agent 的独立落盘与运行边界
- 因此每个子 Agent 都应尽量保有自己的 `worktree/`、`runtime/`、`logs/`、`meta.json`

## 9. 单仓库双槽位实现草案

### 9.1 设计目标

在不拆多仓库的前提下，实现：

- 当前本体可稳定工作
- 候选体可隔离构造
- 新旧体可交替切换
- 灵魂层保持唯一身份连续性

### 9.2 推荐实现模型

建议采用：

- 一个主源码仓库
- 两个固定身体槽位
  - `slot-A`
  - `slot-B`
- 一个共享灵魂层
- 一个统一网关
- 一个身体生命周期执行器

### 9.3 仓库与槽位分离原则

最重要的边界是：

- 仓库不是身体
- 工作目录也不是身体本身
- 身体是“从仓库模板派生出来的一组运行实例状态”

因此可以这样理解：

- Git 仓库保存身体模板
- `slot-A` 和 `slot-B` 是两具交替使用的身体槽位
- 每个槽位有自己的运行目录、日志、缓存、PID 和本地状态

### 9.4 与现有代码的贴合点

当前仓库里，这条路线已经开始落地：

- `systems/body_registry.py`
  - 已负责槽位注册表、槽位元数据、active 指针与 slot runtime/worktree materialize
- `systems/probe.py`
  - 已把 probe 检查收敛为结构化报告
- `systems/governor.py`
  - 已承担当前阶段的确定性监督裁决
- `systems/lifecycle.py`
  - 已负责把批准结果变成真实状态迁移
- `systems/execution/` 与相关生命周期模块
  - 已开始承担切换执行、watch-window 协调与 active body 启动
- `systems/agent/run_agent_instance.py`
  - 已把 agent 运行痕迹隔离到槽位 runtime 中

这意味着实验已经从“把并行 worktree 提升为正式身体槽位”的设想，进入“身体协议已开始自我执行”的阶段。

## 10. 推荐目录与槽位模型

### 10.1 推荐结构

建议长期过渡到类似这样的运行布局：

```text
repo-root/
  .body-registry.json
  .body-active.json
  .body-slots/
    slot-A/
      worktree/
      runtime/
      logs/
      meta.json
    slot-B/
      worktree/
      runtime/
      logs/
      meta.json
```

其中：

- `worktree/`
  - 该槽位对应的源码工作树
- `runtime/`
  - 该槽位专属运行目录
- `logs/`
  - 该槽位专属日志
- `meta.json`
  - 槽位状态、版本、最近切换信息
- `.body-registry.json`
  - 全局槽位角色分配、观察窗口与最近切换结果
- `.body-active.json`
  - 当前 active body 的直接启动指针

### 10.2 runtime 隔离内容

每个槽位至少要隔离：

- 当前工作目录
- 临时文件
- 日志
- PID 文件
- 会话缓存
- 本地工具缓存
- 本地状态快照
- 候选检查输出

尽量不要隔离：

- 灵魂层数据库
- 宪法文档
- 全局治理历史

## 11. 双槽位元数据建议

每个槽位的 `meta.json` 建议至少记录：

- `slot_id`
- `body_state`
- `body_version`
- `generation`
- `build_from_commit`
- `last_probe_result`
- `last_switch_at`
- `last_retired_at`
- `materialized_from`
- `runtime_bootstrapped_at`
- `runtime_path`
- `logs_path`
- `worktree_path`

而全局身体注册表建议再额外保存：

- 当前 `active_slot`
- 当前 `retired_slot`
- 当前 `shell_slot`
- 当前观察窗口信息
- 最近一次切换结果

## 12. 单仓库下的隔离策略

### 12.1 首选策略：固定双 worktree

如果仓库本身就是主要身体模板，最适合实验期的方式是：

- 主仓库存主线
- `slot-A/worktree`
- `slot-B/worktree`

两个槽位常驻存在，而不是每次临时创建又删除。

优点：

- 符合你“固定两具身体轮换”的直觉
- 避免频繁建删 worktree 带来的混乱
- 更容易保留槽位级演化历史

### 12.2 次选策略：共享仓库 + 独立 runtime

如果早期不想引入常驻 worktree，可以先做：

- 一个共享源码目录
- 两个隔离 runtime 目录

但这种方式更适合“同版本双实例”，不太适合“本体改造替身源码”的实验。

所以从你的目标看，我更推荐固定双 worktree。

## 13. 本体如何改造替身

推荐流程：

1. 当前本体识别当前空壳槽位
2. 本体只在空壳槽位对应的 `worktree` 中生成补丁或应用变更
3. 候选构建与初始化在该槽位自己的 `runtime` 中进行
4. 候选通过后才申请 `probe`

这个模型的好处是：

- 本体不改自己所在槽位
- 改动目标永远是另一具身体
- 失败不会直接污染当前工作本体

## 14. 切换时到底切什么

切换动作建议拆成 4 个明确对象：

- `active lease`
- 网关流量指针
- 当前本体槽位标识
- active body pointer
- 观察窗口上下文

换句话说，切换不是“复制进程”，而是切换：

- 哪个槽位持有正式接入权
- 哪个槽位接收网关正式流量
- 哪个槽位被灵魂层承认是当前本体
- 哪个槽位的 launch target 会被执行器真正拉起

## 15. probe 的实现建议

`probe` 不应只是“能启动就算过”，而应是一个独立受控阶段。

建议至少包括：

- 槽位启动检查
- 基础 REPL/Agent 初始化检查
- 关键工具最小冒烟检查
- 配置与记忆读写边界检查
- 一个或多个典型任务回放

### 15.1 probe 环境要求

- 使用候选槽位自己的 `runtime`
- 只发放 `probe lease`
- 网关不指向真实用户流量
- 所有结果结构化回写灵魂层

## 16. 观察窗口建议

新槽位切为 `active` 后，建议观察窗口至少包含：

- 数个健康探针周期
- 一小批真实请求
- 至少一次记忆写回
- 至少一次工具调用链路验证
- active slot runtime manifest 存在且可读
- `session/state` 写入成功
- 自动监督任务仍在运行
- 触发异常时可直接生成回滚请求

观察窗口结束前：

- 旧体仍保留为 `retired`
- 不应立即清空

## 17. 回收为空壳时的清理规则

旧体从 `retired` 回收到 `shell` 时，建议清理：

- 进程与 PID
- 本地会话缓存
- 临时工具结果
- 临时附件和中间文件
- 探测阶段遗留日志索引

但不清理：

- 槽位元数据
- 身体版本记录
- 切换历史引用

也就是说，清空的是“运行痕迹”，不是“身体谱系”。

## 18. 建议的最小实验实现顺序

如果按实验性项目推进，我建议顺序是：

1. 固定双槽位目录模型
2. 槽位元数据文件
3. 当前活跃槽位指针
4. 候选槽位构建流程
5. `probe` 检查脚本或检查协议
6. 网关切流
7. 观察窗口
8. 回滚
9. 槽位回收为 `shell`

这样推进能避免一开始就做过重的全自动自进化系统。
