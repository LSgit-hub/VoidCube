# 内生驱动质量基线

## 1. 这份基线解决什么问题

这份文档不是另一份设计书，也不是在重新定义“内生驱动是什么”。

它只解决一件事：

- 在 [内生驱动核心设计](./内生驱动核心设计.md) 已经确定的主定义下，当前阶段应该优先守住哪些质量边界

也就是说：

- “内生驱动的本体是什么”看主设计
- “当前收敛时最怕退回什么方向”看这份质量基线

这是一份精简的收敛约束文档，不是第二套架构说明。

如果后续需要判断当前问题更偏“定义错位、实现错位还是验证缺口”，请同时参考 [内生驱动问题清单](./内生驱动问题清单.md)。

## 2. 它和主设计是什么关系

主设计已经明确：

```text
感知状态
  -> 构建世界模型
    -> 识别 need / tension
      -> 形成 intent
        -> 选择治理输出
```

这份基线不改这条主链。

当前阶段它只额外强调一件事：

> 当内生驱动在当前实现里通过 LM 参与判断，并把部分判断继续投影成兼容任务输出时，这条链必须保持稳、准、少噪声。

所以这份基线关注的是主设计里的一个当前实现切面：

```text
感知证据汇聚
  -> LM 认知判断
    -> 治理输出投影
      -> 兼容任务产出
```

这里的“任务产出”不是本体，只是当前阶段仍然保留的一种兼容投影。

## 3. 当前主优化目标

当前阶段，内生驱动的主优化目标不是扩功能，而是提升这段实现切面的稳定性：

- 证据弱时是否更保守
- 证据强时是否更聚焦
- 同类场景下是否更稳定
- 是否减少无依据 improvement 漂移
- 是否减少把认知判断重新压扁成任务冲动

判断标准不是“看起来更复杂”，而是“是否更稳、更准、更少噪声”。

## 4. 已确认的三条核心质量边界

### 4.1 弱证据允许空 proposals

当 grounding 弱、证据不足、当前不适合 improvement 时：

- LM 可以返回空 `proposals`
- 系统必须允许这种返回
- 后续链路不能偷偷补出 LM 候选

这条边界的意义是：

- 内生驱动可以“有判断地不行动”
- 当前兼容任务投影可以为空
- 不再为了看起来智能而硬凑任务

### 4.2 弱 improvement 不得压过保守 review

当同一批次里同时出现：

- 弱 evidence 的 `body_improvement`
- 更保守、更符合 grounding 修复需求的 `review`

系统必须满足以下至少一种结果：

- `review` 的最终候选效用高于 `improvement`
- 或更进一步，直接把弱 `improvement` 从最终 LM 候选里压掉

这条边界的意义是：

- 系统优先稳态和修复
- 不让成长冲动压过证据现实
- 不让兼容任务输出反向污染主判断

### 4.3 LM 主输入优先 context layers，裁掉重复认知噪声

当以下主 context 已存在时：

- `decision_core`
- `supporting_detail`
- `long_tail_context`

prompt 主输入应优先保留这些主层，并裁掉重复的派生摘要，例如：

- `cognitive_assessment_memory`
- `self_iteration_trend_memory`
- `switch_self_regulation_memory`
- `post_task_effect_memory`
- `proposal_drift_memory`
- `cognitive_evolution_draft`

其中：

- `cognitive_evolution_draft` 仍保留在 runtime 观察层
- 但不再抢占 LM prompt 的主注意力

这条边界的意义是：

- 保证 LM 面对的是提炼后的主判断上下文
- 避免被重复摘要污染注意力
- 防止观察层重新挤占主判断层

## 5. 当前收敛原则

### 5.1 先补质量回归，不先扩结构

如果一个“新能力”不能转化成明确的质量边界测试，优先不加。

### 5.2 先减少噪声，再增加认知层

不是字段越多越智能。

对 LM 来说：

- 高信号输入比大而全输入更重要
- 主判断层比重复摘要更重要

### 5.3 观察层可以丰富，主决策层必须克制

运行时观测可以保留更多认知可见性。

但进入 LM 主 prompt 的内容，必须尽量少而关键。

### 5.4 允许保守，禁止虚假积极

在弱场景下：

- 返回空 proposals
- 保留弱质量 review
- 压掉弱 improvement

这些都属于正确行为，不应被误判为“系统没工作”。

### 5.5 不让兼容任务叙事重新上位

后续如果继续优化，不能因为当前仍有 `proposal / task_type / candidate` 这些兼容接口，就把它们重新写回主设计中心。

当前正确方向应始终是：

- 认知判断优先
- 治理输出选择优先
- 任务只是兼容投影

## 6. 当前不建议优先做的事

现阶段不建议继续做这些方向：

- 继续增加更多外围认知展示字段
- 为了“更像超级智能体”继续扩展术语层
- 把观察层结构再塞回 LM 主 prompt
- 在没有质量回归前增加新的自治输出面
- 把兼容任务语言重新写成主摘要语言

## 7. 后续优化应如何判断是否值得做

一个改动值得继续推进，至少应满足以下之一：

- 明显减少无依据 improvement 漂移
- 明显提升弱场景下的保守稳定性
- 明显提升同类场景下的输出一致性
- 明显减少 prompt 噪声而不削弱主判断质量
- 明显减少“认知判断被任务语言重新压扁”的倾向

如果做不到这些，只是让结构更复杂，一般不值得继续加。

## 8. 对后续会话的直接要求

后续如果继续改内生驱动，优先顺序应保持为：

1. 先确认是否影响主设计中的认知判断链
2. 再确认是否影响三条质量边界
3. 优先补测试，后补结构
4. 能收敛就不要扩面
5. 不要把兼容投影重新写回主逻辑

这份基线的目标只有一个：

> 让内生驱动在当前实现阶段持续朝“更稳、更准、更少噪声”的方向前进，
> 而不是重新走回“更宽、更复杂、但不一定更聪明”的路线。
