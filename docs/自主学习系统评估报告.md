# VoidCube 自主学习系统评估报告

> 评估日期：2026-08-05
> 评估范围：项目的自主学习系统、自学习方法与自学习能力

---

## 一、评估总览

VoidCube 的自主学习系统采用了**五层递进架构**：从用户可触发的学习技能，到内生驱动的认知决策引擎，再到受治理的身体自进化。整个系统不是单一的学习算法，而是一个**以 LLM 为认知核心、以确定性规则为安全边界、以 Git worktree 为实验沙箱**的复合自主改进体系。

**核心评级：架构设计 B+ / 实现完整度 B / 学习闭环 C+**

---

## 二、自学习系统五层架构

### 第 1 层：用户触发式自学习（Skill Layer）

**对应代码：** [skills/self-learning/SKILL.md](../skills/self-learning/SKILL.md)

| 维度 | 评估 |
|------|------|
| **触发方式** | 用户手动 `/self-learning start`，被动发起 |
| **学习方法** | Web 搜索 + GitHub 仓库发掘 → 多维度评分 → 笔记归档 |
| **评分体系** | 5 维度加权评分（实用性 30% + 前沿性 20% + 成熟度 20% + 学习成本 15% + 长期价值 15%） |
| **知识管理** | 三级归档：core（≥70 分）→ archive（50-69）→ reference（<50） |
| **输出格式** | Subagent 结构化 JSON contract（Topic → Session → Experiment → Conclusion） |

**优点：**
- 评分维度设计合理，兼顾实用性和前沿性
- 结构化输出可接入自动学习记录管线
- 有明确的工具限制（learn toolset），防止 subagent 越权

**不足：**
- 本质上是"搜索+总结"，不是真正的自主学习
- 依赖用户手动启动，不具有自主性
- 未发现任何代码在执行此技能的 subagent 输出后，**自动**将其经由 Topic → Session → Experiment → Conclusion 管线写入 `SelfLearningConclusionStore`

### 第 2 层：学习结论存储与任务提案（Conclusion Store）

**对应代码：** [systems/self_learning/conclusion_store.py](../systems/self_learning/conclusion_store.py)

| 维度 | 评估 |
|------|------|
| **数据模型** | LearningTopic → LearningSession → ExperimentRecord → LearningConclusion → SupervisorTaskProposal |
| **持久化** | 文件系统 JSON（topics/、sessions/、experiments/、conclusions/） |
| **治理集成** | 写入 GovernanceEvent（CANDIDATE_REVIEW + RECORD_ONLY） |
| **反馈闭环** | `record_feedback()` 记录 usefulness 反馈，可用于后续权重调整 |
| **任务桥接** | `build_supervisor_submission()` 将推荐转化为 Supervisor 任务提案 |

**优点：**
- 完整的学习实验记录模型，支持 hypothesis → method → observations → outcome 的科学方法范式
- 反馈机制存在（`record_feedback`），为强化学习留下接口
- 与 Governance 事件系统打通，学习结论进入可审计的治理历史

**不足：**
- 模块自身标注为 "Legacy … compatibility record/payload layer"，明确不是当前自主执行的所有者
- `record_feedback()` 方法在代码中定义了但未发现实际的调用方——**反馈闭环在代码层面未闭合**
- 从 `LearningRecommendation` 到实际执行的任务之间缺少自动化桥梁

### 第 3 层：内生驱动引擎（Endogenous Drive）

**对应代码：** [systems/supervisor/endogenous_drive.py](../systems/supervisor/endogenous_drive.py)、[endogenous_drive_cycle.py](../systems/supervisor/endogenous_drive_cycle.py)、[endogenous_learning.py](../systems/supervisor/endogenous_learning.py) 等 40+ 个模块

这是整个自学习系统的**认知核心**，也是最复杂的部分。

#### 3.1 三层认知模型

```
感知层 (Perception)      → 用户模式、系统姿态、纠错信号
世界模型 (World Model)    → 真实性压力、记忆压力、身体升级就绪度
反思层 (Reflection)       → 学习产出状态、阻塞压力、自主就绪度
```

#### 3.2 候选任务生成与评分

**三种学习候选类型：**

| 类型 | 来源 | 触发条件 |
|------|------|---------|
| `shell_baseline_learning` | 代码库自检 | Shell 槽位就绪时，学习当前代码库结构 |
| `exploratory_learning` | 活动元数据 | 从用户/Agent 活动中提取学习主题，评估新颖性 |
| `cognitive_assessment_review` | 认知评估记忆 | 回顾内生认知判断，记录学习笔记 |

**评分权重体系（[endogenous_candidate_pipeline.py](../systems/supervisor/endogenous_candidate_pipeline.py)）：**

| 维度 | 权重 |
|------|------|
| 核心价值强度 (core_value_strength) | 38% |
| 紧迫性 (urgency) | 24% |
| 新颖性 (novelty) | 14% |
| 执行就绪度 (execution_readiness) | 14% |
| 特异性 (specificity) | 10% |
| 积压惩罚 (backlog_pressure_penalty) | -12% |
| 重复惩罚 (repetition_penalty) | -10% |

**三大核心价值：**
- **Continuity**：保护长期记忆、谱系和服务连续性
- **Truthfulness**：在不确定性固化前暴露纠错信号和证据缺口
- **Creativity**：将空闲容量转化为有界的学习和改进提案

#### 3.3 自适应策略引擎

**对应代码：** [endogenous_adaptive_policy.py](../systems/supervisor/endogenous_adaptive_policy.py)

根据当前上下文动态选择焦点模式：
- `observation` — 抑制 backlog 增长，只允许治理审查类候选
- `truthfulness` — 偏向真实性审查和纠错
- `creativity` — 开放探索性学习和改进提案

策略通过 `strategy_context_key(user_mode, system_posture, dominant_constraint)` 索引历史策略效果，实现上下文感知的策略选择。

#### 3.4 认知自我调节

**对应代码：** [endogenous_self_regulation_service.py](../systems/supervisor/endogenous_self_regulation_service.py)

从 proposal_drift_memory、reference_alignment、evidence_credibility 等多个信号计算四个动态调节系数：
- `dynamic_candidate_throttle_boost`：候选节流
- `dynamic_observation_bias_boost`：观察偏向
- `dynamic_truthfulness_bias_boost`：真实性偏向
- `dynamic_learning_expansion_suppression`：学习扩展抑制

#### 3.5 自我模型

**对应代码：** [endogenous_self_model.py](../systems/supervisor/endogenous_self_model.py)

系统维护一个"自我理解"快照，包含：
- **就绪度评估**：综合身体结构、近期学习、外部研究、参考对齐四个维度的加权分数
- **自我理解缺口**：明确识别当前缺失的能力（body_profile_incomplete、missing_recent_learning_trace 等）
- **证据可信度摘要**：按通道（recent_learning、external_research、shell_body_profile）评估证据质量

#### 3.6 LLM 驱动的任务生成

**对应代码：** [endogenous_proposals.py](../systems/supervisor/endogenous_proposals.py)

当配置启用 `endogenous_drive_lm_task_generation_enabled` 时，系统调用 API-B（后台 LLM）基于压缩记忆上下文生成智能任务提案。关键约束：
- 提案必须显式绑定 evidence graph / agenda graph 节点
- 证据不足时必须允许返回空 proposals
- LLM 生成的 cognitive_assessment 被视为"真实认知中间层"

**优点：**
- 三层认知模型有清晰的理论基础（感知→世界模型→反思）
- 候选评分权重设计合理，核心价值权重最高
- 自适应策略能在不同上下文间切换，避免盲目扩张 backlog
- 自我调节机制提供了负反馈回路
- LLM 任务生成的提示工程有精心的分层设计（decision_core → supporting_detail → long_tail）

**不足：**
- **核心瓶颈**：整个内生驱动引擎是一个**基于规则的候选生成 + LLM 辅助评分**的系统，不具备从历史结果中统计学习的能力
- 自我模型虽然能评估就绪度，但评估本身来自硬编码规则，无法随着运行经验改善
- 自适应策略的 `strategy_context_key` 历史索引目前仅是键值查找，没有实际的策略梯度更新
- LLM 任务生成依赖外部模型推理能力，成本和延迟不可控

### 第 4 层：自主链路执行（Autonomous Chain）

**对应代码：** [systems/supervisor/autonomous_cycle_service.py](../systems/supervisor/autonomous_cycle_service.py)，以及 planning、review、execution handoff、memory promotion 等 10+ 服务模块

#### 4.1 完整闭环

```
内生驱动评估 → 候选门控(by posture) → 持久化 → API-B 判断插入
    → 任务规划(planning) → 任务审查(review) → 治理审查(governance)
    → 执行交接(handoff) → API-A 执行 → 记忆提升(memory promotion)
    → 结果写回 Memory & Supervisor
```

#### 4.2 任务生命周期

每个自主任务带有完整的元数据追踪：
- `governance_task_type`、`task_family`、`execution_kind`
- 运行时任务画像 (runtime task profile)
- Git lineage（当任务涉及代码变更时）
- 回退计划 (rollback_plan)
- 调度分配 (schedule_allocator)

#### 4.3 审查与决策

- **自动决策**：对于确定性规则可覆盖的任务，系统自动 approve/reject
- **治理审查**：涉及身体改进的任务必须通过 Governor 审查
- **记忆提升**：学习类任务的结果通过 `autonomous_task_memory_promotion_service` 写入记忆系统

**优点：**
- 完整的任务生命周期管理，从生成到执行到记忆形成闭环
- 治理事件贯穿全链路，所有决策可审计
- 记忆提升机制确保学习成果持久化

**不足：**
- 执行交接后 API-A 实际"学会"了什么，Supervisor 只能通过下一个 review cycle 的治理事件间接感知——**缺乏直接的学习效果评估**
- `autonomous_cycle_service.run()` 中 drive→review 两个阶段是顺序执行，中间有失败则 review 仍会尝试运行，但 drive 失败时 review 在没有新候选的情况下运行可能无意义

### 第 5 层：身体自进化（Body Self-Evolution）

**对应代码：** [systems/body_registry.py](../systems/body_registry.py)、[systems/governor.py](../systems/governor.py)、[systems/lifecycle.py](../systems/lifecycle.py)、[systems/probe.py](../systems/probe.py) 等

#### 5.1 双槽位架构

```
slot-A (active) ← 当前运行的替身
slot-B (shell)  ← 空闲候选槽位，接收改进
```

每个槽位是完整 Git worktree 的独立副本。

#### 5.2 状态机

```
shell → candidate → probe → awaiting_user_consent → active → retired → shell
                    ↑ 失败则 abandon                                 ↓
                    └────────────────────────────────────────────────┘
```

#### 5.3 安全机制

| 机制 | 说明 |
|------|------|
| **Governor 确定性引擎** | 所有状态变更必须通过规则审批，LLM 仅作为低置信度时的咨询角色 |
| **Probe 五类检查** | 启动、配置加载、记忆路径、工具冒烟、任务回放 |
| **Watch Window** | 激活后的观察期（默认 300s），失败自动回退 |
| **Git 级回退** | 改进回退通过 `git reset --hard` 精确恢复到健康 commit |
| **用户同意门控** | 身体切换必须经过 `awaiting_user_consent` → 用户明确同意 |
| **进化边界** | `evolution_boundary.py` 严格定义 Agent 可修改和不可修改的路径 |

#### 5.4 改进流程

1. Agent 在 shell worktree 中编辑代码 → git commit
2. 提交 `BodyImprovementReport`（含 diff_summary、changed_files）
3. Governor 审查 → issue probe lease
4. 执行五类健康检查
5. Governor 切换审查 → 等待用户同意
6. 激活新替身，旧进入 retired + Watch Window
7. Watch Window 通过 → 回收；失败 → 回退

**优点：**
- **安全设计是系统最强的部分**：确定性治理引擎 + 多层门控 + Git 级回退 + 进化边界
- 双槽位架构使"实验-验证-切换"流程物理隔离，不影响运行中服务
- Governor 的 LLM 推理是纯咨询性的，不覆盖确定性决策——这是正确的安全设计
- 健康评分、文件重复修改惩罚、学习新鲜度等评分维度考虑周全

**不足：**
- 身体改进的内容（Agent 在 worktree 中修改什么代码）完全由 LLM（API-A）决定，系统不做代码质量的确定性验证
- **Probe 验证的是"没坏"而非"变好了"**——五类检查确保替身能启动、能加载配置、工具能执行，但不会在改进前后分别跑一次基准来量化"这个改动到底有没有让系统变得更好"
- 缺少改进效果的基线度量（baseline measurement）：系统记录了什么被改了（git diff），验证了改完不会炸（probe），但从未在改之前跑一次基准、改之后再跑一次做对比

## 三、自学习方法分类评估

### 3.1 基于搜索的知识获取（Skill Layer）

| 评估项 | 结论 |
|--------|------|
| 方法 | Web 搜索 + GitHub 挖掘 + 多维度评分 |
| 自动化程度 | 低——需用户手动 `/self-learning start` |
| 学习质量 | 依赖搜索质量和 LLM 总结能力 |
| 持久化 | 笔记文件系统归档，非结构化 |
| 闭环 | 缺失——Subagent 输出未自动接入 Conclusion Store |

### 3.2 基于内生驱动的自主选题学习

| 评估项 | 结论 |
|--------|------|
| 方法 | 从用户活动/Agent 工作元数据中提取主题，计算新颖性/特异性评分，生成学习候选 |
| 自动化程度 | 高——在内生驱动周期中自动触发 |
| 学习质量 | 主题去重和冷却机制设计合理，但学习内容质量依赖 API-A 执行质量 |
| 持久化 | 通过 AutonomousChainStore → Memory 完整闭环 |
| 闭环 | **部分闭合**——任务执行结果通过 review cycle 写回 Memory，但无量化效果评估 |

### 3.3 基于认知评估的元学习

| 评估项 | 结论 |
|--------|------|
| 方法 | 系统定期审查自己的认知判断质量（proposal_drift、reference_alignment），生成改进假设 |
| 自动化程度 | 高——`cognitive_assessment_review` 候选在内生驱动中自动生成 |
| 学习质量 | 元认知设计是创新点，但假设验证路径不清晰 |
| 持久化 | 认知评估记忆通过 `cognitive_assessment_memory` 字段在提案间传递 |
| 闭环 | **弱**——"我上一次判断偏了"这个认知能否真正改善下一次判断，取决于 LLM 的上下文理解，非系统性学习 |

### 3.4 基于身体自进化的代码改进

| 评估项 | 结论 |
|--------|------|
| 方法 | Agent 在隔离 worktree 中修改代码 → 健康检查 → 治理审批 → 切换 |
| 自动化程度 | 中——需要用户同意门控 |
| 学习质量 | 取决于 API-A Agent 的代码理解和改进能力 |
| 持久化 | 完整的 Git 历史 + 槽位元数据中的 health_history |
| 闭环 | **安全闭环完整，但效果闭环缺失**——知道是否安全切换，不知道是否真的变得更好 |

### 3.5 基于反馈信号的行为调整

| 评估项 | 结论 |
|--------|------|
| 方法 | 自适应策略、自我调节系数、策略记忆、历史效果统计 |
| 自动化程度 | 高——完全自动化 |
| 学习质量 | **本质上是参数查表而非学习**——`strategy_context_key` 映射是静态关联 |
| 持久化 | 通过 `EndogenousGovernanceStatePersistenceService` 持久化 |
| 闭环 | **弱**——策略选择基于规则，策略效果评估也是基于规则，没有强化信号更新 |

### 3.6 基于 Web 的在线知识获取——能力与实际的差距

这是对"学习系统能否到网站上学习最新技术/知识（如 GitHub、Python 官方 API 文档等）"的专项评估。

#### 3.6.1 工具栈：能力完备

VoidCube 拥有三套可直接访问互联网学习最新技术的工具：

| 工具 | 能力 | 后端支持 |
|------|------|---------|
| `web_search_tool` | 搜索 Web，返回 URL/标题/摘要 | Exa / Firecrawl / Parallel / Tavily / 本地模式 |
| `web_extract_tool` | 提取任意 URL 的完整内容为 Markdown | 同上，支持批量 URL 提取 |
| `browser_*` 系列（10+ 工具） | 完整浏览器自动化：导航、快照、点击、输入、滚动、截图、控制台 | Camofox（基于 Firefox） |

**对应代码：**
- [tools/web_tools.py:1080](../tools/web_tools.py#L1080) — `web_search_tool`，支持 5 种搜索后端，含本地模式回退
- [tools/web_tools.py:1236](../tools/web_tools.py#L1236) — `web_extract_tool`，异步批量提取 + LLM 智能压缩
- [tools/browser_tool.py](../tools/browser_tool.py) — 98KB 的完整浏览器自动化套件

此外，专门的 **`learn` toolset** 已在 [tools/toolsets.py:130-146](../tools/toolsets.py#L130-L146) 中定义：

```python
"learn": {
    "description": "Research-only tools for self-learning subagents: web search, "
                   "file reading, terminal, code execution, and browser automation. "
                   "No file writes, no skill mutations, no memory writes, no delegation.",
    "tools": [
        "web_search", "web_extract",
        "read_file", "search_files",
        "terminal", "execute_code",
        "browser_navigate", "browser_snapshot", "browser_click",
        "browser_type", "browser_scroll", "browser_extract",
        "browser_wait", "browser_close", "browser_screenshot",
    ],
}
```

这是一个专门为自学习 subagent 设计的"只读研究"工具集——可以搜索、提取网页、浏览网站，但不能写文件、不能修改技能、不能写记忆。

同样，[skills/self-learning/SKILL.md:422-424](../skills/self-learning/SKILL.md#L422-L424) 也明确规定了 subagent 使用此 toolset：

> Subagent 仅可使用以下工具（learn toolset）：web_search, web_extract, read_file, search_files, terminal, execute_code。禁止 write_file, patch, delegate_task, memory, clarify, skill_manage。

#### 3.6.2 集成层：自主链路未系统性地强制使用 Web 工具

问题出在**从"任务生成"到"任务执行"的衔接**上，存在三处断裂：

**断裂 ① — 自主学习任务 prompt 没有指示使用 Web 工具**

[VoidCube_cli/autonomous_executor.py:126-140](../VoidCube_cli/autonomous_executor.py#L126-L140) — 当内生驱动生成的 `exploratory_learning` 候选被审批后，注入给执行 Agent 的 prompt 实际是：

```
[Autonomous Learning Task] Research: {title}
{summary}
Learning branch: exploratory
Execute this research task thoroughly. Produce structured findings and conclusions.
```

对比 SKILL.md 中的详细指示（搜索最新趋势、GitHub 高星仓库、提取网页内容、多维度评分），自主链路的 prompt **没有任何明确的 Web 工具使用指令**。Agent 是否调用 `web_search` / `web_extract` **完全取决于 LLM 自身的判断**，而非系统性要求。

**断裂 ② — 执行时不切换 toolset**

`inject_execution_prompt()`（[autonomous_executor.py:218-243](../VoidCube_cli/autonomous_executor.py#L218-L243)）只是将文本注入 CLI agent 的输入队列——没有 toolset 切换逻辑。Agent 保留全部工具权限（包括 `write_file`、`patch` 等），意味着：

- 学习任务**未被限制**在 `learn` toolset 中（可以写文件，存在越权风险）
- 学习任务也**未被显式赋予** `learn` toolset（如果 Agent 当前 toolset 不包含 web 工具，则无法上网）

**断裂 ③ — 学习主题来源于本地元数据，而非 Web 发现**

[endogenous_learning.py:37-65](../systems/supervisor/endogenous_learning.py#L37-L65) — `extract_learning_topic()` 从 gateway activity metadata（用户请求文本、Agent 工作摘要）中提取主题，而不是主动搜索 Web 发现新技术趋势。探索性学习的"新颖性"评分基于该主题是否近期在本地出现过（`topic_novelty_score` 比较的是 `recent_learning_signatures`），而非与外部知识库的对比。

这意味着：**如果用户从未提及某项新技术，系统不会主动从 Web 发现它。**

#### 3.6.3 三层学习入口的 Web 能力矩阵

| 学习入口 | 能否访问 Web | 能否访问 GitHub | 能否读 API 文档 | 触发方式 | Web 使用保障 |
|----------|:---:|:---:|:---:|------|:---:|
| `/self-learning` Skill | ✅ 明确指示使用 | ✅ SKILL.md 有 GitHub 搜索策略 | ✅ web_extract | 手动 `/self-learning start` | **强**——SKILL.md 详细规定了搜索策略 |
| 内生驱动 `exploratory_learning` | ⚠️ 看 LLM 主动性 | ⚠️ 看 LLM 主动性 | ⚠️ 看 LLM 主动性 | 自动（内生驱动周期） | **弱**——prompt 无指示 |
| 内生驱动 `shell_baseline_learning` | ❌ 读本地代码库 | ❌ | ❌ | 自动（Shell 槽位就绪时） | 无 |

#### 3.6.4 根因总结

> **工具栈是完整的，但从"自动决定学什么"到"自动上网学"之间缺少一条系统性的指令链路。** 当前状态是：如果 LLM Agent 自己想到要用 `web_search`，它就能用；但没有任何机制**确保**它在执行学习任务时一定会去搜索最新资料，而非仅凭自身训练数据的知识来回答。

具体缺失的环节：

1. **任务生成时**：内生驱动生成的 `exploratory_learning` 候选未携带"需要 Web 搜索"的标记
2. **任务执行时**：`inject_execution_prompt()` 未根据任务类型切换 toolset 或注入 Web 工具使用指令
3. **执行 prompt 中**：没有类似 SKILL.md 中的搜索策略指导（搜索什么关键词、优先什么来源、如何评分）
4. **闭环验证**：没有机制检查学习任务是否实际使用了 Web 工具，以及获取的信息是否来自最新来源

## 四、系统亮点与创新

### 4.1 独特优势

1. **安全优先的自主进化设计**：确定性 Governor + 多层门控 + Git 级回退 + 进化边界，是目前开源 AI agent 项目中最完善的自主代码修改安全体系之一。

2. **双模式架构**：daily_companion 与 auto_evolution 的清晰分离，避免自主学习和用户服务互相干扰。

3. **记忆域隔离**：`agent_interaction` / `companion` / `evolution` 三域物理隔离 + 跨域可审计提升，是成熟的记忆架构设计。

4. **认知模型分层**：Perception → World Model → Reflection 三层认知模型 + 自我就绪度评估 + 证据可信度分析，在概念层面超越了简单的 "LLM agent loop"。

5. **全面的治理事件追踪**：从内生驱动的任务生成到执行完成的记忆提升，所有决策都有治理事件记录，确保了可审计性。

6. **物理隔离的实验环境**：Git worktree 双槽位使代码改进实验不影响运行中服务，这是生产级自主进化的必要前提。

### 4.2 代码工程质量

- 模块化程度高，Supervisor 下有 80+ 个职责分明的模块文件
- 全程使用 Pydantic 进行数据模型验证
- 依赖注入模式清晰，服务通过显式端口（port）协作
- 策略与机制分离（如 `endogenous_policy.py` 常量 vs `endogenous_adaptive_policy.py` 逻辑）

## 五、关键缺陷与改进空间

### 5.1 学习闭环不完整（影响等级：高）

**问题**：系统能生成学习任务、执行学习任务、记录学习结果，但无法**量化评估学习效果**。

- `SelfLearningConclusionStore.record_feedback()` 方法定义了但未发现实际调用方
- `AutonomousTaskReviewService` 审查任务结果但仅做二元决策（approve/reject），不做效果评分
- 身体改进的 Probe 只检查功能正确性，不检查性能/质量提升

**建议**：在 review cycle 中增加效果评估步骤——对比任务执行前后的关键指标，生成量化的 `improvement_score`。

### 5.2 缺乏统计学习能力（影响等级：高）

**问题**：整个内生驱动和学习系统是基于规则的 + LLM 辅助，不具备从历史数据中统计学习的能力。

- 自适应策略的 `strategy_context_key` 是静态关联，不随经验更新
- 候选评分权重是硬编码的，不能从成功/失败的任务中学习调整
- 主题新颖性评分是简单的集合重叠计算，没有语义级比较

**建议**：
- 将 `strategy_memory` 从简单的效果计数升级为带权重的上下文-效果映射，根据实际效果定期更新
- 引入简单的多臂老虎机（multi-armed bandit）或上下文 bandit 来动态调整候选类型的探索/利用比例

### 5.3 第 1 层和第 2 层脱节（影响等级：中）

**问题**：Skill Layer 的自学习（用户触发的搜索学习）和 Conclusion Store 的数据模型设计精良，但两者之间缺乏自动化连接。

- SKILL.md 定义了完整的 subagent 输出 contract，但未发现代码将此输出自动路由到 `SelfLearningConclusionStore`
- Conclusion Store 被标注为 "Legacy"，但 Skill Layer 没有新的替代者

**建议**：在 `skill_manager_tool` 或 `skills_hub` 中增加 subagent 输出后处理——识别 `self-learning` skill 的输出，自动创建 Topic → Session → Conclusion 记录。

### 5.4 身体进化的效果验证缺失——"没坏"≠"变好了"（影响等级：中）

**问题**：替身从当前本体 Git clone 并 incremental commit，Probe 验证了"改完还能正常工作"，但从不验证改进是否真的让系统变得更好。

| Probe 检查项 | 验证的问题 | 不验证的问题 |
|-------------|-----------|-------------|
| `startup_ok` | 能启动吗？ | 启动更快了吗？ |
| `config_load_ok` | 配置能加载吗？ | — |
| `memory_path_ok` | 记忆路径可达吗？ | 记忆召回更准了吗？ |
| `tool_smoke_ok` | 工具能执行吗？ | 工具调用成功率提升了吗？ |
| `task_replay_ok` | 历史任务能回放吗？ | 回放结果比之前更好了吗？ |

- `BodyImprovementReviewService` 的评分维度（repeat_penalty、learning_freshness）评估的是改进过程而非改进结果
- 系统记录了什么被改了（git diff），验证了改完不会炸（probe），但从未在改之前跑一次基准、改之后再跑一次来量化改进效果

**建议**：
- 在改进前对 shell worktree 运行预设 benchmark suite，记录基线分数
- 改进后再次运行同一 benchmark，计算 improvement_delta，低于阈值的改进自动拒绝
- 在 Watch Window 期间收集关键运行时指标（响应延迟、任务成功率、错误率），与改进前的历史基线对比

### 5.5 缺少自主学习的量化度量框架（影响等级：中）

**问题**：无法回答"系统在过去一周学会了什么"这个基本问题。

**建议**：
- 新增 `SelfLearningMetrics` 数据模型，追踪：生成候选数/执行数/成功率、学习主题覆盖度、知识库增长率、身体改进采纳率
- 在 Supervisor UI 中暴露自主学习仪表盘

### 5.6 自主链路未系统性地强制执行 Web 学习（影响等级：中）

**问题**：工具栈完整（`web_search` / `web_extract` / `browser_*` + `learn` toolset），但从任务生成到执行的链路中缺少强制使用 Web 工具的机制。详见 §3.6。

- 自主学习任务的执行 prompt 没有类似 SKILL.md 中的搜索策略指导
- `inject_execution_prompt()` 未根据任务类型切换 toolset 或注入 Web 工具使用指令
- 学习主题源于本地用户活动元数据，系统不会主动从 Web 发现新技术趋势
- `exploratory_learning` 候选的"新颖性"评分基于本地历史而非外部知识对比

**建议**：
- 在 `build_autonomous_task_prompt()` 中为 `exploratory_learning` 类任务注入 Web 搜索指令模板（搜索关键词、优先来源、评分标准）
- 在 `inject_execution_prompt()` 中根据 `execution_policy` 切换至 `learn` toolset
- 在内生驱动中增加"Web 趋势发现"候选类型，定期搜索预设主题的最新动态
- 在 review cycle 中验证学习任务是否使用了 Web 工具、信息是否来自最新来源

## 六、与主流自学习范式的对比

| 学习范式 | VoidCube 是否有 | 实现程度 |
|----------|:---:|------|
| **LLM 驱动的探索学习** | ✅ | 核心方法——内生驱动 + API-B 判断 |
| **经验回放** | ❌ | 无——不存储和重放历史经验进行训练 |
| **强化学习（RL）** | ❌ | 无——没有 reward model 或策略梯度更新 |
| **上下文学习（In-Context Learning）** | ✅ | 依赖 LLM 的上下文窗口进行认知传递 |
| **Few-shot 学习** | ✅ | LLM 生成的提示中包含历史案例 |
| **元学习（Meta-Learning）** | ⚠️ | 有概念设计（自我就绪度评估、认知评估记忆），但实际是规则+LLM 判断 |
| **课程学习（Curriculum Learning）** | ❌ | 无——学习任务按评分排序但无难度递进 |
| **自我对弈（Self-Play）** | ❌ | 无 |
| **联邦学习** | ❌ | 不适用——单机系统 |
| **持续学习（Continual Learning）** | ⚠️ | 记忆系统支持持续积累，但认知模型本身不更新 |

## 七、结论与优先级建议

### 总体评价

VoidCube 构建了一个**架构设计领先、安全机制完善**的自主 Agent 系统。其自学习能力在"LLM Agent 自主性"这个维度上达到了较先进水平——系统能自主发现学习主题、生成改进任务、在隔离环境中执行、经过多层治理后部署。

但在"真正的机器学习"意义上——从数据中统计学习、优化策略参数、量化改进效果——系统仍然处于早期阶段。目前的自学习更准确地说是一个**以 LLM 为推理引擎、以治理规则为安全边界的自主任务生成与执行系统**，而非具备自我优化能力的学习系统。

### 优先级建议

| 优先级 | 改进项 | 预期收益 |
|--------|--------|---------|
| **P0** | 增加学习效果的量化评估——在 review cycle 中计算 improvement_score | 闭合学习闭环，让系统知道"学到了什么" |
| **P1** | 将 Skill Layer subagent 输出自动接入 Conclusion Store | 用户触发的学习也进入系统记忆 |
| **P1** | 在 Probe 阶段增加性能回归检查 | 确保身体进化是真正的改进而非退化 |
| **P2** | 策略记忆从静态查表升级为上下文 Bandit | 让自适应策略真正"适应" |
| **P2** | 新增自主学习度量仪表盘 | 可见性——让用户和系统都能评估学习进度 |
| **P3** | 引入经验回放机制 | 从历史任务中学习成功模式 |
| **P3** | 课程学习——按难度递进安排学习任务 | 提高学习效率 |
