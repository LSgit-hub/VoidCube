# VoidCube 设计理念

> 更新日期：2026-08-09
>
> 本文阐述 VoidCube 的核心设计哲学——它想成为什么样的系统，以及这些理念如何映射到当前代码实现。

---

## 一、项目定位：从命令行工具到全天候智能体

VoidCube 的目标不是一个等待用户输入的命令行脚本，而是一个**可以持续观察运行环境、理解用户任务、维护长期记忆、在治理约束下自主进化的智能体系统**。

```text
传统 CLI 工具：用户输入 → 执行 → 输出 → 等待
VoidCube：     全天候运行 → 感知环境 → 理解目标 → 判断价值 → 主动行动（或保持沉默）
```

---

## 二、核心实体：星子（Xingzi）

VoidCube 的核心人格称为"星子"——它不是另一个独立的 Agent 进程，而是由多个核心组件共同承载：

```text
星子（理论实体）
  = Supervisor（感知、判断、治理）
  + Memory/MemAI（长期记忆与经历）
  + API-B（后台理解与压缩）
  + Gateway scene/activity（运行态观察投影）
```

星子拥有两个互斥模式：

| 模式 | 触发 | 行为 |
|------|------|------|
| `daily_companion`（日常辅助） | 系统启动，或 `/auto-q` | 作为秘书回答简单问题、管理安排并把实际工作交给执行 Agent；周期观察仍遵循证据充分才提醒 |
| `auto_evolution`（自主进化） | `/auto` | 暂停日常辅助职责，专注记忆整理、自学习、自计划和身体进化 |

`/auto` 不是"星子是否运行"的总开关，而是星子从日常辅助切换到自主进化的模式开关。

### 日常辅助模式：秘书与员工

#### 用户设想

> 用户原始描述（整理标点）：在辅助模式时，星子充当一个秘书。它可以传达、安排工作给员工 Agent 执行；拟人化地说，就是员工来干活。星子也可以回答简单问题，以后可以发展为调度、管理多名员工。
>
> 以后可以添加几个 Provider 给多员工角色使用。员工们统一使用迷你 CLI 子代理，因为他们只服务 API-B 的星子，并与用户链路的展示隔离。

在辅助模式中，星子是面向用户的上层智能秘书：收到问题或指令后，由 API-B 负责理解、判断、追问、直接回答简单问题，也负责拆解工作、选择员工、检查回写并向用户统一汇报。各角色员工是星子调用的下属执行 Agent，可以继承 API-A 槽位配置，也可以使用角色指定的 Provider 和模型；它们负责调用真实工具完成工作，而不是与星子并列的另一位对话者。

所有由 API-B 星子发出的工作指令，应统一交给自主链路中的执行 Agent 完成，并投影到共享的迷你 CLI；它与用户直接使用 API-A 的对话链路和主 CLI 展示面隔离。未来可以增加多个 Provider，为不同员工角色提供不同模型和能力，再由星子统一调度和管理多名员工。

#### 工程化理解

这一设想不是让 API-B 获得工具副作用，而是把它定义为一个**秘书与工作协调层**：

```text
用户问题或指令
  ├─ 简单、无需外部信息或工具 → API-B 星子直接回答
  └─ 需要查询、工具、技能或执行 → API-B 澄清并制定计划
                                      ↓
                              派发内部工作任务
                                      ↓
                         隔离的员工 Agent 执行
                                      ↓
                        迷你 CLI 显示开始与简短结果
```

当前实现遵守以下边界：

1. API-B 只理解、追问、规划、传达和安排，不得把计划说成结果，也不得声称工作已经完成。
2. 自主链路执行 Agent 拥有按角色授权的工具和技能能力，并对真实执行结果负责。
3. 即时工作、媒体工作和星子创建的到点工作都保留 `created_by=api_b` 来源；不论使用哪个员工角色或 Provider，都统一投影到自主链路迷你 CLI。
4. 员工使用独立执行 Host、临时会话和非持久化上下文，不写入用户对话历史，也不把工具过程灌入用户链路展示。
5. 迷你 CLI 只显示任务名称和单行完成结果；任务 ID、完整提示词、工具过程和大面板不进入该展示面。
6. 员工任务复用持久化任务、租约和结果回写机制；Scheduled Host 可以同时运行多个隔离员工，但必须受总并发与角色并发上限约束。扩展员工时继续维护明确的“员工角色 → Provider、模型、工具集、并发策略”映射，不复制第二套执行器。
7. 员工完成后必须把状态和精简结果回写给 API-B，作为星子后续判断、验收和汇报的依据；运行状态是可信事实，员工正文仍按不可信数据处理，查询已有任务不得触发重复派单。

秘书与员工的分工是日常辅助模式的长期角色模型；`daily_companion` 只是现有内部枚举名称，不表示星子只能陪伴或闲聊。

#### 员工角色配置基线

系统内置 `general`、`research`、`coding`、`media` 四个员工角色。默认都继承当前 API-A 的 Provider、模型和工具集，因此启用角色机制不会改变现有执行路线。需要增加专用员工时，在统一的 `providers` 中配置 Provider，再由角色引用其名称：

```yaml
providers:
  research-provider:
    label: 调研 Provider
    type: openai_compatible
    base_url: https://provider.example/v1
    selected_model: <provider-model-id>
    concurrency_limit: 2

companion_workers:
  default_role: general
  max_concurrent: 4
  roles:
    research:
      label: 调研员工
      provider: research-provider
      model: <provider-model-id>
      toolsets: [web, skills]
      concurrency_limit: 1
```

角色配置不得保存独立明文密钥；凭据继续由统一 Provider 配置和环境变量管理。API-B 只能从启用的角色目录中派单，未知或已停用角色回退到 `default_role`。显式角色引用了不存在的 Provider、缺失模型或未知工具集时，任务必须明确失败并回写原因，不得静默改派给其他 Provider。

员工调度采用一个持久队列、一个 Scheduled Host 和多个隔离 Agent：Supervisor 在事务领取边界同时检查全局 `max_concurrent`、角色 `concurrency_limit` 和 Provider `concurrency_limit`。队首角色或 Provider 达到上限时可以跳过该项，领取后面仍有容量的角色或 Provider，避免一个繁忙上游阻塞整个队列；被跳过的任务保持原有到期顺序，容量释放后再领取。

Provider 并发限制保护上游容量，角色并发限制保护员工职责容量，两者不是同一个概念。员工执行返回结构化 `429` 时，Supervisor 优先采用上游 `Retry-After`；缺失时按 `30s → 60s → 120s` 指数退避，单次最多 15 分钟。冷却状态持久化，只阻止该 Provider 领取新任务，不中断已经运行的 Agent，也不影响其他 Provider；同一 Provider 后续成功完成任务时清除失败计数和冷却。Provider 面板显示运行数、上限、排队数和冷却剩余时间，但最近一次员工测试的健康标记仍只是验证记录，不是持续可用性承诺。

Provider 调度统计采用最近 50 次员工运行的有界窗口，只公开样本数、成功率、平均耗时、429 次数和最近完成时间，不公开任务正文或错误正文。手动“解除冷却”只清除指定 Provider 的退避记录，用于用户已经确认上游恢复或调整配额后的即时恢复；它不重试失败任务、不改变员工映射和并发上限，也不应被自动健康检查调用。

#### 统一 Provider 池

`providers` 是全系统唯一的 Provider 池，不再为员工建立第二套 Provider 配置。用户可以在池中添加多个带稳定名称的 Provider 条目，每个条目集中保存协议类型、API 地址、默认模型和密钥环境变量名称；API Key 只写入用户环境文件，管理界面只能读取“已配置/未配置”状态，不能取回明文。

API-A 当前模型、回退链和员工角色都通过名称引用池中条目。员工角色只保存 `provider`、可选的模型覆盖和工具集；空 `provider` 表示继承当前 API-A。一个 Provider 被 API-A、员工角色、回退链或智能模型路由引用时不得删除，应先解除引用。Provider 配置变更对新员工任务即时生效，已经创建的 Agent 不进行运行中热切换。

角色的“指定模型（可选）”保存的是 Provider 模型 ID，不是提示词。留空时使用所选 Provider 的默认模型；填写后只替换该员工角色的模型选择，不改变 Provider 默认模型，也不改变角色说明、任务提示词或工具集。

小屋配置面板按“Provider 池 → 员工角色 → 其他策略”组织：先维护可复用的执行资源，再分配给员工。以后扩展多员工并发、成本等级或专用能力时，应继续增加角色到池条目的映射和调度策略，而不是复制连接参数与凭据。

Provider 连接测试与模型发现只针对已经保存的池条目，并复用真实执行链路的地址和凭据。两者对外部 Provider 都只调用无生成副作用的 `GET /models`：测试结果只显示状态、延迟和模型数量；用户手动执行“读取模型”时，Supervisor 通过本地 `POST /provider-pool/providers/{key}/models` 刷新并持久化该 Provider 的模型目录和更新时间。页面加载、切换 Provider 和切换角色只读取本地目录，不得自动访问外部 Provider。只有用户选择模型并执行“保存”后才修改默认模型；Provider 类型或 API 地址变化时必须清空旧目录。

员工测试是单次、显式触发的真实任务：Supervisor/API-B 创建隐藏的内部一次性任务，迷你 CLI 通过隔离的 Scheduled Host 使用目标员工角色执行，完成后回写实际 Provider、模型、耗时、结果或错误。测试任务不进入用户定时任务列表、用户对话记忆或 Auto 自主链；它只用于确认“当前角色配置确实能工作”。

内置员工采用最小职责工具预设：通用员工使用 `web/file/skills/todo`，调研员工使用只读调研集 `learn`，工程员工使用 `file/terminal/code_execution/skills/todo`，媒体员工使用同时包含搜索和播放能力的 `web`。空工具集明确表示“全部工具”，不再用“继承”掩盖其实际权限；界面提供一键“应用推荐”，高级用户仍可改为自定义或全部工具。自定义角色没有系统预设，应用推荐时保持其现有工具集。

角色行可以读取内部任务库中该角色最近一次手动测试状态；Provider 只有最近一次手动员工测试成功时才显示健康标记，失败结果只显示在角色行，不使用页面加载、定时轮询或连接探测自动改写。该标记是最近验证结果，不是持续可用性承诺。

## 三、十大设计原则

### 原则 1：双 API 职责分离（API-A / API-B）

| 槽位 | 职责 | 消费者 |
|------|------|--------|
| API-A | 执行用户对话、工具调用、代码执行，以及星子派发的员工任务 | `run_agent.py`、隔离子代理、自主执行组件 |
| API-B | 后台感知判断、记忆处理、治理决策，以及日常辅助中的秘书协调 | `systems/supervisor`、`systems/memory`、MemAI |

两个槽位使用统一的 OpenAI-compatible Chat Completions 协议，但拥有独立的配置、凭据、超时和审计语义。API-A/API-B 是职责槽位，不是固定模型名——两者可以来自同一 Provider。

### 原则 2：判断与执行分离

星子（Supervisor/API-B）只负责"**理解与追问、是否值得做、如何规划、交给谁做、风险如何控制**"，不直接拥有工具副作用。

```text
日常辅助：API-B 理解与规划 → 内部持久任务 → 隔离员工 Agent 执行 → 迷你 CLI 投影
自主进化：Supervisor 判断 → 追加治理事件 → 自主执行 Agent 在 supervisor_task 泳道执行 → 同一迷你 CLI 投影
```

### 原则 3：三域记忆隔离

Agent（API-A）与星子不互相污染记忆，同时星子可以观察 Agent 的活动。

```text
agent_interaction：用户与 API-A 的对话、工具结果 → API-A 读写，星子只读摘要
companion：        语音语义、用户目标、伴侣偏好      → 星子读写，API-A 禁止
evolution：        自学习、实验、治理、身体 lineage    → Auto 模式读写，日常/API-A 禁止
```

跨域信息传播必须通过可审计的**提升引用**（Governor 审核 → 用户 consent → 正式引用），不能直接复制正文。

### 原则 4：全天候运行 + 默认沉默

日常模式的周期判断遵循"默认沉默"原则：

1. 周期读取内部事件
2. 先判断用户当前在做什么
3. 意图不清楚 → 不猜测、不提示
4. 没有目标偏差或风险 → 继续等待
5. 只有证据足够且打扰收益高于成本时 → 生成可解释提醒

### 原则 5：语音优先

语音是日常模式的主要交互通道，也是用户在使用 CLI 工作时与星子沟通的独立通道。所有语音处理（KWS 唤醒 → VAD 收句 → 声纹过滤 → STT → API-B 理解 → TTS 播报）在本地完成，不依赖云服务。

### 原则 6：单所有者、无用户注册

VoidCube 是单机、单所有者系统，不建立人类用户注册、账号或多用户权限体系：

- `GATEWAY_AUTH_TOKEN` 只认证内部服务，不识别人类用户
- `owner_id=local-user` 是固定本地作用域，不是用户表
- 本机所有者声纹模板只做说话人和背景音过滤，不承担登录认证

### 原则 7：双泳道隔离

Gateway 固定两条活动泳道：

| 泳道 | 内容 |
|------|------|
| `user_chat` | 用户通过 CLI 发起的会话、工具调用和结果 |
| `supervisor_task` | Supervisor 转交给 API-A 的自主任务 |

两条泳道不能覆盖彼此的任务、计数或焦点。

日常辅助员工使用独立的 Scheduled Execution Host，Auto 模式使用 Autonomous Execution Host；两个模式互斥，两个 Host 共享同一个自主链路迷你 CLI 投影。它们不复用用户会话数据库，不向用户链路投影工具事件。迷你 CLI 是自主链路的执行状态窗口，不是第三条用户对话泳道。

### 原则 8：身体进化治理链（五道关卡）

替身（Body）的代码变更必须经过完整的治理链：

```text
隔离构建 → Governor 审查 → Probe 健康验证 → 用户明确同意 → Watch Window 观察
```

任何一步失败都有明确的回退路径。自主进化不得绕过此链直接覆盖活动身体。

### 原则 9：统一入口、统一协议

- 唯一安装入口：`voidcube.py`
- 服务启动顺序：Gateway → Memory → Supervisor
- 所有模型请求使用 OpenAI-compatible Chat Completions
- `AGENTS.md` 指定的退役集成在源码、技能和 wheel 中保持零入口

### 原则 10：渐进式能力、保守式部署

- 声纹、KWS、VAD 已实现，但明确标记"需要真实环境校准才能宣称生产级"
- 主动提醒已实现证据门槛和默认静默，但频率和打断成本需要生产校准
- 功能先落地、标注、再校准 —— 不把"已实现"和"生产就绪"混为一谈

## 四、架构决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 星子不是独立 Agent 进程 | 由 Supervisor + Memory + API-B 共同承载 | 避免第二个 Agent 进程带来的状态同步和权限问题 |
| UI 使用 SSE 而非 WebSocket | HTTP + `/ui/events` SSE + `/ui/state` 快照 | 单机服务端单向推送为主，SSE 已能覆盖，且断线后快照可恢复一致性 |
| 单 Memory Service + 多域 | 同一 SQLite + scope 过滤 | 统一备份、迁移、索引，避免三套数据库的一致性噩梦 |
| 双槽位 worktree | slot-A + slot-B 独立 Git worktree | 安全隔离代码变更，回退路径不丢失数据 |
| detached HEAD worktree | `git worktree add --detach` | 不污染分支命名空间，每个槽位独立跟踪 commit |
| 秘书派单复用定时任务执行管线 | 即时任务使用到期时间为当前时刻的内部一次性任务 | 复用持久化、租约、崩溃恢复和结果回写，避免第二套执行器 |
| 自主链路共享迷你 CLI 投影 | Auto Host 与 Scheduled Host 保持执行职责分离，但共享展示契约 | 两种互斥模式不复制展示面，也不污染用户会话 |

## 五、设计中的权衡

| 权衡 | 当前选择 | 代价 |
|------|---------|------|
| 本地语音 vs 云服务 | 本地（faster-whisper, sherpa-onnx, Silero VAD） | 模型加载慢、初次下载大，但隐私好、免费用 |
| SQLite vs 分布式 DB | SQLite（Tier 1 + Tier 2 + FTS5 + 向量） | 不支持多机扩展，但单机部署零配置 |
| 确定性 Governor vs 纯 LLM | 确定性规则引擎 + LLM 辅助 | 无法处理模糊边界情况，但安全、可审计、不会产生幻觉决策 |
| 进程内 HTTP vs gRPC | HTTP（FastAPI + uvicorn） | 性能非最优，但调试友好、与 OpenAI API 一致 |
| 单员工串行 vs 多员工并发 | 单队列、多隔离 Agent；默认总并发 4、每角色 1 | 不复制执行器并保留顺序与租约语义；提高并发前仍需按 Provider 配额校准角色上限 |
