# VoidCube 替身（Body）自进化机制说明

> 更新日期：2026-07-28
> 本文档整合了替身体系的构造原理、Git 操作、生命周期管理和回退机制，方便日后查阅。

---

## 一、替身是什么

### 1.1 一句话定义

**替身（Body）是 VoidCube 整个项目代码仓库的一个完整的 Git worktree 独立副本。** 它不是 `agent/` 目录、不是 `run_agent.py`、也不是 Agent 的技能——它是所有代码在某个 Git commit 的完整快照。

### 1.2 不是什么

| 替身不是... | 实际情况 |
|-------------|---------|
| `agent/` 目录 | 替身包含 `agent/`，但也包含其他所有目录 |
| `run_agent.py` | 替身包含它，但不止于此 |
| `tools/` 工具集 | 替身包含全部工具代码，但不是"工具配置" |
| Agent 的技能 (skills) | 技能代码也在 worktree 中，但替身比技能大得多 |
| Agent 的配置 | 配置在 `config.yaml` 中，也在 worktree 里 |
| **整个 VoidCube 项目的 Git 快照** | **✅ 这就是替身** |

### 1.3 替身包含什么

Worktree 物化时从 `source_root`（VoidCube 项目根目录）创建完整副本：

```
VoidCube/                 ← source_root（整个项目）
├── voidcube.py           ← 唯一启动入口
├── cli.py                ← CLI 交互主逻辑
├── run_agent.py          ← AIAgent 主循环
├── agent/                ← API-A Agent 核心模块
├── tools/                ← 工具注册/安全/审批/执行
├── systems/              ← Gateway/Memory/Supervisor/Voice/Execution
├── VoidCube_cli/         ← CLI 包
├── VoidCube_core/        ← 底层基础设施
├── Mem/src/memai/        ← MemAI 领域包（例外：不跟随 Body 切换）
├── tests/                ← 全套测试
├── plugins/              ← 插件
├── skills/               ← 可加载技能
├── presets/              ← 部署预设
└── ...
```

**例外**：`Mem/src/memai/` 代码固定从共享仓库加载，不跟随 Body 槽位切换（架构基线第 17 条）。

### 1.4 替身和运行中进程的关系

- 当前运行中的 Agent 进程，其 Python 模块从 `pip install -e .` 的安装位置加载（即 `source_root` 本身），**不会动态切换 worktree**。
- 替身切换通过更新 `active.json` 指针实现，**新代码在下次启动时生效**。
- 子代理（delegate_task）绑定 worktree 作为 `cwd`/`terminal_cwd`，在当前会话中直接操作 worktree 中的文件。

## 二、替身架构：双槽位布局

### 2.1 物理布局

```
{state_root}/
├── registry.json          # 全局角色分配 (active / shell / retired)
├── active.json            # 当前活跃替身启动指针 (BodyLaunchTarget)
└── slots/
    ├── slot-A/
    │   ├── meta.json      # 槽位元数据 (BodySlotMeta)
    │   ├── worktree/      # Git worktree — 独立代码副本
    │   │   └── worktree-origin.json  # 物化来源清单
    │   ├── runtime/       # 运行时数据 (state, tmp, cache)
    │   │   └── slot-runtime.json
    │   └── logs/          # 独立日志目录
    └── slot-B/
        ├── meta.json
        ├── worktree/
        ├── runtime/
        └── logs/
```

每个槽位拥有完全独立的 worktree、runtime 和 logs，互不干扰。

### 2.2 角色分配

全局 `registry.json` 维护三个角色（同一时刻每个角色只有一个槽位）：

| 角色 | 含义 | 状态要求 |
|------|------|---------|
| `active` | 当前正在运行的替身 | `active` |
| `shell` | 空闲的候选槽位，用于接收改进 | `shell`（必须） |
| `retired` | 被替换的旧替身，Watch Window 期间保留 | `retired` |

**默认初始化**：slot-A = active，slot-B = shell。

### 2.3 槽位元数据模型 (`BodySlotMeta`)

| 字段分类 | 字段名 |
|---------|--------|
| **身份** | `slot_id`, `body_state`, `body_version`, `generation` |
| **路径** | `worktree_path`, `runtime_path`, `logs_path` |
| **来源追踪** | `build_from_commit`, `source_branch`, `source_commit`, `materialized_from` |
| **候选构建** | `candidate_branch`, `candidate_commit` |
| **激活状态** | `active_ref`, `active_commit` |
| **回退信息** | `rollback_ref`, `rollback_commit` |
| **健康度** | `health_score`, `health_history`, `current_healthy_commit`, `previous_healthy_commit`, `improvement_count` |
| **用户同意** | `switch_consent_request`, `switch_consent_requested_at`, `switch_consent_approved_at` |
| **变更追踪** | `diff_summary`, `changed_files`, `last_probe_result` |
| **回退进行中** | `rollback_in_progress`, `last_improvement_rollback` |

## 三、Git 操作原理

### 3.1 Worktree 物化

核心命令（[body_registry.py](systems/body_registry.py) `_materialize_git_worktree`）：

```bash
# 等价于
git worktree add --detach --force {target_root} {source_commit}
```

流程：
1. **检查目标状态**：如果已有注册 worktree 且有内容但未设 `clear_existing`，且当前 HEAD ≠ source_commit，则报错
2. **移除旧 worktree**：`git worktree remove --force {target_root}`（如果已注册）
3. **清理目录**：如果目录已存在但未注册为 worktree，直接清空
4. **`git worktree prune`**：清理已失效的 worktree 引用
5. **创建隔离 worktree**：detached HEAD 模式，不绑定分支
6. **验证隔离性**：确认 `git rev-parse --show-toplevel` 等于 target_root 自身

### 3.2 非 Git 后备

如果 source_root 不是 Git 仓库，退化为 `shutil.copytree`（`_sync_directory`），跳过以下目录：

```python
DEFAULT_SLOT_COPY_IGNORE_NAMES = (
    ".git", ".body-active.json", ".body-slots",
    ".body-registry.json", ".pytest_cache", ".pytest_tmp",
    ".mypy_cache", ".venv", "__pycache__",
    ".soul-runtime", "cache", "logs", "sessions", "state",
)
```

### 3.3 Commit 追踪方法

| 方法 | Git 命令 | 用途 |
|------|---------|------|
| `_git_head_for_path(path)` | `git rev-parse HEAD` | 获取任意路径的 HEAD SHA |
| `_git_branch_for_path(path)` | `git branch --show-current` | 获取当前分支名 |
| `_git_head_for_isolated_worktree(path)` | 先验证 `--show-toplevel == path`，再 `rev-parse HEAD` | 获取隔离 worktree 的 HEAD |
| `_git_changed_files_for_path(path, base, candidate)` | `git diff --name-only {base} {candidate}` | 计算两个 commit 间的变更文件 |

### 3.4 Commit 记录时机

```
初始化 (initialize_layout):
  active_commit ← git rev-parse HEAD (worktree)
  current_healthy_commit ← 同上

标记候选 (mark_candidate):
  source_commit    ← git rev-parse HEAD
  candidate_commit ← build_from_commit 或 source_commit
  rollback_commit  ← source_commit (作为回退目标)
  changed_files    ← git diff rollback_commit..candidate_commit

激活 (activate_slot):
  active_commit ← candidate_commit 或 build_from_commit 或 git rev-parse HEAD
```

### 3.5 替身改进时 Agent 如何操作 Git

Agent 在 worktree 中完成代码编辑后，自主执行器通过 git diff 收集变更并提交 `BodyImprovementReport`：

```python
# 收集变更
git diff --name-only {baseline_head}..HEAD    # → changed_files
git diff --stat {baseline_head}..HEAD          # → diff_summary

# 提交改进报告到 Supervisor
POST /v1/body/improvement-report
{
    "slot_id": "...",
    "baseline_commit": "...",
    "commit_hash": "...",
    "diff_summary": "...",
    "changed_files": [...],
    "improvement_description": "..."
}
```

## 四、替身状态机与生命周期

### 4.1 状态转换图

```
               ┌─────────┐
               │  shell  │  ← 初始化/回收后的空闲槽位，可接受新改进
               └────┬─────┘
                    │ mark_candidate()
                    ▼
              ┌───────────┐
              │ candidate │  ← 代码变更已提交，等待 probe
              └─────┬──────┘
                    │ start_probe() (Governor 批准 candidate→probe)
                    ▼
              ┌────────┐
              │ probe  │  ← 接受五类健康检查
              └───┬─────┘
                  │ probe passed?
                  ├── No  → abandon_candidate() → shell
                  ▼ Yes
    ┌─────────────────────────┐
    │ awaiting_user_consent   │  ← 等待本机所有者明确同意
    └───────────┬─────────────┘
                │ 用户同意?
                ├── No  → abandon_candidate() → shell
                ▼ Yes
           ┌─────────┐
           │ active  │  ← 新的活跃替身，启动 Watch Window
           └────┬─────┘
                │ Watch Window 通过 → recycle_retired_slot() → shell
                │ Watch Window 失败 → rollback → 恢复 retired → active
                ▼
           ┌─────────┐
           │ retired │  ← 旧替身，Watch Window 期间保留
           └─────────┘
                │ 可重新激活 (restore_retired_slot)
                │ 或回收为 shell (recycle_retired_slot)
```

### 4.2 合法状态转换表

```python
ALLOWED_STATE_TRANSITIONS = {
    "shell":                  {"candidate"},
    "candidate":              {"probe", "shell"},
    "probe":                  {"awaiting_user_consent", "shell"},
    "awaiting_user_consent":  {"shell"},
    "active":                 {"retired"},
    "retired":                {"active", "shell"},
}
```

## 五、替身升级与激活完整流程

整个升级流程由 `BodyUpgradeExecutionAdapter.execute_body_upgrade` 驱动，分为 6 个阶段：

### Stage 1: 准备工作区
```
prepare_slot_workspace(shell_slot)
  → 从 active 槽位或指定源物化一个新的 worktree
  → 创建独立的 runtime/ 和 logs/
```

### Stage 2: 标记候选
```
mark_candidate(shell_slot)
  → 状态: shell → candidate
  → 记录 source_commit, candidate_commit, rollback_commit
  → 计算 git diff 变更文件列表
```

### Stage 3: Governor 审查 (candidate → probe)
```
GovernorRequest(event_type="health_review_request", target_transition="candidate_to_probe")
  → GovernorDecisionEngine.evaluate() 检查 build_complete 证据
  → 通过: issue_probe_lease → start_probe() → 状态变为 probe
```

### Stage 4: 执行 Probe（五类健康检查）

| 检查项 | 说明 |
|--------|------|
| `startup_ok` | 替换身能否正常启动 |
| `config_load_ok` | 配置能否正常加载 |
| `memory_path_ok` | 记忆路径是否可达 |
| `tool_smoke_ok` | 工具是否能正常执行 |
| `task_replay_ok` | 历史任务能否回放 |

**Probe 失败** → `abandon_candidate()` → 工作区被清空并重置为 shell。

### Stage 5: Governor 切换审查 (probe → awaiting_user_consent)
```
GovernorRequest(event_type="switch_request")
  → Governor 检查 probe_passed == True
  → 通过: await_user_consent() → 状态: probe → awaiting_user_consent
  → 在 Supervisor UI 的提升面板显示为待确认候选
```

### Stage 6: 用户同意 + 激活
```
用户通过 UI 点击"同意"
  → confirm_body_switch(approved=True)
  → Governor 再次审查 (target_transition="probe_to_active")
  → activate_slot():
      - 旧 active → retired (记录 retired_at)
      - 新 slot → active (generation += 1)
      - 启动 Watch Window (默认 300 秒)
      - 更新 active.json 指针
```

**用户拒绝** → `abandon_candidate()` → 槽位回到 shell。

## 六、回退机制（两种类型）

### 6.1 Watch Window 回退（激活后的安全回退）

**触发条件**：新激活的替身在 Watch Window 期间 Agent 不健康。

**操作**：无需 Git 操作——只是 registry 角色互换。
```
旧 retired slot → restore_retired_slot() → active（重新激活）
新 active slot → retired
```

原 retired 槽位的 worktree 完整保留，随时可恢复。回退后停止失败槽位的 agent，切换到恢复后的槽位。

### 6.2 替身改进回退（非 active 槽位的 Git 级回退）

**触发条件**：shell/candidate/probe 槽位的改进被检测为破坏性变更（regression、probe 失败、destructive change）。

**核心方法**：[`restore_previous_healthy_commit`](systems/body_registry.py)

**完整流程**：

```
1. 前置验证:
   - 不能是 active/retired 状态 (它们使用 Watch Window 协议)
   - 必须有 previous_healthy_commit 记录
   - worktree 必须是隔离的 git worktree
   - worktree 必须干净 (git status --porcelain 无输出)

2. 安全检查:
   - 当前 HEAD 必须匹配 expected_current_commit
   - target_commit 必须存在 (git rev-parse --verify)
   - target != current (不能回退到同一 commit)
   - target 必须是 current 的祖先 (git merge-base --is-ancestor)

3. Git 执行:
   git reset --hard {previous_healthy_commit}
   → 验证恢复后的 HEAD == target_commit

4. 状态更新:
   - body_state → probe, lease = "rollback_probe"
   - candidate_commit = target_commit
   - 记录 rollback_in_progress

5. 重新 Probe:
   → 通过: finalize → body_state → shell, 回到可用池
   → 失败: finalize → lease = "rollback_probe_failed", 需人工介入
```

### 6.3 回退对比总结

| 类型 | 适用场景 | Git 操作 | 状态变化 |
|------|---------|---------|---------|
| Watch Window 回退 | active 槽位激活后不健康 | **无**（角色互换） | active ↔ retired |
| 改进回退 | 非 active 槽位的破坏性代码变更 | **`git reset --hard`** | probe → probe(rollback) → shell |

## 七、Governor（治理引擎）决策表

`GovernorDecisionEngine` 是替身所有状态变更的审批中枢。它使用确定性的规则引擎，在低置信度/中高风险时可选择性地咨询 LLM（`LLMGovernorReasoner`），但 LLM 意见不覆盖确定性决策。

| 事件类型 | 决策逻辑 | 输出动作 |
|---------|---------|---------|
| `body_upgrade_request` | 升级提案 → 要求更多证据 | `record_evolution_event` |
| `health_review_request` (candidate→probe) | build_complete? | `issue_probe_lease` |
| `health_review_request` (probe→shell) | probe_failed? | `abandon_candidate` |
| `health_review_request` (probe→active) | probe_passed + user_consent? | `activate_slot` |
| `switch_request` | probe_passed? → 等待用户同意 | `await_user_consent` |
| `rollback_request` | 有失败信号? → 恢复 retired | `restore_retired_slot` |
| `improvement_rollback_request` | 有破坏/回归/失败信号? 且非 active/retired? | `restore_healthy_commit` (git reset --hard) |
| `post_switch_review` | watch_window_passed? + slot=retired? | `recycle_retired_slot` |
| `switch_suggestion` | 健康分超阈值 + improvement≥1? | `issue_probe_lease` |
| `switch_consent_rejection` | 用户明确拒绝 → 放弃候选 | `abandon_candidate` |

## 八、Watch Window（观察窗口）

新替身激活后，旧替身不会立即被回收，而是进入一个观察期：

```python
WatchWindowState:
    status: "inactive" → "active" → "completed"
    expires_at: 默认 300 秒（5 分钟）
    stable_window_days: 3
    stable_health_checks: 3
```

**后台轮询循环**（每秒一次）：
1. 检查活跃 Agent 的健康状态
2. **健康 + 过期** → 通过 → `recycle_retired_slot()`（旧槽位回到 shell）
3. **不健康** → 触发 `rollback_required` → `restore_retired_slot()`（回退到旧槽位）

## 九、替身被如何实际使用

### 9.1 Agent 改进自己的代码

当 Agent 收到 `body_improvement` 任务时，提示词指示：
- "Edit the shell body code directly"
- "Worktree path: {worktree_path}"
- "Commit the shell worktree changes before reporting completion"

Agent 在 worktree 中修改文件 → git commit → 提交 `BodyImprovementReport`。

### 9.2 子代理绑定 worktree

`delegate_task` 工具可以将 worktree 绑定为子 Agent 的工作目录：
```python
child.terminal_cwd = worktree_path   # 终端命令在此执行
child.cwd = worktree_path            # 文件操作在此执行
```

### 9.3 启动时选择替身

`voidcube.py` 启动时读取 `active.json` → `BodyLaunchTarget` → 获取正确的 worktree 路径。

## 十、关键设计约束

1. **至少需要两个槽位** — `len(slot_ids) >= 2`
2. **同一时刻只有一个 active** — registry 保证 `active_slot` 是单值
3. **shell 状态必须是 shell** — 否则抛 ValueError
4. **不能自己物化自己** — 拒绝 `source_slot_id == slot_id`
5. **任何代码变更必须通过治理链** — 不允许直接覆盖 active 槽位
6. **Git worktree 必须是隔离的** — `git rev-parse --show-toplevel` 必须等于 worktree_path 自身
7. **回退前 worktree 必须干净** — `git status --porcelain` 不能有输出
8. **MemAI 代码固定从仓库加载** — 不跟随 Body 槽位切换
9. **用户同意是不可跳过的** — 身体切换必须经过 `awaiting_user_consent` → 用户明确同意 → `activate_slot`
10. **自主进化不得绕过治理链** — 不能绕过 candidate/probe/consent/watch/rollback 直接覆盖活动身体

## 十一、架构全景图

```
                    星子(Supervisor) 内生驱动 / 自学习
                           │
                           ▼ 生成改进任务
              ┌────────────────────────┐
              │  AutonomousChainStore  │  任务投影
              └───────────┬────────────┘
                          │ API-A 执行改进
                          ▼
              ┌────────────────────────┐
              │  BodyImprovementReport │  Agent 提交改进
              └───────────┬────────────┘
                          │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
   prepare_slot    mark_candidate    Governor审查
   (git worktree)  (记录commit)     (确定引擎+LLM)
         │                │                │
         └────────────────┼────────────────┘
                          ▼
                      run_probe
               (5项健康检查, 全部通过)
                          │
                 ┌────────┴────────┐
                 ▼                 ▼
            probe通过          probe失败
                 │                 │
                 ▼                 ▼
        await_user_consent   abandon_candidate
                 │           (清空worktree→shell)
          ┌──────┴──────┐
          ▼              ▼

          │              │
          ▼              ▼

      新→active,
      启动Watch Window)
          │
```
