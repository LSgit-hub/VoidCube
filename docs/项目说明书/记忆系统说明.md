# VoidCube 记忆系统说明

> 更新日期：2026-07-28
>
> 本文档说明 VoidCube 长期记忆系统的架构、三域隔离方案、召回机制和跨域提升引用。

---

## 一、记忆系统概览

VoidCube 的记忆体系不是简单的聊天记录保存，而是一个**分层、分域、可审计**的长期记忆系统：

```text
┌─────────────────────────────────────────────────────────────┐
│                      Memory Service (端口 6001)               │
│                                                             │
│  ┌─────────────────┐  ┌──────────────┐  ┌───────────────┐  │
│  │ Tier 1 (原始)    │  │ Tier 2 (压缩)│  │ Profile (事实) │  │
│  │ sessions/turns   │  │ MemAI Event  │  │ 显式捕获/撤销  │  │
│  │ archive          │  │ Scene/Arc    │  │ tombstone      │  │
│  └────────┬────────┘  └──────┬───────┘  └───────┬───────┘  │
│           │                  │                   │          │
│           └──────────────────┼───────────────────┘          │
│                              │                              │
│                    ┌─────────▼─────────┐                    │
│                    │   混合召回 (recall) │                    │
│                    │  Tier1+Tier2+      │                    │
│                    │  Profile+Archive   │                    │
│                    └─────────┬─────────┘                    │
│                              │                              │
│              ┌───────────────┼───────────────┐              │
│              ▼               ▼               ▼              │
│      ┌──────────┐   ┌──────────────┐   ┌──────────┐       │
│      │ 词法索引  │   │  语义索引     │   │  备份    │       │
│      │ SQLite   │   │  向量嵌入     │   │  轮转    │       │
│      │ FTS5     │   │  (可选)       │   │  导出    │       │
│      └──────────┘   └──────────────┘   └──────────┘       │
└─────────────────────────────────────────────────────────────┘
```

**最短调用链**：`AIAgent → mem Provider → Gateway /api/mem/* → Memory Service → MemAI`

---

## 二、Tier 1：原始会话存储

| 存储内容 | 说明 |
|---------|------|
| sessions | 会话元数据（创建时间、模式、状态） |
| turns | 每轮对话的消息、工具调用、结果 |
| archive | 已关闭会话的归档 |

- 使用 SQLite + WAL 模式（Schema v6）
- 保存近期原始对话，供 Agent 上下文注入
- Tier 1 → Tier 2 通过质量门禁压缩

---

## 三、Tier 2：MemAI 结构化记忆

MemAI（`Mem/src/memai/`）实现了 **Chronicle Scholar LM** 设计，将原始对话转化为结构化记忆：

| 结构 | 含义 |
|------|------|
| **Event** | 单一事实/事件（带时间戳、来源、域） |
| **Scene** | 一组语义相关的 Events（时间段 + 主题） |
| **Arc** | 跨场景的情节线（目标进展、关系演变） |
| **Epoch** | 大时间跨度的历史分段（人生阶段） |

MemAI 提供独立的 CLI 工具：
```bash
memai ingest     # 从对话提取结构化记忆
memai query      # 时间优先的混合查询
memai maintain   # 压缩、衰减、修订
memai benchmark  # 多 Fixture 评分
```

## 四、三域记忆隔离

### 4.1 为什么需要三域隔离

三个容易混淆的概念必须分开：

1. Agent（API-A）的对话记忆 ≠ 星子的私人对话
2. Auto 模式的自言自语和学习 ≠ 日常伴侣的知识
3. 跨域信息不能直接复制——必须通过可审计的引用

### 4.2 三个域

所有读写按 `owner_id + workspace_id + memory_domain` 过滤，外加 Gateway 注入的 actor 权限：

| memory_domain | 内容 | 写入者 | 读取者 |
|---------------|------|--------|--------|
| `agent_interaction` | 用户与 API-A 的对话、工具结果、任务事实 | AIAgent | AIAgent；日常星子只读摘要 |
| `companion` | 语音语义、提醒结果、用户目标、伴侣偏好 | 日常星子 | 日常星子；API-A 禁止 |
| `evolution` | Auto 模式的自学习、计划、实验、治理、身体 lineage | Auto 星子 | Auto 星子、Governor；日常和 API-A 禁止 |

### 4.3 读写矩阵

| 调用方 | `agent_interaction` | `companion` | `evolution` |
|--------|---------------------|-------------|-------------|
| API-A 用户会话 | 读写 | ❌ 禁止 | ❌ 禁止 |
| 星子日常模式 | 只读（按目标/近期筛选） | 读写 | ❌ 禁止 |
| 星子 Auto 模式 | 只读冻结 evidence packet | ❌ 禁止 | 读写 |
| Memory 维护 | 按域独立压缩/衰减 | 按域独立 | 按域独立 |
| Governor/Execution | ❌ 禁止 | ❌ 禁止 | 读取获批任务和 lineage |

### 4.4 域隔离的实现方式

- **不是**三套数据库 — 同一 SQLite + scope 过滤
- **不是**表前缀 — 所有表统一结构，按 `memory_domain` 列过滤
- Gateway 注入 `memory_actor`：API-A session = `api_a`，Supervisor 服务 = `stellar_companion`（可临时使用 `stellar_auto` 或 `governor`）
- 客户端正文中的 actor 会被丢弃并覆盖

### 4.5 压缩规则

- Tier 1 → Tier 2 只能在**同一 domain 内**压缩，禁止跨域自动聚类
- `companion` 保存用户目标和偏好，不保存 API-A 完整工具输出
- `evolution` 保存任务和实验，不保存实时语音

## 五、跨域提升引用（Promotion）

### 5.1 为什么需要提升引用

Auto 模式发现的重要结论（如用户偏好、改进效果）在默认情况下对日常星子不可见。提升引用是唯一的跨域信息传播通道——不允许直接复制正文。

### 5.2 提升流程

```text
Auto 结论 (evolution domain)
  → Governor 确认来源、方向、理由
  → memory_promotion_candidates（awaiting_user_consent）
  → 本机所有者通过 UI 明确同意 / 拒绝
       ├─ 同意：同一 SQLite 事务创建 active memory_promotion_ref
       └─ 拒绝：候选标记为 rejected，不创建引用
  → 日常 companion recall 只解引用 active memory_promotion_ref
```

### 5.3 允许的提升方向

| 来源 | 目标 | 用途 |
|------|------|------|
| `agent_interaction` | `companion` | 将已确认的用户目标提升为伴侣知识 |
| `evolution` | `companion` | 将 Auto 结论提升为日常伴侣可用知识 |

**禁止方向**：
- `companion → agent_interaction`（语音隐私不能泄露给 API-A）
- 任何域 `→ evolution`（实时用户内容不能污染 Auto）

### 5.4 关键规则

- 只有 `governor` 和 `memory_maintenance` 可以提出候选
- 候选是否生效必须由本机所有者明确选择
- 同一来源、方向不能重复创建 pending 候选
- 源记忆删除时，active 引用被撤销，pending 候选被拒绝
- `local-owner` 是 consent 审计值，不是账号或登录身份

## 六、召回机制

### 6.1 混合召回

`recall.py` 从多个来源提取并排序：

1. **Tier 1**：近期原始对话 turns
2. **Tier 2**：MemAI 结构化记忆（Event/Scene/Arc）
3. **Profile**：显式用户事实
4. **Archive**：已归档历史会话

### 6.2 排序与过滤

- 相关性排序（语义 + 词法匹配）
- 时间衰减（越近越重要）
- 跨域去重
- 动态权重（对话阶段、用户目标相关性）
- 字符预算控制（默认 8000 字符）

### 6.3 索引体系

| 索引 | 技术 | 用途 |
|------|------|------|
| 词法索引 | SQLite FTS5 | 关键词全文搜索 |
| 语义索引 | 向量嵌入（可选） | 语义相似度搜索 |
| Profile 索引 | 谓词倒排 | 用户事实精确匹配 |

---

## 七、Profile（用户事实）管理

`profile_capture.py` 和 `profile_store.py` 提供显式事实的保守捕获：

- 只捕获用户**明确陈述**的事实（不推断）
- `supersedes` 链：新事实覆盖旧事实
- `revoke`：带时间戳的撤销
- `tombstone`：已删除事实的审计记录
- 版本化存储，支持回滚

---

## 八、备份与恢复

- SQLite 统一备份（`backup.py`）
- 轮转策略（保留最近 N 份）
- 三域数据在同一备份中，恢复时保持域隔离
- 跨域提升候选表和正式引用表随备份导出

---

## 九、治理事件存储

- `GovernanceEventRepository`：所有治理决策的权威记录
- `mem_governance.jsonl`：`memory_domain=evolution` 显式标注
- 旧记录由原子迁移补齐 domain 字段
- `AutonomousChainStore` 是可重建投影，治理真相在 MemAI 事件仓库

## 十、记忆 API 端点

所有端点通过 Gateway `/api/mem/*` 代理，按 actor 权限过滤：

| 端点 | 用途 |
|------|------|
| `/api/mem/recall` | 混合召回（Tier1 + Tier2 + Profile + Archive） |
| `/api/mem/sessions` | 会话管理 |
| `/api/mem/turns` | 回合记录 |
| `/api/mem/compressed` | 压缩记忆 CRUD |
| `/api/mem/profile` | 用户事实管理 |
| `/api/mem/promotion-candidates` | 跨域提升候选管理 |
| `/api/mem/promotions` | 正式提升引用审计 |
| `/api/mem/backup` | 备份触发 |
| `/api/mem/governance` | 治理事件查询 |

---

## 十一、生产环境安全要求

> ⚠️ 三域记忆和 actor 注入已贯穿全链路，但**生产环境必须配置随机 `GATEWAY_AUTH_TOKEN`**，否则注册接口处于本机开发模式——任何本机进程都能伪造 actor。
