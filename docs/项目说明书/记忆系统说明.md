# VoidCube 记忆系统说明

> 更新日期：2026-08-04
>
> 本文档说明 VoidCube 长期记忆系统的架构、三域隔离方案、召回机制、跨域提升引用，以及近期的增强：**LLM 提取默认化+缓存**、时间感知召回、实体图检索、双时态 as-of 查询与压缩质量仪表盘。

---

## 一、记忆系统概览

VoidCube 的记忆体系不是简单的聊天记录保存，而是一个**分层、分域、可审计**的长期记忆系统：

```text
┌─────────────────────────────────────────────────────────────┐
│                      Memory Service (端口 6001)               │
│                                                             │
│  ┌─────────────────┐  ┌──────────────┐  ┌───────────────┐  │
│  │ Tier 1 (原始)    │  │ Tier 2 (压缩)│  │ Profile (事实) │  │
│  │ sessions/turns   │  │ MemAI Event  │  │ 显式捕获/撤销  │  │
│  │ archive          │  │ Scene/Arc    │  │ tombstone      │  │
│  └────────┬────────┘  └──────┬───────┘  └───────┬───────┘  │
│           │                  │                   │          │
│           └──────────────────┼───────────────────┘          │
│                              │                              │
│                    ┌─────────▼─────────┐                    │
│                    │   混合召回 (recall) │                    │
│                    │  Tier1+Tier2+      │                    │
│                    │  Profile+Archive   │                    │
│                    └─────────┬─────────┘                    │
│                              │                              │
│              ┌───────────────┼───────────────┐              │
│              ▼               ▼               ▼              │
│      ┌──────────┐   ┌──────────────┐   ┌──────────┐       │
│      │ 词法索引  │   │  语义索引     │   │  实体图  │       │
│      │ SQLite   │   │  向量嵌入     │   │  共现边  │       │
│      │ FTS5     │   │  (可选)       │   │  多跳扩展│       │
│      └──────────┘   └──────────────┘   └──────────┘       │
└─────────────────────────────────────────────────────────────┘
```

**最短调用链**：`AIAgent → mem Provider → Gateway /api/mem/* → Memory Service → MemAI`

> 召回引擎在词法/语义之上还叠加了两个维度：**时间感知**（按查询中的时间词解析窗口、按时间契合度加权）与**实体图扩展**（按实体共现边做一跳多跳召回）。详见第六节。

## 二、Tier 1：原始会话存储

| 存储内容 | 说明 |
|---------|------|
| sessions | 会话元数据（创建时间、模式、状态） |
| turns | 每轮对话的消息、工具调用、结果 |
| archive | 已关闭会话的归档 |

- 使用 SQLite + WAL 模式（Schema v6）
- 保存近期原始对话，供 Agent 上下文注入
- Tier 1 → Tier 2 通过质量门禁压缩

---

## 三、Tier 2：MemAI 结构化记忆

MemAI（`Mem/src/memai/`）实现了 **Chronicle Scholar LM** 设计，将原始对话转化为结构化记忆：

| 结构 | 含义 |
|------|------|
| **Event** | 单一事实/事件（带时间戳、来源、域） |
| **Scene** | 一组语义相关的 Events（时间段 + 主题） |
| **Arc** | 跨场景的情节线（目标进展、关系演变） |
| **Epoch** | 大时间跨度的历史分段（人生阶段） |

MemAI 提供独立的 CLI 工具：
```bash
memai ingest     # 从对话提取结构化记忆
memai query      # 时间优先的混合查询
memai maintain   # 压缩、衰减、修订
memai benchmark  # 多 Fixture 评分
```

> **LLM 提取默认化**：Tier 1 → Tier 2 压缩与记忆升级默认使用 LLM 提取（取 `memory.llm.roles.extraction` / `roles.summarization` 角色，未配置时回落到默认模型），仅在无 API key 时降级为启发式/机械路径。LLM 结果按 (task, model, 输入哈希) 缓存到 `mem_llm_cache` 表，同一批对话被重复压缩、同一记忆被重复升级时直接命中缓存，避免重复计费。

## 四、三域记忆隔离

### 4.1 为什么需要三域隔离

三个容易混淆的概念必须分开：

1. Agent（API-A）的对话记忆 ≠ 星子的私人对话
2. Auto 模式的自言自语和学习 ≠ 日常伴侣的知识
3. 跨域信息不能直接复制——必须通过可审计的引用

### 4.2 三个域

所有读写按 `owner_id + workspace_id + memory_domain` 过滤，外加 Gateway 注入的 actor 权限：

| memory_domain | 内容 | 写入者 | 读取者 |
|---------------|------|--------|--------|
| `agent_interaction` | 用户与 API-A 的对话、工具结果、任务事实 | AIAgent | AIAgent；日常星子只读摘要 |
| `companion` | 语音语义、提醒结果、用户目标、伴侣偏好 | 日常星子 | 日常星子；API-A 禁止 |
| `evolution` | Auto 模式的自学习、计划、实验、治理、身体 lineage | Auto 星子 | Auto 星子、Governor；日常和 API-A 禁止 |

### 4.3 读写矩阵

| 调用方 | `agent_interaction` | `companion` | `evolution` |
|--------|---------------------|-------------|-------------|
| API-A 用户会话 | 读写 | ❌ 禁止 | ❌ 禁止 |
| 星子日常模式 | 只读（按目标/近期筛选） | 读写 | ❌ 禁止 |
| 星子 Auto 模式 | 只读冻结 evidence packet | ❌ 禁止 | 读写 |
| Memory 维护 | 按域独立压缩/衰减 | 按域独立 | 按域独立 |
| Governor/Execution | ❌ 禁止 | ❌ 禁止 | 读取获批任务和 lineage |

### 4.4 域隔离的实现方式

- **不是**三套数据库 — 同一 SQLite + scope 过滤
- **不是**表前缀 — 所有表统一结构，按 `memory_domain` 列过滤
- Gateway 注入 `memory_actor`：API-A session = `api_a`，Supervisor 服务 = `stellar_companion`（可临时使用 `stellar_auto` 或 `governor`）
- 客户端正文中的 actor 会被丢弃并覆盖

### 4.5 压缩规则

- Tier 1 → Tier 2 只能在**同一 domain 内**压缩，禁止跨域自动聚类
- `companion` 保存用户目标和偏好，不保存 API-A 完整工具输出
- `evolution` 保存任务和实验，不保存实时语音

## 五、跨域提升引用（Promotion）

### 5.1 为什么需要提升引用

Auto 模式发现的重要结论（如用户偏好、改进效果）在默认情况下对日常星子不可见。提升引用是唯一的跨域信息传播通道——不允许直接复制正文。

### 5.2 提升流程

```text
Auto 结论 (evolution domain)
  → Governor 确认来源、方向、理由
  → memory_promotion_candidates（awaiting_user_consent）
  → 本机所有者通过 UI 明确同意 / 拒绝
       ├─ 同意：同一 SQLite 事务创建 active memory_promotion_ref
       └─ 拒绝：候选标记为 rejected，不创建引用
  → 日常 companion recall 只解引用 active memory_promotion_ref
```

### 5.3 允许的提升方向

| 来源 | 目标 | 用途 |
|------|------|------|
| `agent_interaction` | `companion` | 将已确认的用户目标提升为伴侣知识 |
| `evolution` | `companion` | 将 Auto 结论提升为日常伴侣可用知识 |

**禁止方向**：
- `companion → agent_interaction`（语音隐私不能泄露给 API-A）
- 任何域 `→ evolution`（实时用户内容不能污染 Auto）

### 5.4 关键规则

- 只有 `governor` 和 `memory_maintenance` 可以提出候选
- 候选是否生效必须由本机所有者明确选择
- 同一来源、方向不能重复创建 pending 候选
- 源记忆删除时，active 引用被撤销，pending 候选被拒绝
- `local-owner` 是 consent 审计值，不是账号或登录身份

## 六、召回机制

### 6.1 混合召回

`recall.py` 从多个来源提取并排序：

1. **Tier 1**：近期原始对话 turns
2. **Tier 2**：MemAI 结构化记忆（Event/Scene/Arc）
3. **Profile**：显式用户事实
4. **Archive**：已归档历史会话
5. **实体图扩展**：查询命中已知实体时，补充其共现实体的关联记忆（见 6.4）

### 6.2 排序与过滤

- 词法 + 语义相关性排序（FTS5 trigram / 余弦相似度）
- **时间契合度（temporal fit）**：查询带显式时间窗口时，按记忆与窗口的重叠率加权（整段覆盖=1.0，点记录落在窗内=1.0）
- **结构相关性**：同分时按层级 `Epoch > Arc > Scene > Event > 原始记录` 优先，落实"紧凑弧线优于事件堆"
- 时间衰减（越近越重要）
- 跨域去重（shingle/Jaccard + per-session 上限）
- 动态权重（event_kind、pinned/hidden、citation_count）
- 用户反馈调节（relevant/irrelevant/outdated/incorrect）
- 字符预算控制（默认 8000 字符）
- 否定子句过滤、概念同义扩展（中英）

### 6.3 时间感知召回

`build_recall_plan` 从查询文本解析时间窗口，`temporal_intent ∈ {explicit, implicit, none}`：

| 时间意图 | 触发词 | 行为 |
|---------|--------|------|
| `explicit` | 今天/昨天、本周/上周、本月/上个月、ISO 日期（`2026-03` 等） | 过滤 + 时间契合度加分 |
| `implicit` | 最近/近期/recent（30 天窗）、历史/history（不设窗） | 仅过滤，不加分 |
| `none` | 无时间词 | 保持原有排序（行为零变化） |

`temporal_intent` 与解析出的窗口写入 `query_plan`，经 `/recall/traces` 可审计。

### 6.4 实体图扩展（多跳召回）

`entity_graph.py` 在压缩写入与升级时构建实体共现图（`entity_nodes` / `entity_edges` / `entity_memory_links`）。召回时：

1. 用查询词匹配已知实体节点；
2. **直接引用**该实体的记忆（proximity 1.0）进入候选；
3. 沿**共现边**做一跳扩展，引用邻居实体的记忆（proximity 0.6）也进入候选——这是纯词法无法做到的"多跳访问"。

图内省与重建：`GET /graph/entities`、`GET /graph/neighbors/{entity_id}`、`POST /graph/rebuild`。图为空时召回零开销、无行为变化。

### 6.5 双时态 as-of 查询

`compressed_memories` 增加不可变事务时间 `created_at`（迁移自动回填 `compressed_at`）：

- **有效时间（valid time）**：`timespan_start/end`（记忆覆盖的领域时间），由 `timespan_start/timespan_end` 参数过滤；
- **事务时间（transaction time）**：`created_at`，记忆版本何时成为"现行"。

`RecallRequest.as_of=T` 按事务时间做快照查询：**T 时刻的现行版本 = 创建时间 ≤ T 且未被创建时间 ≤ T 的后继（`superseded_by` 链）取代**。用于审计、"当时的主张是什么"等场景；不传 `as_of` 时仍只返回 `status='active'`。

### 6.6 索引体系

| 索引 | 技术 | 用途 |
|------|------|------|
| 词法索引 | SQLite FTS5 | 关键词全文搜索 |
| 语义索引 | 向量嵌入（默认本地 n-gram，可接外部模型） | 语义相似度搜索（同义改写召回） |
| 实体图 | entity_nodes/edges/links | 实体共现与多跳召回 |
| Profile 索引 | 谓词倒排 | 用户事实精确匹配 |

### 6.7 LongMemEval 基准基线

`scripts/evaluate_longmemeval.py` 按 LongMemEval（arXiv 2410.10813）schema 做 **turn 级召回**评测（`Mem/benchmarks/longmemeval_zh.v1.json`，5 类 20 例）：

| 能力类别 | 开启语义前 | 开启语义后 | 解读 |
|---------|-----------|-----------|------|
| 时间推理 temporal-reasoning | 1.0 | **1.0** | P0 时间感知召回生效 |
| 跨会话 multi-session | 0.67 | 0.67 | 基本可用；个别会话被语义噪声干扰 |
| 单会话·助手 single-session-assistant | 0.67 | **1.0** | 语义补上关键词漏召 |
| 单会话·偏好 single-session-preference | 0.33 | **0.67** | 共享子串的改写被语义召回 |
| 单会话·用户 single-session-user | 0.0 | **0.33** | 部分改写命中；纯同义改写仍失分 |
| 知识更新 knowledge-update | 0.0 | 0.0 | 仍召回**旧陈述** → 需更新感知排序 |
| **总体** | **0.44** | **0.61** | MRR 0.42→0.58 / MAP 0.42→0.58 |

> **语义检索**：默认启用零依赖的本地 `CharNgramEmbedder`（字符 n-gram hashing，确定性、可测试），捕获**共享子串**的改写（如"晚上几点后不要被打扰"↔"晚上十点之后请勿推送通知"）。真实同义改写（0 共享字符）需训练/LLM 嵌入模型——接入外部模型后一条命令即可量化增益：
>
> ```bash
> python scripts/evaluate_longmemeval.py \
>   --semantic-provider openai --semantic-model text-embedding-3-small \
>   --semantic-base-url https://api.openai.com/v1 --semantic-api-key-env OPENAI_API_KEY
> # Ollama 本地：--semantic-provider ollama --semantic-model nomic-embed-text \
> #   --semantic-base-url http://localhost:11434/v1
> ```
>
> 外部嵌入的**真实 HTTP 传输路径已用本地 mock embeddings API 端到端验证**（`test_semantic_index_real_http_transport_end_to_end`）：把 config.yaml 的 `memory.semantic_recall.provider/model/base_url` 指向真实模型即可直接测量，无需改代码。
>
> **现行状态查询**（含"现在/目前/当前"，如"现在用什么容器运行时"）提高 recency 权重，倾向最新陈述；**知识更新**（旧陈述更匹配、新陈述不含主题词）仍是提取级问题——需实体/事实抽取把"podman ∈ 容器运行时"链接起来，纯排序无法解决。改进后应提高 `tests/test_memory_longmemeval.py` 中固化的阈值。

## 七、Profile（用户事实）管理

`profile_capture.py` 和 `profile_store.py` 提供显式事实的保守捕获：

- 只捕获用户**明确陈述**的事实（不推断）
- `supersedes` 链：新事实覆盖旧事实
- `revoke`：带时间戳的撤销
- `tombstone`：已删除事实的审计记录
- 版本化存储，支持回滚
- **双时态**：`valid_from/valid_to` 为有效时间，`created_at` 为事务时间；`recall` 传 `as_of` 时按事务时间快照解析"当时生效的事实"
