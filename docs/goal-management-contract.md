# VoidCube 单一目标管理契约

本文定义 Goal Manager 的稳定职责。它先解决“目标管理器是什么”，再决定它以核心工具、服务还是上下文工具的形式接入运行时。接入方式可以演进，但下面的语义必须保持稳定。

## 定义

Goal Manager 是 VoidCube 用来**定义、跟踪和验证一个当前目标**的辅助工具。它同时服务于两类使用者：

- 用户观察目标的意图、进展、阻塞和完成依据；
- LLM 在一个明确目标范围内进行规划、执行、复核和收口。

“单一目标”指一个会话或一次工作流程在同一时刻只有一个当前目标。目标内部可以拆成里程碑、任务、测试或其他执行节点，但这些节点都属于同一个目标闭环，不能被解释为多个并列的当前目标。

Goal Manager 管理的是**当前工作的控制状态**，不是长期记忆库、知识库或通用实体图谱。

## 目标对象

一个有效目标至少包含以下内容：

| 字段 | 含义 |
| --- | --- |
| `objective` | 用户希望达成的结果，用可观察的结果描述 |
| `intent` | 为什么要达成该结果，以及必要的范围和约束 |
| `acceptance_criteria` | 判断结果是否完成的条件 |
| `status` | 当前生命周期状态 |
| `progress` | 当前完成程度；只能由明确的状态或证据支持 |
| `next_action` | 当前最值得执行或澄清的下一步 |
| `blockers` | 阻止继续推进的事项 |
| `evidence` | 支持进度或完成结论的执行结果、测试、文件或用户确认 |

目标的子节点是实现手段。用户和 LLM 默认围绕根目标交流；只有在需要规划或执行时才展开子节点。

## 生命周期

目标状态应表达工作事实，而不是模型情绪或推测：

```text
planned -> in_progress -> waiting_review -> completed
                    \-> blocked -> in_progress
planned ------------> cancelled
in_progress --------> cancelled
```

- `planned`：目标已定义，尚未开始执行；
- `in_progress`：存在正在推进的工作；
- `blocked`：存在明确阻塞，需要用户输入、外部条件或重新规划；
- `waiting_review`：执行条件已满足，等待用户或授权审核者确认；
- `completed`：验收条件已满足，并且有可追溯依据；
- `cancelled`：用户明确终止目标。

模型不能仅凭一句“应该完成了”把目标置为 `completed`。完成必须通过验收条件和证据检查，或获得明确的用户确认。

## 责任边界

Goal Manager 必须负责：

- 记录一个当前目标及其意图；
- 将目标拆成可执行节点；
- 表达节点之间的拆解、依赖和阻塞关系；
- 给出当前状态和下一步建议；
- 记录执行结果、观察和证据；
- 检查完成条件；
- 记录重规划和状态变更的原因。

Goal Manager 不负责：

- 保存所有历史对话和用户长期偏好；
- 充当实体知识图谱或语义记忆检索库；
- 代替执行器运行任意副作用；
- 因为历史记忆或模型推断而直接修改当前目标状态；
- 同时维护多个未区分优先级的当前目标。

## 状态真源

当前目标的状态真源是 Goal Manager。会话提示词、UI、执行队列和记忆系统都只能读取或提出变更建议；正式状态变更必须经过 Goal Manager 的状态接口和审计记录。

记忆系统可以提供：

- 相关历史经验；
- 过去的决策和失败原因；
- 相似目标或解决方案；
- 可供核验的上下文证据。

这些内容默认属于参考信息。它们不能直接覆盖当前目标的意图、依赖、进度或完成状态。

## LLM 使用规则

LLM 面对 Goal Manager 时应遵守以下顺序：

1. 读取当前目标和当前节点；
2. 判断是否需要澄清意图或验收条件；
3. 读取与当前节点相关的上下文和记忆；
4. 执行一个可验证的下一步；
5. 回传执行结果或阻塞原因；
6. 由 Goal Manager 更新进度并判断是否可以收口。

LLM 可以请求创建子节点、调整计划或提交完成检查，但不能绕过 Goal Manager 声称目标已经完成。

## 用户观察规则

用户界面和会话摘要应优先显示：

- 当前目标是什么；
- 当前处于什么状态；
- 已完成了什么；
- 下一步是什么；
- 当前有什么阻塞；
- 为什么可以或不能宣布完成。

完整事件历史、子图和记忆召回属于展开内容，不应覆盖当前目标摘要。

## 与记忆系统的关系

目标图和记忆图保持两种不同语义：

- 目标边表示“必须完成、依赖或阻塞”；
- 记忆关系表示“相关、提及、属于或历史关联”。

二者可以通过显式引用连接，例如目标节点引用一条历史决策或测试记录，但不能把记忆实体直接当作目标节点，也不能把 `related_to` 解释成执行依赖。

当前引用层只保存 `memory_id`、关系类型（`context`、`prior_solution`、`decision`、`constraint`、`evidence`、`blocked_by`、`supersedes`）、置信度、创建者和时间戳。Goal Manager 不复制记忆标题、正文、embedding 或权限数据，不直接连接 `memory.db`；引用新增和软删除都写入目标审计事件，记忆内容仍由 MemAI 按自身权限提供。

引用解析是显式、按需的上下文步骤，不是每轮自动注入。解析适配器使用绑定了 `owner_id`、`workspace_id` 和 `memory_domain` 的 `MemoryClient` 逐条读取记忆，并施加引用数量、单条内容和总上下文预算；读取失败的引用会被跳过，不会把服务错误或内部字段送入模型。只有经过适配器生成的 fenced context 才能进入提示词。

## 有效性判定

Goal Manager 是否有效，使用以下可观察指标评估：

- 目标是否能被一句话准确复述；
- LLM 是否能稳定得到唯一的下一步；
- 阻塞是否能被明确记录和恢复；
- 完成声明是否都有验收依据；
- 用户是否能快速知道当前进展和剩余工作；
- 历史记忆是否减少重复劳动，而没有改变当前目标事实。

如果目标无法复述、下一步长期为空、完成状态没有依据，说明目标定义或计划质量不足；这时应澄清或重规划，而不是继续增加上下文内容。

## 当前实现说明

当前代码已经实现项目根节点、DAG 子节点、依赖、阻塞、进度、验收、证据、审核、重规划和审计事件。它目前位于 `plugins/goal_manager/`，这是部署形态；本契约把 Goal Manager 定义为 VoidCube 的目标领域能力。后续可以把它提升为核心工具或核心服务，而不改变本契约规定的语义。

新目标默认先经过复杂度路由：简单的一次性请求使用轻量会话目标；同时包含多步执行和验证、变更风险或多个交付物的目标自动升级到 Goal Manager。用户显式使用 `glq` 时始终升级。Goal Manager 不可用时保留会话目标，使任务仍可继续。
