# VoidCube 当前问题

更新日期：2026-07-21

本清单只记录尚未完成、能从当前代码直接验证的问题。完成事项不在这里累积，相关演进由 Git 历史追溯。优先级先看数据正确性和不可逆损失，再看主路径收口、恢复能力和维护成本。

## 当前问题

| 优先级 | 问题 | 证据与影响 | 下一步 |
| --- | --- | --- | --- |
| P0 | Tier 2 语义搜索的数据写入与查询没有闭环 | `compressed_memories` 虽有 `embedding` 字段，正常压缩写入路径却不生成向量；查询侧还通过 Chat Completions 让通用 LLM 输出浮点数组。LLM 调用成功但库内没有向量时，接口会返回空结果并标记为非降级语义搜索 | 当前协议只允许 Chat Completions，因此先删除伪 embedding 生成和伪成功语义入口，无向量时明确退回关键词查询。真正 embedding 必须先通过独立架构决策明确客户端、模型版本、写入、回填和失效策略 |
| P0 | Tier 1 相关性衰减按执行次数而非实际时间计算 | `_tier1_decay_cycle()` 每次运行都把所有未压缩 turn 乘固定系数；新写入数据、手动重复触发和调度频率变化都会改变衰减结果，`decay_interval_hours` 没有参与计算 | 增加可持久化的最后衰减时间，按实际经过时间计算指数衰减并在同一事务更新时间；覆盖新 turn、重复触发、服务重启和长时间停机测试 |
| P1 | Memory 服务存在两套 Tier 1 -> Tier 2 桥接实现 | `systems/memory/memory_service.py` 与 `systems/memory/tier1_to_tier2_bridge.py` 同时维护候选选择、LLM pipeline、归档和统计，embedding、质量指标和事务修复需要在两处同步 | 先用行为测试固定候选、无事件、归档和回滚语义，再确定唯一所有者并删除另一套实现，不保留长期转发兼容 |
| P1 | Memory 数据库没有内建备份、恢复和导出闭环 | SQLite 连接已启用 WAL 和 busy timeout，但服务没有一致性快照、备份轮换、恢复校验或面向用户的导出入口；数据库损坏或误操作后缺少标准恢复路径 | 基于 SQLite backup API 建立在线快照、校验、轮换、恢复演练和显式导出；备份文件迁移到 `VOIDCUBE_HOME` 数据目录 |
| P1 | 压缩只有工作量信号，没有在线质量门禁 | 当前能观测处理 turn 数、事件数、降级状态和有效写入数，但没有事件覆盖率、回链完整性、压缩比或降级比例阈值，低质量结果仍可能进入 Tier 2 | 定义最小质量报告并随每批压缩持久化；覆盖率或回链不达标时保留 Tier 1、报告 degraded，不推进压缩状态 |
| P1 | Memory 和服务生命周期缺少跨服务契约测试 | 单元测试已覆盖 WAL、回滚、无事件保护和 Supervisor lifespan，但缺少 Memory lifespan、Gateway 注册恢复、真实代理路由以及重启后维护状态的组合验证 | 增加最小本地三服务集成测试，覆盖启动顺序、注册丢失恢复、shutdown 取消、Memory 不可用和重复维护 |
| P2 | Memory Service 没有完整的多租户所有权边界 | session ID 和 namespace 能过滤部分查询，但表结构、通用查询和管理接口没有统一的 tenant/user 所有权或鉴权检查；若服务暴露给多个不可信用户，存在跨用户读取风险 | 保持当前单用户本地部署定位；只有确定多用户需求后再一次性增加认证、租户键、复合索引和全接口隔离测试，不用 metadata 充当安全边界 |
| P2 | 仓库根目录仍混有本地运行态 | `.body-*`、`.soul-runtime`、数据库与治理日志虽被忽略，但源码根目录仍承担运行数据职责 | 设计一次性迁移到 `VOIDCUBE_HOME`，验证后删除旧路径读取分支 |
| P2 | 旧治理事件可能缺少标题和摘要 | 新事件已写入恢复字段，但历史源数据从未记录的信息无法可靠推断 | 仅在真实数据影响观察时提供离线补全，不在运行时增加猜测型兼容 |
| P2 | `Mem/README.md` 与子项目文档仍混有早期目标态叙述 | 独立 Mem 文档中的当前范围、路线和 VoidCube 集成位置没有完全跟上现役服务 | 在 Memory 服务收口阶段同步重写，避免主仓与子项目各维护一套目标架构 |

## 主干收敛批次

本清单的执行顺序由[项目架构与逻辑架构](./项目架构与逻辑架构.md#14-主干架构收敛计划)统一定义：

| 批次 | 当前问题归属 | 本批次不做 |
| --- | --- | --- |
| M0 | 架构所有权、Agent 状态表述、Gateway/Facade 边界、长期真相和语义能力决策 | 不改业务行为，不进入模块联调 |
| M1 | `cli.py` 会话 UI 与命令路由 | 不改自主治理或 Memory 算法，不重写 Agent 主循环 |
| M2 | 运行态迁移、配置优先级、Store/Mem/身体/会话状态所有权 | 不保留旧路径长期双写 |
| M3 | 两个 Memory P0、bridge 唯一化、质量门禁、备份恢复、Mem 文档 | 不扩展多租户，不新增未决模型协议 |
| M4 | 自主任务状态、Store/Mem 恢复、Gateway/Facade/Adapter 执行闭环 | 不改变 `/auto` 与用户同意门语义 |
| M5 | 跨服务契约测试、健康与 trace、构建和隔离安装验收 | 不以单元测试代替真实三服务验证 |

M0 契约由文档测试持续约束。M1 Agent 用户链路已经收口：请求/响应、传输、流式装配、工具执行、持久化、单轮/attempt 状态、retry/compression recovery、response disposition、成功工具 turn 与 finalization 均有唯一所有者。CLI 流式展示、动态路由、内建执行表和 busy 生命周期也已统一；当前进行 M1 整体验收，验收完成前不进入 M2 或模块联调。

## 必须守住的边界

- `/auto` 与 `/auto-q` 当前只负责临时启用和停用自主链路；未来是否移除属于后续设计，不得提前写成现行行为。
- 自主链路启停不得关闭 Gateway、Memory、Supervisor 基础服务，也不得阻断用户主 CLI。
- 用户链路走 `user_chat`；自主任务由 API-A 执行组件走 `supervisor_task`。主 CLI 用户 host 不直接认领自主任务。
- Web 小屋保持只读观察，不增加用户聊天、人工队列管理或身体切换控制入口。
- 替身代码改进属于 API-A 自主执行面；身体切换机械流程属于 Executor；最终激活必须经过用户同意。
- 已退役的模型集成不得以 Provider、OAuth、适配器、别名、回退、技能或打包缓存形式恢复。

## 完成判定

问题只有在主实现、失败路径测试、现役文档和构建/安装契约同时对齐后才可从本清单删除。不得把未验证事项移入“已完成”章节来制造收口状态。

P0 的额外判定条件：

- 当前主干中的语义搜索必须证明“无伪 embedding、无伪成功、无向量时明确降级”；未来若重新启用真正 embedding，再追加“写入向量、版本一致、可检索、可回填、可失效”五项验收；
- 衰减必须证明相同时间跨度在手动重复触发、服务重启和调度延迟下得到等价结果。
