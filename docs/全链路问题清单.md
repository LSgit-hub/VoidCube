# 全链路问题清单

本文只记录当前实现仍需持续观察的风险，不作为完成日志。

## 运行与恢复

- 本地后台进程重启后可依据 wrapper 完成标记收敛终态，但父进程丢失后不能恢复 stdin 控制；此时先显示 `unknown`。
- 远程环境只有提供持久化 resume token 才能恢复控制；当前无 token 的执行在重启后明确进入 `unknown`。
- ProcessRegistry 的总容量达到上限且只有 active/unknown 项时会拒绝新后台任务，需要运维先完成对账或扩容。

## 动作证据

- ActionJournal 已覆盖统一 registry 派发的副作用工具；绕过该协调器的新执行入口必须在合并前接入相同写前登记契约。
- `unknown` 的不可幂等动作仍需逐工具 reconciler，不能提供统一自动重试开关。
- 上下文只携带脱敏 ActionRef；读取原始 evidence 时仍需按调用方权限做字段过滤。

## 服务与用户体验

- `/health` 表示进程存活及退化状态，自动化调度应以 `/ready` 为准。
- 语音链路使用持久麦克风流、本地 KWS 和 Silero VAD；唤醒判断只由本地 KWS 负责。
- KWS、VAD 和说话人校验需要在真实设备噪声下持续校准，模型资产位于 `runtime/voice/models/`。

## 持续门禁

- 修改模型、鉴权、协议、技能或打包时必须运行退役集成扫描和 wheel 契约。
- 修改自主任务状态时必须覆盖双 claim、旧 owner 迟到写回和 recovery 降级门禁。
- 修改消息或动作存储时必须覆盖迁移、事务回滚、幂等重放和重启恢复。

## 自进化跨环境

- 5G 已在 Windows + Podman 真实环境完成一次候选生成、Windows baseline/candidate Benchmark 和治理 handoff；当前真实场景只覆盖单文件 Python 编译，不能代表所有项目依赖。
- Podman 镜像构建依赖配置的镜像源和网络；需要继续验证镜像 digest 固定、依赖源不可用和镜像重建失败时的明确阻塞行为。
- Tirith 和 Podman disk quota 已形成显式逐命令能力证据；当前本机状态分别为 `unavailable` 和 `unsupported`。它们暂作为治理告警传播，生产部署仍需决定哪些状态必须硬阻塞。
- 平台选择已能要求 Windows 或 Linux + Windows，但当前 authoring 默认仍依赖 Podman，评测执行器尚未完成真正的多 runner 证据聚合；5I 完成前不能把“选择了双平台”理解为“双平台已经执行”。
- 5I 将 Windows native linked-worktree runner 设为默认 authoring/验证路径，Podman 降为按需 Linux runner；迁移期间必须避免保留两套默认主路径。
- 后续仍需扩展平台敏感 BenchmarkPack，覆盖 Windows 路径、权限、进程、文件锁、Node 原生模块以及部分 runner 成功、另一 runner 失败的矩阵。
