# 内生驱动核心设计

## 1. 这份文档回答什么

这份文档回答的不是“内生驱动会产出哪些任务”，而是：

- 内生驱动在 VoidCube 里应该是什么
- 它为什么不能被理解成普通任务生成器
- 当前 LM 认知接入在整体架构里处于什么位置
- 如何在不影响 API-A Agent 服务的前提下，把它演进成监督者的大脑核心

本文以当前代码为落点，统一描述：

- 认知主链
- LM 宪章与提示词接入
- 证据输入与治理输出
- 当前边界与后续演进方向

如果后续目标是继续优化稳定性而不是扩展能力，请同时参考 [内生驱动质量基线](./内生驱动质量基线.md)。

如果后续目标是收敛问题、统一主定义并避免兼容层重新上位，请同时参考 [内生驱动问题清单](./内生驱动问题清单.md)。

## 2. 先给结论

内生驱动不应该被定义成：

> 系统空闲时，自动生成几个任务放进队列。

它应该被定义成：

> 监督者内部的认知核心。
> 它持续感知用户、系统、记忆、身体和自身治理状态，判断“现在发生了什么”“最重要的问题是什么”“下一步该主动推动什么”。

任务只是它的一个外显接口，不是本体。

所以更准确的定位是：

- 不是“任务派发器”
- 不是“候选打印机”
- 而是“监督者认知中枢 + 治理输出中枢”

LM 在这里也不应被理解成“替代程序的任务生成器”，而应被理解成：

- 受认知宪章约束的判断部件
- 参与世界理解、证据解释和治理建议形成的认知层
- 仍然受程序边界、验证和治理护栏约束的上层推理器

## 3. 目标架构

目标中的内生驱动应当是一个持续循环：

```text
感知状态
  -> 构建世界模型
    -> 识别 need / tension
      -> 形成 intent
        -> 选择治理输出
          -> 记录结果
            -> 用结果修正下一轮判断
```

这不是“每隔几分钟想出几个任务”，而是“每隔几分钟重建一次自己所处局面”。

### 3.1 感知层

输入至少覆盖：

- 用户面
- Agent 面
- 记忆面
- 身体面
- 治理面
- 自我面

目标不是收集更多字段，而是形成统一的感知快照。

### 3.2 世界模型层

世界模型负责把离散信号解释成局面，例如：

- 当前是否应优先服务用户
- 当前系统是否处于增长窗口
- 当前队列是否拥塞
- 当前 truthfulness 压力是否升高
- 当前身体改进是否具备条件

这一步的意义是：后续判断不再直接面对零散计数器。

### 3.3 Need / Tension 层

这一层负责识别“当前最需要被处理的内在问题”。

典型 need 不是任务名，而是：

- `protect_user_service`
- `repair_truthfulness`
- `stabilize_memory_continuity`
- `expand_learning_frontier`
- `prepare_body_growth`
- `clear_governance_backlog`
- `observe_before_acting`

### 3.4 Intent 层

Intent 是多个 need 合并后的高层方向。

例如：

- 先稳态
- 先观察
- 先修正
- 先学习
- 先积累证据
- 暂不推动身体改进

意图和任务不是一回事。任务只是意图在当前阶段的一种投影。

### 3.5 决策 / 治理输出层

这一层负责决定当前意图应该落在哪种输出通道：

- `task_candidate`
- `governance_review_suggestion`
- `memory_maintenance_request`
- `switch_observation_signal`
- `internal_judgement_record`

当前阶段可以继续保留任务输出，但不能再把任务输出理解成本体。

### 3.6 反思层

反思层评估“上一次判断到底有没有价值”。

重点不是记录结果本身，而是让结果反向影响后续偏好：

- 哪些判断总是没有收益
- 哪些方向总被拒
- 哪些观察真的降低了风险
- 哪些自治冲动只是噪声

## 4. 当前实现到底是什么

当前代码已经不只是简单规则拼接了。它已经具备：

- 感知快照
- 世界模型
- 反思与自我调节
- `attention_agenda`
- `uncertainty_ledger`
- `observation_program`
- `meta_governance`
- `strategy_memory`
- `cognition_state` 持久化

同时，它也已经接入了一层受控的 LM 认知判断链：

```text
程序感知 / 证据汇聚
  -> context layers + evidence packet
    -> LM cognition charter prompt
      -> typed proposal / judgement
        -> 程序校验 / 约束 / 映射
          -> 治理输出与兼容投影
```

所以当前实现已经不是“纯任务生成器”，也不是“LM 全接管自治体”。

更准确地说：

> 代码主体已经在向认知循环靠拢，
> 当前 LM 接入是认知核心中的一个判断部件，
> 但对外兼容面仍保留了 `candidate / task` 投影。

## 6. LM 认知接入如何嵌入主设计

### 6.1 它解决什么问题

LM 接入的目的，不是把内生驱动重新拉回“更会产任务”的方向，而是让系统在程序已完成证据汇聚与结构整理后，拥有一个更强的认知判断部件，用来：

- 理解当前局面
- 在认知姿态约束下解释证据
- 形成更高层的治理建议
- 生成受限、可审计、可回查的结构化提案

### 6.2 当前配置方式

当前主配置入口已经收敛为一套 `cognition_charter`：

- `endogenous_drive_cognition_charter.core_mission`
- `endogenous_drive_cognition_charter.self_model_principles`
- `endogenous_drive_cognition_charter.evidence_policy`
- `endogenous_drive_cognition_charter.task_generation_policy`
- `endogenous_drive_cognition_charter.self_iteration_guardrails`
- `endogenous_drive_cognition_charter.cognitive_control_policy`

LM 模型本身仍复用 Supervisor / Mem 共用的 LLM 配置源，默认建议使用：

- `memory.llm.roles.governance_reasoner`

旧入口仍保留，但只应作为迁移兼容层，而不应继续被当成主设计：

- `endogenous_drive_lm_task_generation_enabled`
- `endogenous_drive_lm_task_max_candidates`
- `endogenous_drive_lm_task_model_role`
- `endogenous_drive_core_mission_prompt`
- `endogenous_drive_task_generation_principles`

### 6.3 认知宪章的角色

这套 charter 不只是“给 LM 的一段 prompt”，而是把 LM 的角色从易漂移的自然语言任务说明，升级成一套更稳定的认知约束。

它至少要回答五件事：

- 我为什么存在
- 我如何理解自己
- 我如何使用证据
- 我如何形成治理建议或任务投影
- 我绝对不能越过哪些边界

因此它既服务于：

- 面向 LM 的认知宪章
- 面向程序的认知控制策略

### 6.4 程序侧认知控制

当前 `cognitive_control_policy` 不只决定 prompt 文字，还决定程序何时主动收缩或放大某种认知姿态，例如：

- 什么时候提高 observation bias
- 什么时候提高 truthfulness bias 或 candidate throttle
- 什么时候压低 learning expansion
- 弱证据通道与 self-understanding gaps 如何放大收紧力度

在这之上，程序又支持语义化姿态模板 `active_posture_profile`，例如：

- `balanced`
- `observe_first`
- `evidence_repair_first`
- `truthfulness_first`
- `conservative`

姿态选择支持：

- `manual`
- `auto`

`auto` 模式会参考服务压力、纠偏信号、弱证据通道、self-understanding gaps、proposal drift、readiness、dominant constraint 等因素，先判断“当前应以什么思维姿态思考”，再把该姿态注入 LM 输入侧。

## 7. 当前 LM 主输入是什么

### 7.1 主结构

当前程序不是把散乱字段直接扔给 LM，而是先整理出主输入层：

- `decision_core`
- `supporting_detail`
- `long_tail_context`

在此基础上，再补充程序侧认知整理与观察层信息，例如：

- `perception`
- `world_model`
- `reflection`
- `adaptive_policy`
- `needs`
- `intents`
- `signals`
- `self_model_snapshot`
- `evidence_credibility_summary`
- `task_type_priors`
- `proposal_drift_memory`
- `memory_context`
- `evidence_channels`
- `research_digest`
- `evidence_graph`
- `agenda_graph`

### 7.2 这些输入的意义

这意味着 LM 当前看到的已不只是“几个任务线索”，而是更接近一套认知输入层：

- 自身状态
- 治理状态
- 学习状态
- 记忆与研究上下文
- 当前 shell 身体画像
- 程序先行整理后的自我理解摘要
- 程序先行整理后的证据可信度摘要
- 跨轮次漂移与纠偏记忆

其中关键新增层的定位大致是：

- `self_model_snapshot`：程序先整理“我当前怎样理解自己”
- `evidence_credibility_summary`：程序先整理“哪些依据更可信、哪里更弱、哪里冲突”
- `task_type_priors`：程序先整理“当前更偏观察、复核、学习还是改进”
- `proposal_drift_memory`：程序记住最近几轮是否在重复偏移

### 7.3 外部证据入口

当前 `external_research_evidence` 已经是正式证据入口雏形，适合接入：

- 最新研究摘要
- 架构笔记
- 外部理论线索
- 人工整理的前沿判断

当前仍以配置或文件注入为主，而不是运行时主动联网抓取。这样做的目的，是先把“外部依据通道”接到认知核心，再决定是否引入自动检索。

## 8. 当前允许 LM 产出什么

### 8.1 受限 candidate kind

为了安全，LM 当前只能返回受限的 `candidate_kind`，例如：

- `memory_maintenance`
- `truthfulness_review`
- `exploratory_learning`
- `shell_baseline_learning`
- `queue_hygiene_review`
- `body_improvement`

这意味着：

- LM 还不能自由发明任务类型
- 当前重点是先让它学会基于证据做判断
- 程序继续负责边界控制与兼容映射

### 8.2 typed proposal 协议

当前 LM 返回的不是纯文本标题，而是受控的 typed proposal。核心字段包括：

- `title`
- `summary`
- `candidate_kind`
- `task_type`
- `rationale`
- `evidence_summary`
- `confidence`
- `risk_level`
- `evidence_level`
- `observation_required`
- `execution_mode`
- `blocking_factors`
- `referenced_evidence_nodes`
- `referenced_agenda_nodes`

其中当前主要限制为：

- `task_type`: `observation / review / learning / maintenance / improvement`
- `risk_level`: `low / medium / high`
- `evidence_level`: `weak / moderate / strong`
- `execution_mode`: `observe_only / review_then_queue / guarded_execution`

### 8.3 程序侧认知校验

LM 输出后，程序不会“照单全收”，而是继续做认知一致性校验，例如对照：

- `task_type_priors`
- `evidence_credibility_summary`
- `self_model_snapshot`
- `reference_alignment`

判断 proposal 是否：

- 顺着当前程序判断的优先姿态
- 顺着当前证据可信度结构
- 顺着当前 self-understanding gaps
- 顺着当前引用对齐稳定性

这层校验的意义不是粗暴覆盖 LM，而是形成一条更完整的闭环：

```text
感知
  -> 程序侧认知整理
    -> LM 判断
      -> 程序侧认知校验
        -> 治理输出与后续反馈
```

## 9. 对现状的准确判断

当前实现已经不是“纯任务生成器”了，因为它已经有：

- `cognition_state`
- `meta_governance`
- `observation_program`
- `strategy_memory`
- 自我调节
- context layers
- LM cognition charter
- proposal drift / alignment feedback

但它也还没有完全到位，因为：

- 任务出口仍然太显眼
- 旧叙事仍然容易把它写成候选派发器
- 认知层和兼容层还没有在命名上完全分离
- LM 当前更多仍在“受控任务提案层”这个阶段，而不是完整治理判断层

所以现在最正确的理解是：

> 内生驱动的本体已经在向“认知核心”演进，
> LM 已经成为认知判断链的一部分，
> 但对外兼容面还保留了 `candidate/task` 投影。

## 10. 设计原则

### 10.1 用户服务优先

只要用户面 tension 高于成长面 tension，就优先稳态，不主动推高风险自治动作。

### 10.2 认知常驻，执行克制

内生驱动可以持续感知和判断，但不代表必须持续行动。

### 10.3 先判断，再执行

先把“知道该做什么”做对，再决定“怎么自动做”。

### 10.4 感知与判断常驻，执行出口受限

输出必须经过模式、窗口、护栏和治理约束。

### 10.5 LM 参与判断，但不越过程序边界

LM 可以参与更高层的证据解释、姿态遵循和治理建议形成，但程序仍负责：

- 输入裁剪
- 协议约束
- 风险护栏
- 一致性校验
- 最终落地边界

### 10.6 API-B 负责判断，API-A 继续服务用户

内生驱动属于监督者认知核心，不应反向污染 API-A 的直接用户服务链。

## 11. 推荐的演进路线

### 阶段 A

把 `evaluate_endogenous_drive()` 从“任务候选接口”升级成“认知评估接口”。

目标是让每次输出都能解释：

- 为什么当前该观察
- 为什么当前该稳态
- 为什么当前该学习
- 为什么当前不该做别的

### 阶段 B

把输出从单一任务出口，扩展成多通道治理输出。

### 阶段 C

把 outcome 反馈真正喂回 `strategy_memory`、`proposal_drift_memory` 和 policy 计算。

### 阶段 D

让 LM 进一步参与更高层的 world model / tension / governance 综合判断，程序继续担任边界和安全护栏。

### 阶段 E

逐步削弱兼容层在主摘要与主判断中的存在感，让 `need / intent / governance output` 真正压过 `task_type / candidate` 叙事。

## 12. 对当前实现的建议

我的建议是四条：

1. 保留 `evaluate_endogenous_drive()` 这个入口，但把它解释为 cognition evaluation，不再解释为 task generator。
2. 保留 `EndogenousTaskCandidate` 作为兼容投影，但不要再让文档把它写成主角。
3. 把 `cognition_charter + context layers + evidence packet + alignment feedback` 明确写成同一条主设计，而不是单独再维护一份分叉设计书。
4. 继续收敛日志、注释和文档中的 `candidate / task / proposal` 旧叙事，避免后续会话把兼容层误认为主设计。

## 13. 最近一步

最合适的下一步是：

> 继续把运行时总述和代码表述统一成“认知核心 + 治理输出”，并清理最容易把主判断压回 `task_type` 的旧摘要与旧命名。

这样后续不管是接 observation、review、body growth，还是更深的自主治理，都会站在同一套根定义上往前走。
