# 内生驱动核心设计

## 1. 这份文档回答什么

这份文档回答的不是“内生驱动会产出哪些任务”，而是：

- 内生驱动在 VoidCube 里应该是什么
- 它为什么不能被理解成普通任务生成器
- 如何在不影响 API-A Agent 服务的前提下，把它演进成监督者的大脑核心

本文以当前代码为落点，目标是把“感知、建模、发现需要、形成意图、选择治理输出”这条主链说清楚。

## 2. 先给结论

内生驱动不应该被定义成：

> 系统空闲时，自动生成几个任务放进队列。

它应该被定义成：

> 监督者内部的认知核心。
> 它持续感知用户、系统、记忆、身体和自身治理状态，判断“现在发生了什么”“最重要的问题是什么”“下一步该主动推动什么”。

任务只是它的一个外显接口，不是本体。

所以更准确的定位是：

- 不是“任务派发器”
- 不是“候选打印机”
- 而是“监督者认知中枢 + 治理输出中枢”

## 3. 当前实现到底是什么

当前代码已经不只是简单规则拼接了。它已经具备：

- 感知快照
- 世界模型
- 反思与自我调节
- attention_agenda
- uncertainty_ledger
- observation_program
- meta_governance
- strategy_memory
- cognition_state 持久化

也就是说，代码主体已经在向“认知循环”靠拢。

但当前主外壳仍保留了“candidate / task”叙事，所以容易让后续维护者误以为它还是一个任务生成器。这个文档就是要把这个误解纠正过来。

## 4. 目标架构

目标中的内生驱动应当是一个持续循环：

```text
感知状态
  -> 构建世界模型
    -> 识别 need / tension
      -> 形成 intent
        -> 选择治理输出
          -> 记录结果
            -> 用结果修正下一轮判断
```

这不是“每隔几分钟想出几个任务”，而是“每隔几分钟重建一次自己所处局面”。

### 4.1 感知层

输入至少覆盖：

- 用户面
- Agent 面
- 记忆面
- 身体面
- 治理面
- 自我面

这里的目标不是收集更多字段，而是形成一个统一的感知快照。

### 4.2 世界模型层

世界模型负责把离散信号解释成局面，例如：

- 当前是否应优先服务用户
- 当前系统是否处于增长窗口
- 当前队列是否拥塞
- 当前 truthfulness 压力是否升高
- 当前身体改进是否具备条件

这一步的意义是：后续判断不再直接面对零散计数器。

### 4.3 Need / Tension 层

这一层负责识别“当前最需要被处理的内在问题”。

典型 need 不是任务名，而是：

- `protect_user_service`
- `repair_truthfulness`
- `stabilize_memory_continuity`
- `expand_learning_frontier`
- `prepare_body_growth`
- `clear_governance_backlog`
- `observe_before_acting`

### 4.4 Intent 层

Intent 是多个 need 合并后的高层方向。

例如：

- 先稳态
- 先观察
- 先修正
- 先学习
- 先积累证据
- 暂不推动身体改进

意图和任务不是一回事。任务只是意图在当前阶段的一种投影。

### 4.5 决策 / 治理输出层

这一层负责决定当前意图应该落在哪种输出通道：

- `task_candidate`
- `governance_review_suggestion`
- `memory_maintenance_request`
- `switch_observation_signal`
- `internal_judgement_record`

当前阶段可以继续保留任务输出，但不能再把任务输出理解成本体。

### 4.6 反思层

反思层评估“上一次判断到底有没有价值”。

重点不是记录结果本身，而是让结果反向影响后续偏好：

- 哪些判断总是没有收益
- 哪些方向总被拒
- 哪些观察真的降低了风险
- 哪些自治冲动只是噪声

## 6. 对现状的准确判断

当前实现已经不是“纯任务生成器”了，因为它已经有：

- cognition_state
- meta_governance
- observation_program
- strategy_memory
- 自我调节

但它也还没有完全到位，因为：

- 任务出口仍然太显眼
- 旧叙事仍然容易把它写成候选派发器
- 认知层和兼容层还没有在命名上完全分离

所以现在最正确的理解是：

> 内生驱动的本体已经在向“认知核心”演进，
> 但对外兼容面还保留了“candidate/task”投影。

## 7. 设计原则

### 7.1 用户服务优先

只要用户面 tension 高于成长面 tension，就优先稳态，不主动推高风险自治动作。

### 7.2 认知常驻，执行克制

内生驱动可以持续感知和判断，但不代表必须持续行动。

### 7.3 先判断，再执行

先把“知道该做什么”做对，再决定“怎么自动做”。

### 7.4 感知与判断常驻，执行出口受限

输出必须经过模式、窗口、护栏和治理约束。

### 7.5 API-B 负责判断，API-A 继续服务用户

内生驱动属于监督者认知核心，不应反向污染 API-A 的直接用户服务链。

## 8. 推荐的演进路线

### 阶段 A

把 `evaluate_endogenous_drive()` 从“任务候选接口”升级成“认知评估接口”。

目标是让每次输出都能解释：

- 为什么当前该观察
- 为什么当前该稳态
- 为什么当前该学习
- 为什么当前不该做别的

### 阶段 B

把输出从单一任务出口，扩展成多通道治理输出。

### 阶段 C

把 outcome 反馈真正喂回 strategy_memory 和 policy 计算。

### 阶段 D

让 LM 参与更高层的 world model / tension / governance 综合判断，程序继续担任边界和安全护栏。

## 9. 对当前实现的建议

我的建议是三条：

1. 保留 `evaluate_endogenous_drive()` 这个入口，但把它解释为 cognition evaluation，不再解释为 task generator。
2. 保留 `EndogenousTaskCandidate` 作为兼容投影，但不要让文档把它写成主角。
3. 继续收敛日志、注释和文档中的“candidate task”叙事，避免后续会话把兼容层误认为主设计。

## 10. 最近一步

最合适的下一步是：

> 把当前内生驱动的文档叙事统一成“认知核心 + 治理输出”，并继续清理代码里的旧表述。

这样后续不管是接 observation、review、body growth，还是更深的自主治理，都会站在同一套根定义上往前走。
