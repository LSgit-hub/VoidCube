# VoidCube 项目架构分析

> 文档状态：架构分析快照。
>
> 当前正式架构入口以 [voidcube架构基线.md](./voidcube架构基线.md) 为准；组件接线说明以 [architecture-integration.md](./architecture-integration.md) 为准。本文主要保留当前仓库目录定位、过渡态判断和维护建议。

## 1. 总体结论

以 [voidcube架构基线.md](./voidcube架构基线.md) 为准，VoidCube 当前应被理解为：

- `CLI` 是唯一用户入口
- `systems/` 是目标主架构的主体落点
- `Mem` 是长期记忆与治理能力的核心支撑
- `agent/`、`run_agent.py`、`tools/`、`VoidCube_cli/` 是当前执行体、工具面和交互壳

而且这个项目需要从两个层面一起理解：

- 对用户来说：看到的是 `CLI + Agent`
- 对系统来说：真正搭起来的是一套围绕 Agent 自学习、自进化、自管理的内部架构

再进一步说：

- VoidCube 是母体系统
- 双身体里的两个 Agent 是母体持续培养、切换给用户使用的两个子 Agent

因此，这个仓库不再适合描述成“本地 CLI 主线 + 服务化旁路线”的双线项目。更准确的说法是：

**这是一个正在从既有 CLI 执行体收敛到单机多进程服务化架构的同一项目仓库。**

当前的真实问题不是“存在两套目标架构”，而是：

- 新基线已经明确
- 仓库中仍有一部分实现和文档停留在过渡态

## 2. 分层视角

从职责上看，当前项目可归纳为 6 层：

```text
用户
  ->
CLI 入口层
  cli.py
  VoidCube_cli/
  ->
网关与治理编排层
  systems/gateway/
  systems/governor.py
  systems/execution/
  ->
Agent 执行层
  run_agent.py
  agent/
  systems/agent/
  ->
工具执行层
  model_tools.py
  toolsets.py
  tools/
  ->
记忆与治理存储层
  systems/memory/
  plugins/memory/
  Mem/
  ->
自学与演化支持层
  systems/self_learning/
  docs/* 身体治理协议
```

### 各层职责

- CLI 入口层
  - 接收用户输入
  - 展示输出
  - 作为用户对系统进行手动管理的标准入口
- 网关与治理编排层
  - 统一内部通信
  - 维护活动事实
  - 路由到活跃 Agent
  - 承接治理裁决与执行器协作
- Agent 执行层
  - 运行任务
  - 调用工具
  - 使用 API-A 推理
- 工具执行层
  - 暴露工具 schema
  - 路由工具调用
  - 承担环境交互
- 记忆与治理存储层
  - 保存长期记忆
  - 维护治理历史与演化记录
  - 承接 API-B
- 自学与演化支持层
  - 负责知识采集、实验、验证、结论沉淀

其中：

- CLI 入口层主要服务用户
- 其余内部层主要服务 Agent 的持续演进

## 3. 主运行链路

当前应统一按下面的链路理解系统：

```text
用户
  -> CLI
  -> 记忆服务 / 监督治理面
  -> 网关
  -> 活跃 Agent
  -> 工具 / 记忆 / 外部能力
  -> 结果回到 CLI
```

对于自提升相关能力：

```text
自学系统
  -> 记忆服务
  -> 治理裁决面
  -> 执行器
  -> 网关同步活跃身体
  -> 结果写回记忆
```

这里最关键的边界有三条：

1. CLI 是用户入口，不是第二套本地模式
2. Agent 是执行体，不是长期身份存储位置
3. 监督治理面只做判断，不直接承担机械执行动作

还要补上一条：

4. 这套内部架构当前最主要的升级对象，是 Agent 本身

## 4. 关键目录的架构定位

### 4.1 `cli.py` 与 `VoidCube_cli/`

这部分是项目的人机交互壳，负责：

- 命令行入口
- 会话交互
- 手动配置与控制入口
- 平台适配
- slash command / toolset / 配置管理

它们是正式架构的一部分，但其职责是“入口与控制面”，不是长期真相源。

它们也不是当前阶段最优先的自我升级对象。

### 4.2 `run_agent.py` 与 `agent/`

这部分仍然是当前最重要的执行核心，负责：

- system prompt 组装
- 上下文管理
- 工具调度
- 记忆编排
- 模型调用循环

从基线角度看，这一层代表“身体执行逻辑”的核心实现。后续无论如何收敛，Agent 都应继续无状态化，并把长期状态下沉到记忆服务。

更关键的是，当前整个项目搭建内部架构的主要目的，就是持续产出更好的 Agent，再切换给用户使用。

因此，后续如果涉及目录与运行结构设计，也应该优先支持：

- 把子 Agent 作为独立可管理对象落盘
- 让每个子 Agent 具备自己的 `worktree/runtime/logs/meta`

这里要特别区分：

- `agent/` 与 `run_agent.py` 内部可以存在临时记忆管理、上下文压缩和短期会话整理
- 但这套记忆系统不是 `Mem`
- `Mem` 才是长期记忆、灵魂真相和治理解释的最终承载层
- 长期记忆的压缩、整理、管理由 `Mem` 自己内部的记忆管理者模型完成，不由 Agent 代做

### 4.3 `tools/`、`model_tools.py`、`toolsets.py`

这是项目的能力执行总线，负责：

- 工具注册
- schema 暴露
- 工具权限与能力面裁剪
- 环境交互与安全守卫

这一层和基线不冲突，后续仍会是 Agent 的重要执行面。

### 4.4 `systems/`

`systems/` 应被视为基线主架构的集中落点，而不是可有可无的实验支线。其职责包括：

- `gateway/`
  - 内部网关、活动事实、路由、活跃身体选择
- `memory/`
  - 长期记忆服务与 API-B 接口落点
- `agent/`
  - 作为独立执行实例运行的 Agent
- `self_learning/`
  - 自学系统
- `execution/`
  - 执行器与动作适配层
- `governor.py`
  - 治理裁决语义
- `body_registry.py` / `lifecycle.py` / `probe.py`
  - 身体注册、状态迁移、探测与观察窗口协议

当前的主要问题不是 `systems/` 是否需要存在，而是其中部分旧实现还保留了“supervisor 既裁决又执行”的过渡职责。

从项目目标角度讲，`systems/` 这一层并不是为了自己而存在，而是为了把 Agent 的自学习、自进化、自管理做成稳定的内部能力。

### 4.5 `Mem/` 与记忆提供器

`Mem/` 不是无关子项目，而是长期记忆与治理能力的重要来源。当前仓库里关于记忆有三层：

- 本地轻量记忆
- 主运行时的 Agent 内部记忆 / memory provider 编排
- `Mem/` 的结构化长期记忆与治理能力

按“重要理解”段的口径，记忆管理者与监督者默认属于同一条 Mem / API-B 能力链，只是在不同时间窗口承担不同权限和任务上下文，而不是天然对应两套独立进程。

这三层里最容易混淆的是中间这一层：

- Agent 内部记忆系统负责短期工作记忆与临时会话态
- `Mem` 负责长期压缩、整理、归档和治理使用

基线要求后续逐步把影响身份连续性、治理解释和演化记录的真相收口到这条线上。

## 5. 当前已对齐的部分

按新基线看，仓库里已经具备不少正确方向上的基础：

- CLI 入口已经稳定存在
- 网关已经具备注册、路由和活动时间线雏形
- 记忆服务已经独立成面
- 双槽位身体注册、probe、watch-window 已经成形
- 自学系统已有初级骨架
- 执行器适配层已开始把机械动作从 supervisor 剥离

这些基础说明项目不是要推翻重来，而是要继续收口职责边界。

## 6. 当前仍需警惕的偏差

最需要避免的误读有四类：

- 把 CLI 理解成“本地模式”，把 `systems/` 理解成“服务模式”
- 把 `systems/` 写成与主链路无关的旁路线
- 把监督治理面继续写成可选增强层
- 把 supervisor 的过渡执行职责误写成长期架构职责

这些误读会直接导致：

- 文档继续鼓励绕过网关
- 执行器边界继续模糊
- 记忆 / 治理 / 执行三层再次混在一起

## 7. 维护建议

接下来更值得做的不是重新发明总架构，而是沿基线持续收口：

1. 让文档统一承认“CLI 唯一入口 + 单机多进程唯一目标形态”
2. 让治理裁决与机械执行彻底分层
3. 让网关继续成为统一活动事实与内部入口
4. 让长期状态继续向记忆服务 / Mem 收口
5. 让自学系统始终只生产证据和建议，不直接发版

## 8. 一句话总结

VoidCube 当前不是“两套系统并存”，而是**一套对用户表现为 CLI + Agent、对内部则依靠网关、记忆/监督、执行器、自学系统持续改进 Agent 并切换给用户使用的单机多进程架构**；仓库中的主要任务，是把仍处于过渡态的实现和文档继续向这条基线收口。
