# 自主链路 vs 用户链路 — 冲突点全面分析

> 建立日期：2026-08-07
>
> 适用范围：`VoidCube_cli` 中自主链路（supervisor_task）与用户链路（user_chat）的交互冲突

---

## 0. 执行路径概览：谁在哪条 CLI 上运行

在分析冲突之前，必须明确两条链路的执行宿主。

### 0.1 两条独立的 `VoidcubeCLI` 实例

| 实例 | 角色 | `embedded_role` | 用途 |
|------|------|-----------------|------|
| **父 host（主 CLI）** | 用户交互 | `""`（无） | 承载 prompt_toolkit TUI、处理用户输入、输出到终端 |
| **component_host（迷你 CLI）** | 自主任务执行 | `"autonomous"` | 承载自主轮询循环、执行 Supervisor 下发的任务、输出被静默 |

component_host 在父 host 的 `_ensure_autonomous_component_host()` 中按需创建（[app.py:1464-1497](../VoidCube_cli/app.py#L1464-L1497)）：

```python
component_host = type(self)(
    model=..., toolsets=..., provider=...,
    embedded_role="autonomous",
)
```

两个实例各自拥有独立的 `ApplicationRuntime`、`_agent_running`、`session_id`、`conversation_history`、`ChatBlockStore`。

### 0.2 两条 `AutonomousExecutorRuntime`，操作不同 host

[autonomous_runtime_host.py:19-61](../VoidCube_cli/autonomous_runtime_host.py#L19-L61) 中的 `autonomous_executor_runtime()` 按 host 缓存 runtime 实例，**所有端口（`get_current_task`、`set_current_task`、`enqueue_pending_input` 等）都读写传入 host 的属性**：

```python
get_current_task=lambda: getattr(host, "_current_autonomous_task", None),
set_current_task=lambda task: setattr(host, "_current_autonomous_task", task),
enqueue_pending_input=lambda prompt: host._pending_input.put(prompt),
```

| 调用位置 | 传入的 host | 读写的 `_current_autonomous_task` |
|----------|------------|----------------------------------|
| `_autonomous_component_runtime()`（[app.py:1499](../VoidCube_cli/app.py#L1499)） | `component_host` | component_host 的 |
| 主 CLI 的 `chat()`（[app.py:3658](../VoidCube_cli/app.py#L3658)） | `self`（父 host） | 父 host 的 |

**关键结论：`poll_workflow()` 认领任务后写入 `component_host._current_autonomous_task`；主 CLI 的 `chat()` 读取 `parent._current_autonomous_task`（始终为 `None`）。因此主 CLI 的 `chat()` 永远走 `user_chat` 角色，不会误执行自主任务。**

### 0.3 自学习任务的完整执行路径

```
Gateway (approved tasks)
  │
  ▼
run_autonomous_component_loop (daemon 线程)
  → poll_workflow()                         # 从 Gateway 拉取/认领 self_learning 或 body_improvement 任务
  → inject_execution_prompt()               # 构建 prompt
  → component_host._pending_input.put()     # 注入到迷你 CLI 的队列
  → get_pending_input()                     # 从迷你 CLI 队列取出
  → run_component_operation_silently(...)   # 线程级 stdout→StringIO 静默
    → component_host._execute_pending_input()
      → component_host.chat(message)        # ← 自学习在迷你 CLI 上执行
```

**自学习始终在 component_host（迷你 CLI）上执行，不会占用主 CLI。**

### 0.4 输出静默机制

两层防护确保自主链路不污染用户终端：

**第一层**：`_should_emit_scrollback_output()`（[app.py:1431](../VoidCube_cli/app.py#L1431)）——component_host 的 `_is_embedded_component()` 返回 `True`，跳过大部分显式终端输出。

**第二层**：`run_component_operation_silently()`（[autonomous_component_output.py:33-40](../VoidCube_cli/autonomous_component_output.py#L33-L40)）——`_ThreadOutputProxy` 做线程级 stdout/stderr 重定向，只拦截 autonomous 线程的写入，主线程不受影响：

```python
class _ThreadOutputProxy:
    def write(self, data):
        if threading.get_ident() == self._target_thread_id:
            return self._sink.write(data)    # autonomous 线程 → StringIO（丢弃）
        return self._original.write(data)    # 其他线程 → 真实 stdout
```

**隐患**：`chat()` 中硬编码的 `cprint=_cprint`（[app.py:3664](../VoidCube_cli/app.py#L3664)）没有使用 component_host 的 `_quiet_autonomous_component_cprint`。当前靠第二层（线程级重定向）兜底，但如果 autonomous 线程 spawn 子线程调 `_cprint`，子线程输出不会被拦截。

## 1. CLI 实例 / 终端占用冲突

### 1.1 `_agent_running` 标志独立但不可见

**位置**：[app.py:985-997](../VoidCube_cli/app.py#L985-L997)、[autonomous_runtime_host.py:42](../VoidCube_cli/autonomous_runtime_host.py#L42)

父 host 和 component_host 各自拥有独立的 `ApplicationRuntime`，因而拥有**独立的 `_agent_running` 标志**。两者并不共享此状态。

**问题**：
- 父 host 的 TUI 状态栏读取 `self._agent_running`（[app.py:3967](../VoidCube_cli/app.py#L3967)），无法感知 component_host 正在执行工具
- `can_poll_workflow()` 检查 `component_host._agent_running`（[app.py:1543](../VoidCube_cli/app.py#L1543)），无法感知父 host 正在执行用户 turn
- 两侧只能通过 `_api_a_execution_gate` 锁间接感知对方活动——这是一个粗粒度的二值信号，无法区分"正在运行"和"即将运行"

**实际风险**：状态栏在自主任务执行期间不显示活动指示器（但自主面板独立渲染，部分弥补）。

### 1.2 终端输出抑制依赖双层防护

**位置**：[app.py:1431-1433](../VoidCube_cli/app.py#L1431-L1433)、[autonomous_component_output.py:33-40](../VoidCube_cli/autonomous_component_output.py#L33-L40)

两层防护各自有盲区：

- `_should_emit_scrollback_output()` 依赖 `embedded_role` 正确设置；如果 component_host 创建时未正确设置该属性，终端输出会泄露。
- `_ThreadOutputProxy` 只拦截创建它的线程的输出；如果 autonomous 线程内 spawn 子线程做 I/O，那部分输出会绕过拦截。

**实际风险**：低。当前双层防护叠加后覆盖了主要路径。但 `chat()` 中 `cprint=_cprint` 硬编码是潜在的单点穿透。

### 1.3 共享 `_api_a_execution_gate` 锁（核心串行化点）

**位置**：[app.py:1384](../VoidCube_cli/app.py#L1384) 和 [app.py:4641](../VoidCube_cli/app.py#L4641)

只有一个全局锁 `_api_a_execution_gate`（`threading.Lock`），被传递给 `CliInteractiveLifecycleRuntime`：

```python
execution_gate=self._api_a_execution_gate,
```

这意味着：
- **用户链路执行 turn 时**，持有该锁 → 自主链路 poll_workflow 无法认领新任务，但轮询循环继续运行
- **自主链路执行时**，也通过同一个锁 → 用户输入被 process_loop 阻塞在 `_pending_input` 队列中
- 锁的粒度是**整个 turn 执行**，而非更细粒度的操作

**实际风险**：如果自主链路执行一个长任务，用户在此期间按 Enter 发送的消息会排队等待（而非丢失），但用户会感受到"卡住"无反馈。这是有意为之的串行化设计，但缺少用户体验提示。

## 2. Agent 实例冲突

### 2.1 Agent 销毁重建仅影响 component_host（自学习任务）

**位置**：[app.py:3670-3676](../VoidCube_cli/app.py#L3670-L3676) 和 [app.py:3933-3934](../VoidCube_cli/app.py#L3933-L3934)

```python
autonomous_toolsets = (
    autonomous_task_toolsets(current_autonomous_task)
    if autonomous_task_run_id      # 父 host 的 chat() 中此值为 ""
    else None
)
if autonomous_toolsets is not None and self.agent is not None:
    self.agent = None   # 仅当 autonomous_task_run_id 非空时触发
```

由于父 host 的 `chat()` 中 `autonomous_task_run_id` 始终为 `""`（见 0.2 节），`autonomous_toolsets` 为 `None`，**父 host 的 Agent 永远不会被此路径销毁**。

仅 component_host 的 `chat()` 中 `autonomous_task_run_id` 非空，且当任务类型为 `self_learning` 时 `autonomous_task_toolsets()` 返回 `["learn"]`，触发销毁重建（以限制 toolset）。

[autonomous_executor.py:44-50](../VoidCube_cli/autonomous_executor.py#L44-L50)：

```python
def autonomous_task_toolsets(task):
    if autonomous_task_execution_kind(task) == "self_learning":
        return ["learn"]    # 自学习只允许 learn toolset
    return None             # body_improvement 不限制
```

**问题**：
- 自学习任务每次都重建 Agent（API 重连 + 工具重载），增加 ~200ms 延迟
- `body_improvement` 任务不限制 toolset，不触发重建，行为不一致
- `finally` 块中的 `self.agent = None` 意味着自学习任务结束后 component_host 的 Agent 被清理，下次任务需重建

**注意**：这是**有意的设计**（限制自学习权限），不是 bug。冲突点在于重建开销和生命周期不一致。

### 2.2 Component Host 独立 Agent 的资源共享

**位置**：[app.py:1464-1497](../VoidCube_cli/app.py#L1464-L1497)

两个独立 Agent 共享同一个 provider/API key，可能触发 API 并发限制。此外：

- 工具回调（sudo password、approval sink、secret capture）只在父 host 注册（[app.py:4498-4503](../VoidCube_cli/app.py#L4498-L4503)），component_host 触发交互式工具时会失败
- Voice session 只在父 host 上存在
- 当前自主任务类型（self_learning → learn only, body_improvement → git worktree edit）基本不触发需要用户交互的工具，风险较低

## 3. 会话和对话历史冲突

### 3.1 会话 ID 混用

**位置**：[app.py:1286-1295](../VoidCube_cli/app.py#L1286-L1295)

父 host 的 session_id 同时标记 `interactive_source="cli"` 和 `autonomous_source="cli_supervisor_task_lane"`。Component host 通过 `_ensure_supervisor_task_session_view` 获得独立 session_id，但两者写入同一个 `SessionDB`（SQLite），依赖 `source` 字段区分。如果 source 字段写入不一致，查询结果可能混乱。

### 3.2 Conversation History 隔离（实际未污染）

**位置**：[app.py:3830-3839](../VoidCube_cli/app.py#L3830-L3839)

父 host 和 component_host 各自拥有独立的 `conversation_history`：
- 父 host 的 turn 结果写入 `parent.conversation_history`（角色为 `user_chat`）
- component_host 的 turn 结果写入 `component_host.conversation_history`（角色为 `supervisor_task`）

**两者互不污染**。之前的分析中"自主链路的 tool-call 混入用户对话历史"是错误的——因为 `chat()` 中 `self` 指向当前 host，`TurnResultApplicationRuntime.apply()` 写入的是当前 host 的 `conversation_history`。

**但有一个边缘情况**：如果未来代码变更，让父 host 的 `chat()` 能检测到 `_current_autonomous_task`（比如通过共享 component_host 的 runtime），则可能引入污染。当前不受此影响。

### 3.3 ChatBlockStore 独立但有共用路径

**位置**：[app.py:1079-1088](../VoidCube_cli/app.py#L1079-L1088)

每个 host 实例有自己的 `ChatBlockStore`（懒加载，存储在 `self._chat_block_store`）。父 host 和 component_host 的 Store **互不干扰**。

但有一个例外：父 host 的 `_handle_application_event()`（[app.py:3364-3369](../VoidCube_cli/app.py#L3364-L3369)）将所有事件写入父 host 的 Store。component_host 的事件不会进入父 Store。但如果某个工具事件在父 host 上也触发了（比如全局回调），则可能重复记录。

## 4. 中断和输入队列冲突

### 4.1 中断路由实际是正确的

**位置**：[app.py:3799-3822](../VoidCube_cli/app.py#L3799-L3822)

TUI 的 Enter 键处理检查 `parent._agent_running`（[app.py:4099-4103](../VoidCube_cli/app.py#L4099-L4103)）：

```python
enqueue_input=lambda payload, is_command: self._ensure_application_runtime().enqueue_turn_input(
    payload, is_command=is_command, busy_input_mode=self.busy_input_mode,
),
```

`enqueue_turn_input` 判断：
- `parent._agent_running == True` → 用户输入进入 `_interrupt_queue`（触发中断）
- `parent._agent_running == False` → 用户输入进入 `_pending_input`（排队等待）

**当自主链路在 component_host 上运行时**：`parent._agent_running` 为 `False`（因为运行的是 component_host，不是父 host），用户输入进入 `_pending_input`（空闲队列），然后由 process_loop 通过 `_api_a_execution_gate` 串行化执行。**不会错误地触发 interrupt。**

**当用户链路在父 host 上运行时**：`parent._agent_running` 为 `True`，用户输入进入 `_interrupt_queue`，正确触发用户链路中断。

小结：中断路由是正确的，不会出现"中断错误目标"的问题。之前的分析对此有误判。

## 5. 状态栏 / UI 状态冲突

### 5.1 Spinner 和工具状态不可见

**位置**：[tool_event_adapter.py:52-54](../VoidCube_cli/tool_event_adapter.py#L52-L54) 和 [tool_event_adapter.py:141-143](../VoidCube_cli/tool_event_adapter.py#L141-L143)

自主链路的 tool 事件在 component_host 上更新 `_spinner_text` / `_tool_start_time` / `_current_tool_name`（通过 `host._invalidate()`）。但 TUI 状态栏从父 host 读取：

```python
# app.py:3967, 4255-4257
agent_running=lambda: bool(self._agent_running),  # 父 host → False
spinner_text=lambda: self._spinner_text,           # 父 host → 空
```

因此状态栏在自主任务执行期间**不会显示工具活动**。

**部分弥补**：`_autonomous_panel_state_ports` 从 component_host 读取状态（[app.py:1814-1829](../VoidCube_cli/app.py#L1814-L1829)），自主面板独立渲染当前任务、spinner 和执行事件。

### 5.2 自主面板与状态栏竞争行空间

**位置**：[app.py:4539-4547](../VoidCube_cli/app.py#L4539-L4547)

自主面板在状态栏同区域额外渲染（当 `_has_visible_autonomous_work_view()` 返回 True 时），与状态栏竞争同一行空间。两个面板各自独立计算宽度和截断，窄终端下可能错乱。

## 6. 资源生命周期冲突

### 6.1 Agent 退出清理

**位置**：[app.py:4401-4408](../VoidCube_cli/app.py#L4401-L4408)

退出时清理顺序：
1. `_stop_autonomous_execution_component(interrupt=True)` → 停止 component_host 的 Agent
2. `interrupt_running_agent()` → 停止父 host 的 Agent
3. `_run_cleanup()` → 全局资源释放

如果 component_host 的 Agent 正在 API 调用中被 interrupt，可能触发 `"Event loop is closed"` 错误（因为 component_host 没有自己的事件循环，共享主线程的）。该错误被 `prompt_toolkit` 的异常处理器捕获，表现为 "Press ENTER to continue..."。

### 6.2 MCP/工具回调注册缺失

**位置**：[app.py:4498-4503](../VoidCube_cli/app.py#L4498-L4503)

工具回调（sudo password、approval sink、secret capture）只在父 host 注册。当前自主任务类型（自学习仅限 `["learn"]` toolset、替身改进在独立 worktree 中编辑文件）基本不触发需要用户交互的工具。但如果未来自主任务范围扩展，可能触发未注册回调。

### 6.3 Atexit 竞争

- `_active_agent_ref` 是模块级全局变量，只指向最后调用 `_init_agent()` 的 Agent。如果 component_host 最后初始化，退出时 `_run_cleanup()` 中的 `shutdown_memory_provider` 可能操作 component_host 的 Agent（它可能已被 component_host 生命周期单独清理）
- 父 host 和 component_host 各自注册了 atexit handler，但全局 `_cleanup_done` 守卫确保 `_run_cleanup()` 只执行一次

## 7. `_active_chat_agent_role` 的角色标记

**位置**：[app.py:3727-3728](../VoidCube_cli/app.py#L3727-L3728) 和 [app.py:3935](../VoidCube_cli/app.py#L3935)

```python
previous_active_role = str(getattr(self, "_active_chat_agent_role", "") or "")
self._active_chat_agent_role = "supervisor_task" if autonomous_task_run_id else "user_chat"
```

这个标志标记"当前 turn 是谁触发的"，用于 Gateway 场景上报。它不是并发控制机制——并发靠 `_api_a_execution_gate` 锁。

- 父 host 的 `chat()` 中：`autonomous_task_run_id` 始终为 `""` → 角色始终为 `"user_chat"`
- component_host 的 `chat()` 中：`autonomous_task_run_id` 非空 → 角色为 `"supervisor_task"`

**问题**：角色标记本身正确，但没有优先级。如果父 host 和 component_host 同时有 pending 任务，先到先得。用户无法"插队"。

## 8. 冲突总结

| 编号 | 冲突点 | 严重程度 | 当前防护 | 实际风险 |
|------|--------|---------|---------|---------|
| 1.3 | `_api_a_execution_gate` 单锁串行化 | 🔴 高 | 无（串行化是设计意图） | 用户等待自主任务完成无反馈，无法打断 |
| 2.1 | 自学习任务 Agent 重建开销 | 🟡 中 | 自动重建 | 每次自学习 ~200ms 延迟 |
| 1.1 | 两侧 `_agent_running` 相互不可见 | 🟡 中 | `_api_a_execution_gate` 间接协调 | 状态栏不显示自主活动，依赖自主面板弥补 |
| 5.1 | Spinner/工具状态在状态栏不显示 | 🟠 低 | 自主面板独立渲染 | 仅在用户注视状态栏时感到困惑 |
| 0.4 | `chat()` 中 cprint 硬编码绕过 quiet | 🟠 低 | `_ThreadOutputProxy` 线程级兜底 | 子线程输出泄露风险 |
| 6.1 | 退出时 Event loop is closed | 🟠 低 | prompt_toolkit 异常处理 | 退出时偶发 "Press ENTER" 提示 |
| 2.2 | 工具回调注册缺失 | 🟠 低 | 当前自主任务基本不触发交互 | 未来扩展时风险 |
| 3.1 | SessionDB source 混写 | 🟠 低 | source 字段区分 | 数据库查询结果可能混乱 |
| 5.2 | 自主面板与状态栏竞争行空间 | 🟠 低 | 各自独立渲染 | 窄终端布局错乱 |
| 6.3 | Atexit 清理 `_active_agent_ref` 竞争 | 🟠 低 | `_cleanup_done` 守卫 | 退出清理顺序不确定 |
| 3.3 | ChatBlockStore 独立但有重复记录可能 | 🟠 低 | 不同 host 实例隔离 | 全局回调事件可能重复 |

## 9. 核心矛盾与改进建议

### 9.1 核心矛盾

当前设计的本质是**双实例 + 单锁串行化**：

- **实例层面**：父 host 和 component_host 是两个独立的 `VoidcubeCLI` 实例，各有独立的 `Agent`、`ApplicationRuntime`、`ChatBlockStore`、`conversation_history`
- **调度层面**：通过一个全局 `_api_a_execution_gate` 锁将两个实例串行化，确保同一时刻只有一个在执行模型 turn
- **分离点**：`_current_autonomous_task` 只存在于 component_host 上，父 host 无法感知——这是确保主 CLI 不会误执行自主任务的关键设计

这种设计正确但粗糙：
- 隔离依靠"用同一个类创建两个实例"，但类携带了大量不需要的能力（TUI 装配、keybinding、voice 等）
- 串行化是全局锁，无优先级、无超时、无可中断性
- 实例间状态不透明：每个实例只能看到自己的状态，看不到对方的

### 9.2 建议改进优先级

**P0 — 立即改进**：

1. **自主任务可中断性**：在 `_api_a_execution_gate` 的等待循环中加入超时检查，当用户按 Enter 时给出反馈（如"自主任务执行中，请等待或使用 /auto-q 停止"），而非静默排队。

2. **命令式取消统一**：`/cancel` 只取消用户 turn，`/auto-q` 只停用并取消自主链路，`/quit` 只退出 CLI；三者都应走可立即处理的命令路径。
