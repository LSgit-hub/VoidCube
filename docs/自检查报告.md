# VoidCube 自检查报告

## 结论

原报告指出的 5 项问题已经完成修复，并已接入自主学习/替身执行链路：

1. 终态收尾、会话持久化和资源清理已闭环。
2. Mem 同步失败会形成可重试的持久化 outbox 状态。
3. 普通文本工具输出增加明确失败模式识别，避免把失败传给模型时伪装成成功。
4. 工具调度路径使用 `Path.resolve(strict=False)`，符号链接别名会进入同一冲突检测空间；解析失败时强制串行。
5. 上下文压缩前会原子持久化结构化 checkpoint；摘要失败时恢复 checkpoint 投影和 action refs，不再只留下静态丢失提示。

## 执行环境风险

原报告在临时沙箱中得到的 `httpx`、`sqlite-vec` 结论不能代表 Windows 宿主环境，现已从主结论中删除。当前项目明确区分：

- Windows 宿主路径，例如 `F:\\...\\VoidCube`；
- Podman/WSL 执行路径 `/workspace`；
- 宿主和执行环境各自的 Git、Python、pytest、Node、npm 可执行文件及版本；
- 依赖声明文件指纹（`requirements*.txt`、`pyproject.toml`、Node 锁文件等）；
- Git HEAD、工作区路径映射、执行后端和验证平台。

`ExecutionEnvironmentManifest` 是内容寻址且不可变的环境证据。Benchmark baseline 和 candidate 必须使用同一份环境清单；环境漂移会直接终止评测。评分策略必须声明所需验证平台，当前 Windows 项目的晋升策略要求 `windows`。Linux Podman 清单只能通过容器范围硬门，不能声称 Windows 宿主测试通过。

替身任务的 Podman 工作树探针现在会验证 `/workspace`、Git HEAD，并采集 Git/Python/pytest/Node/npm 和依赖指纹。Podman 启动失败不得回退到本地执行；任务报告必须携带容器范围环境清单。模型收到的执行提示会列出沙箱工具链，缺少 pytest 或 Node 时必须报告阻塞，不得引用宿主路径替代。

5H 已将平台选择产品化：普通改动默认要求 Windows，依赖声明、容器运行时和环境工具改动要求 Linux + Windows。选择结果、changed files、dependency fingerprint 和原因码均进入不可变 `ExperimentSpec`，scoring policy 未覆盖选中平台时在评测持久化前阻塞。Tirith 扫描器状态和容器磁盘 quota 状态进入逐命令 authoring 证据；旧记录可读，但缺少这些字段时不能进入新的自主晋升路径。

架构复核同时确认：Podman 适合提供 Linux 可复现验证，但不应继续作为 Windows 项目所有 authoring 的必经环境。5I 将切换为 Windows native linked-worktree authoring + 按需 Podman 验证；在该阶段完成前，当前 Podman authoring 是过渡实现，不代表最终主路径。

## 主要改动

- `agent/tool_execution.py`、`agent/tool_scheduler.py`：工具失败判定和真实路径冲突。
- `agent/context_compressor.py`、`run_agent.py`：持久化压缩 checkpoint 和会话恢复绑定。
- `systems/evolution_evaluation/models.py`、`executor.py`、`environment.py`：评测环境清单、平台硬门和 baseline/candidate 环境一致性。
- `tools/terminal_tool.py`：Windows linked worktree 到 `/workspace` 的 Git/工具链探针，禁止本地回退。
- `VoidCube_cli/autonomous_executor.py`、`systems/body_registry.py`、监督者治理模块：环境证据随自主任务、改进报告和晋升授权传播。
- `systems/evolution_authoring/repository.py`、`systems/supervisor/evolution_candidate_evaluation_service.py`：候选 authoring 结果内容寻址持久化，并在进入 ExperimentSpec 前核对 candidate ref、单父提交 lineage、真实 Git diff、快照和知识引用。
- `systems/evolution_evaluation/executor.py`、`systems/supervisor/evolution_evaluation_governance.py`：逐 case 命令、退出码、日志摘要、环境 manifest、统一 environment identity 和双 subject checkout 进入 ExperimentResult；缺失或失败证据不能获得晋升授权。
- `systems/evolution_evaluation/selection.py`、`tools/tirith_security.py`、`tools/environments/docker.py`：确定性平台选择、扫描器可用性和磁盘 quota 能力证据。

## 仍需保持的边界

容器验证结果不是 Windows 宿主验证结果。若候选改动涉及 Windows 路径、权限、进程、文件锁或 Node 原生模块，必须在 Windows 宿主重新执行对应 BenchmarkPack，并生成 `validation_scope=host`、`validated_platforms=("windows",)` 的环境证据；否则结果只能观察或拒绝，不能晋升。真实 5G 场景覆盖的是单文件 Python 编译和最小质量指标，不代表所有项目测试或原生依赖已经覆盖。

## 下一步建议

执行 5I native-first 改造：默认在 Windows linked worktree 中使用项目 `.venv` authoring 和测试，只在平台选择要求 Linux 时启动 Podman runner；随后扩展真实 BenchmarkPack，覆盖 Windows 路径、权限、进程、文件锁和 Node 原生模块。
