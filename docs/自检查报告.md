                                                                                                                                                           
   我把 Agent 当作“行动躯体”看了一遍。最不满意的地方不是工具数量，而是它在“做完动作之后确认自己到底完成了什么”这件事上还不够可靠。                            
                                                                                                                                                              
   **1. 高风险：终态提交不是原子操作，持久化失败可能让整个收尾过程直接中断**                                                                                  
                                                                                                                                                              
   位置：                                                                                                                                                     
                                                                                                                                                              
   - `/workspace/agent/turn_finalization.py:164-167`                                                                                                          
   - `/workspace/agent/conversation_runtime.py:66-71`                                                                                                         
   - `/workspace/agent/session_persistence.py:85-97`                                                                                                          
   - `/workspace/agent/session_persistence.py:136-180`                                                                                                        
                                                                                                                                                              
   终态流程大致是：                                                                                                                                           
                                                                                                                                                              
   1. 清理任务资源                                                                                                                                            
   2. 持久化 transcript                                                                                                                                       
   3. 计算诊断信息                                                                                                                                            
   4. 清理中断标记和流回调                                                                                                                                    
   5. 同步 Mem                                                                                                                                                
   6. 返回结果                                                                                                                                                
                                                                                                                                                              
   但 `cleanup_task_resources()` 和 `persist_session()` 都是在没有统一 `try/finally`                                                                          
   的情况下直接调用的。只要清理或持久化抛出异常，后面的中断清理、诊断、Mem 同步和最终结果都不会执行。                                                         
                                                                                                                                                              
   更隐蔽的是，`flush_to_db()` 遇到一般异常时会在 `session_persistence.py:178-180` 记录 warning，然后返回 `False`。`persist()` 在                             
   `session_persistence.py:96-97` 只是根据这个返回值决定是否刷新 JSON 镜像，不会把失败状态交给上层。因此可能出现：                                            
                                                                                                                                                              
   - SQLite 没写入；                                                                                                                                          
   - JSON 镜像也不刷新；                                                                                                                                      
   - Agent 仍继续执行后续收尾；                                                                                                                               
   - 调用方拿不到“持久化失败”的明确状态；                                                                                                                     
   - 最终回答可能看起来像正常完成。                                                                                                                           
                                                                                                                                                              
   对一个行动躯体来说，这是最核心的问题：动作可能已经发生，但身体对自身行动历史的确认失败了，却没有形成可靠的失败终态。                                       
                                                                                                                                                              
   已有缓解是 SQLite 具备 revision、sequence、hash 和冲突重试机制，设计方向是对的；缺的是失败结果必须进入终态契约，而不是只留在日志里。                       
                                                                                                                                                              
   **2. 高风险：成功回答和 Mem 同步之间没有可见的一致性关系**                                                                                                 
                                                                                                                                                              
   位置：                                                                                                                                                     
                                                                                                                                                              
   - `/workspace/agent/turn_finalization.py:241-254`                                                                                                          
   - `/workspace/agent/memory_manager.py:163-172`                                                                                                             
   - `/workspace/run_agent.py:5200-5207`                                                                                                                      
                                                                                                                                                              
   `sync_memory()` 的所有异常都会被 `turn_finalization.py:253-254` 静默吞掉。`MemoryManager.sync_all()` 本身也会逐个 provider 捕获异常，仅记录 warning。      
                                                                                                                                                              
   这意味着 Agent 可以向用户返回一个成功回答，但这次回答完全没有进入 Mem，而且结果中没有：                                                                    
                                                                                                                                                              
   - `memory_sync_failed`                                                                                                                                     
   - 失败的 provider                                                                                                                                          
   - 是否部分同步成功                                                                                                                                         
   - 是否需要补偿重试                                                                                                                                         
   - 本次会话是否仍可被认为“记忆已落盘”                                                                                                                       
                                                                                                                                                              
   由于 Mem 负责身份连续性和跨会话回忆，这不是普通的后台日志问题。它会造成“当前 Agent 说过某件事，但未来的 Agent 不知道自己说过”的身份断裂。                  
                                                                                                                                                              
   这里保留 provider 隔离是合理的，单个记忆 provider 失败不应阻断主回答。但至少需要把同步状态作为结构化结果或 action evidence                                 
   返回，并提供重试队列或待同步记录。                                                                                                                         
                                                                                                                                                              
   **3. 中风险：普通文本工具输出的成功判断过于乐观**                                                                                                          
                                                                                                                                                              
   位置：                                                                                                                                                     
                                                                                                                                                              
   - `/workspace/agent/tool_execution.py:48-78`                                                                                                               
                                                                                                                                                              
   JSON 工具结果会检查 `status`、`state`、`exit_code`、`success` 和 `error`。但非 JSON 文本只有在左侧去空白后以 `error`                                       
   开头时才被认为失败，其他内容全部归为 `SUCCEEDED`。                                                                                                         
                                                                                                                                                              
   因此类似下面的工具输出会被判定为成功：                                                                                                                     
                                                                                                                                                              
   - `failed: permission denied`                                                                                                                              
   - `command exited with code 1`                                                                                                                             
   - `timeout while waiting`                                                                                                                                  
   - `unable to connect`                                                                                                                                      
   - `not found`                                                                                                                                              
                                                                                                                                                              
   这会把真实失败传递给模型时伪装成普通成功结果。最终模型可能据此继续下一步，或向用户声称动作已经完成。                                                       
                                                                                                                                                              
   这属于协议边界设计问题。最好要求所有具有行动副作用的工具返回结构化                                                                                         
   `ToolExecutionResult`；对于非结构化文本，至少应该有工具级成功/失败标记，而不是依赖自然语言前缀启发式。                                                     
                                                                                                                                                              
   **4. 中风险：并行工具的路径冲突检测可被符号链接绕过**                                                                                                      
                                                                                                                                                              
   位置：                                                                                                                                                     
                                                                                                                                                              
   - `/workspace/agent/tool_scheduler.py:64-77`                                                                                                               
   - `/workspace/agent/tool_scheduler.py:80-87`                                                                                                               
                                                                                                                                                              
   路径规范化只使用 `expanduser()` 和 `abspath()`，没有 `resolve()`。冲突检测只比较路径的 `Path.parts` 前缀。                                                 
                                                                                                                                                              
   因此两个路径如果通过不同符号链接指向同一个真实目录，调度器可能认为它们互不重叠，并行执行写操作。例如：                                                     
                                                                                                                                                              
   - `/workspace/data`                                                                                                                                        
   - `/workspace/link-to-data`                                                                                                                                
                                                                                                                                                              
   如果两个路径实际指向同一实体，就可能产生并发写入冲突或读写竞态。                                                                                           
                                                                                                                                                              
   当前调度器已经有白名单、最大 worker 数量、禁止并行工具和路径重叠检测，这些是有效缓解。问题在于它把“字符串路径空间”当成了“文件实体空间”。                   
                                                                                                                                                              
   **5. 设计风险：上下文压缩失败后，行动语义会退化为静态提示**                                                                                                
                                                                                                                                                              
   位置：                                                                                                                                                     
                                                                                                                                                              
   - `/workspace/agent/context_compressor.py:1045-1058`                                                                                                       
   - `/workspace/agent/context_compressor.py:1081-1103`                                                                                                       
                                                                                                                                                              
   这里不能说行动证据完全丢失，因为 fallback 会保留 action refs，且压缩摘要也会要求保留 Done、In Progress、Blocked、命令、结果和错误。                        
                                                                                                                                                              
   但摘要生成失败时，旧轮次的正文语义会被替换成静态 fallback，只保留：                                                                                        
                                                                                                                                                              
   - 压缩失败提示；                                                                                                                                           
   - 被删除的轮次数量；                                                                                                                                       
   - action refs；                                                                                                                                            
   - 近期消息；                                                                                                                                               
   - 当前资源状态。                                                                                                                                           
                                                                                                                                                              
   这会让恢复后的 Agent 知道“曾经有这些动作”，但未必知道动作的完整目的、输入、输出和失败原因。对可恢复执行来说，action ref                                    
   只能定位证据，不能完全替代证据本身。                                                                                                                       
                                                                                                                                                              
   更稳妥的方式是把压缩前的行动摘要作为结构化 checkpoint 持久化，摘要失败时优先恢复 checkpoint，而不是只插入文本 fallback。                                   
                                                                                                                                                              
   **已有部分做得不错的地方**                                                                                                                                 
                                                                                                                                                              
   - 工具执行已经有 `SUCCEEDED`、`FAILED`、`CANCELLED`、`TIMED_OUT`、`UNKNOWN` 等结构化状态。                                                                 
   - 调用异常、未启动、被中断跳过的工具不会完全静默消失。                                                                                                     
   - action journal 会记录工具状态，压缩后的消息也会携带 action refs。                                                                                        
   - SQLite transcript 有 revision、sequence、prefix hash 和冲突重试。                                                                                        
   - 正常中断路径的测试明确验证了先持久化、再清理 interrupt。                                                                                                 
   - 压缩 prompt 明确要求保留任务进度和错误信息。                                                                                                             
                                                                                                                                                              
   所以问题不是 Agent 没有状态模型，而是状态模型在终态、持久化、Mem 和最终回答之间还没有完全闭环。
