# VoidCube 自检查报告

## 结论

原报告指出的 5 项问题已经完成修复，并已接入自主学习/替身执行链路：

1. 终态收尾、会话持久化和资源清理已闭环。
2. Mem 同步失败会形成可重试的持久化 outbox 状态。
3. 普通文本工具输出增加明确失败模式识别，避免把失败传给模型时伪装成成功。
4. 工具调度路径使用 `Path.resolve(strict=False)`，符号链接别名会进入同一冲突检测空间；解析失败时强制串行。
5. 上下文压缩前会原子持久化结构化 checkpoint；摘要失败时恢复 checkpoint 投影和 action refs，不再只留下静态丢失提示。

## 执行环境风险

原报告在临时沙箱中得到的 `httpx`、`sqlite-vec` 结论不能代表 Windows 宿主环境，现已从主结论中删除。当前项目明确区分：

- Windows 宿主路径，例如 `F:\\...\\VoidCube`；
- Podman/WSL 执行路径 `/workspace`；
- 宿主和执行环境各自的 Git、Python、pytest、Node、npm 可执行文件及版本；
- 依赖声明文件指纹（`requirements*.txt`、`pyproject.toml`、Node 锁文件等）；
- Git HEAD、工作区路径映射、执行后端和验证平台。

`ExecutionEnvironmentManifest` 是内容寻址且不可变的环境证据。Benchmark baseline 和 candidate 在每个平台必须共享同一个 `ExecutionEnvironmentIdentity`，但因 Git HEAD 不同分别生成 manifest。评分策略的平台集合必须与确定性 selection 精确一致；Linux Podman 清单只能证明 Linux/container，不能声称 Windows 宿主测试通过。

默认 authoring 已改为 Windows native linked worktree，固定使用项目 `.venv` 和宿主 Git/Node；项目虚拟环境缺失或 Windows runner 不可用时明确阻塞，不会回退到 Podman 后声称 Windows 已验证。Podman 只由 Linux validation runner 按 selection 启动，其 `/workspace`、Git HEAD、工具链、镜像 digest 和依赖指纹仍必须通过探针，失败不得本地回退。

5H 已将平台选择产品化：普通改动默认要求 Windows，依赖声明、容器运行时和环境工具改动要求 Linux + Windows。选择结果、changed files、dependency fingerprint 和原因码均进入不可变 `ExperimentSpec`，scoring policy 未覆盖选中平台时在评测持久化前阻塞。Tirith 扫描器状态和容器磁盘 quota 状态进入逐命令 authoring 证据；旧记录可读，但缺少这些字段时不能进入新的自主晋升路径。

5I 已落实 native-first：authoring 与 validation 解耦，selection-aware factory 只构造本次必需平台的 runner。Windows-only 改动不启动 Podman；依赖、容器或环境工具改动运行 Linux Podman + Windows 双平台矩阵。任一 runner 缺失、失败、超时、清理失败或环境漂移都不会产生可晋升结果。

5J 将平台风险固化为标准 BenchmarkPack。case 可用 `platform:windows` 限定适用平台，执行器和 Governor 使用同一矩阵规则；旧 case 无标签时仍覆盖全部选中平台。标准 pack 包含 portable Python import，以及 Windows 路径、只读属性、子进程、跨进程文件锁和 `node-pty` 原生模块实际启动。受信任 evaluator 临时链接主仓库已安装的 Node 依赖，依赖缺失、lock 版本不一致、junction 清理失败或任一 probe 失败都会阻止晋升。

## 主要改动

- `agent/tool_execution.py`、`agent/tool_scheduler.py`：工具失败判定和真实路径冲突。
- `agent/context_compressor.py`、`run_agent.py`：持久化压缩 checkpoint 和会话恢复绑定。
- `systems/evolution_evaluation/models.py`、`executor.py`、`runners.py`、`environment.py`：多平台 manifest/identity 矩阵、selection-aware runner 生命周期、平台硬门和 baseline/candidate 环境一致性。
- `tools/terminal_tool.py`、`tools/environments/local.py`、`tools/path_runtime.py`：Windows native linked worktree 与项目 `.venv`、按需 Podman `/workspace` 探针、Git Bash cwd 映射和禁止隐式回退。
- `VoidCube_cli/autonomous_executor.py`、`systems/body_registry.py`、监督者治理模块：环境证据随自主任务、改进报告和晋升授权传播。
- `systems/evolution_authoring/repository.py`、`systems/supervisor/evolution_candidate_evaluation_service.py`：候选 authoring 结果内容寻址持久化，并在进入 ExperimentSpec 前核对 candidate ref、单父提交 lineage、真实 Git diff、快照和知识引用。
- `systems/evolution_evaluation/executor.py`、`systems/supervisor/evolution_evaluation_governance.py`：逐平台/逐 subject/逐 case 命令、退出码、日志摘要、capability 状态、环境矩阵和 checkout 进入 ExperimentResult；缺失或失败证据不能获得晋升授权。
- `systems/evolution_evaluation/selection.py`、`tools/tirith_security.py`、`tools/environments/docker.py`：确定性平台选择、扫描器可用性和磁盘 quota 能力证据。
- `systems/evolution_evaluation/benchmark_packs.py`、`windows_probes.py`：版本化标准 pack、配套 policy/factory 和 Windows 原生行为 probes。

## 仍需保持的边界

容器验证结果不是 Windows 宿主验证结果，Windows 结论只能来自 `validation_scope=host`、`validated_platforms=("windows",)` 的 runner。5J 标准 pack 已覆盖路径、只读属性、子进程、文件锁和当前桌面端 `node-pty` 原生模块，但新增 Windows 原生依赖或特殊 ACL/长路径行为时仍需扩展版本化 case，不能把现有 6 个 case 解释为无限范围的平台证明。
