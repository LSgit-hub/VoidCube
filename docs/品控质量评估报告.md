# VoidCube 品控质量评估与改进建议

> 评估日期：2026-08-05  
> 评估基线：`master` / `6d5bf35`  
> 评估角色：品控/质量经理  
> 评估范围：主应用、CLI、Gateway、Supervisor、Memory、MemAI、工具与发行配置

## 结论先行

当前项目属于“条件通过”，不建议把本地测试全绿直接等同于生产就绪。

- 代码与测试规模较大，架构边界、退役集成策略、记忆域隔离和关键交互契约已有较强保护。
- 使用项目 `.venv` 的 Python 3.14.6 运行全量门禁，共 2282 项，结果为 `2277 passed, 4 skipped, 1 xfailed`。修订前唯一失败的文档断链已修复并复测通过。
- 原评估发现的最高风险是 Memory Tier 2 维护超时没有真正施加到异步压缩调用；本轮已用 `asyncio.wait_for` 修复，并补充超时后继续处理后续 scope 的回归测试。
- 发布工程仍缺少静态检查、覆盖率阈值、依赖锁定和依赖安全检查；项目 `.venv` 已确认使用 Python 3.14.6，但验证命令若直接调用 PATH 上的 `python` 仍可能误用 3.11。

## 已确认问题

### P1：Memory 维护超时未被执行（已修复）

**原问题**：[`systems/memory/maintenance.py`](../systems/memory/maintenance.py#L78) 的 `run_tier2_bridge_cycle` 只在调用返回后计算 `deadline_exceeded`，慢请求会阻塞后续 scope。

**修复状态**：当前实现对每个 scope 使用 `asyncio.wait_for`，超时后生成结构化失败结果、记录 `deadline_exceeded=True` 并继续下一个 scope；`asyncio.CancelledError` 仍会向上传播。回归测试位于 [`tests/test_memory_health_signals.py`](../tests/test_memory_health_signals.py#L888)，验证超时 scope 被取消、后续 scope 完成且失败计数正确。

**剩余关注**：压缩实现内部仍需保持数据库事务边界；后续可增加取消发生在写入前、写入中和写入后的集成测试，证明取消不会留下半写入状态。

**建议**：

1. 已用 `asyncio.wait_for(compress(request), timeout=...)` 实施真实超时，并将 `TimeoutError` 转为结构化失败结果。
2. 已保留任务取消向上传播；继续补充数据库写入阶段的取消测试，确认事务边界。
3. 已增加“压缩函数超时后继续下一个 scope”的回归测试，并保留可告警的 `deadline_exceeded` 字段。

### P1：质量门禁只验证测试，不验证代码质量和依赖风险

`.workflow/voidcube-ci.yml` 只有安装依赖和执行 `scripts/run_ci_tests.py` 两步；仓库没有 ruff/flake8、mypy/pyright、coverage、pre-commit 或依赖漏洞检查的 CI 步骤。虽然仓库有 [`tools/osv_check.py`](../tools/osv_check.py)，但它没有接入流水线。

**影响**：类型漂移、未使用导入、复杂度增长、覆盖率下降和已知依赖漏洞都可能在合并时不被阻断。测试通过只能说明已编写场景通过，不能说明未覆盖代码安全。

**建议**：分两阶段接入：

1. 先在 CI 中加入 `ruff check`、`python -m compileall`、覆盖率报告和最低阈值（先只报告，稳定后转失败）。
2. 再加入 `mypy`/`pyright` 的增量范围和 `tools/osv_check.py` 或等效依赖审计；对高危漏洞设硬门禁。

### P1：验证命令可能误用系统 Python

根项目和 `Mem/pyproject.toml` 都声明 `>=3.14,<3.15`，CI 也只跑 Python 3.14。项目 `.venv` 已确认是 Python 3.14.6，并用该解释器完成了完整门禁；但直接输入 `python` 时，Windows PATH 可能选择系统 Python 3.11，造成错误的验证结论。

**影响**：开发者可能在错误解释器上安装依赖或运行测试，产生“本地通过但目标失败”或相反的假象。`.venv\pyvenv.cfg` 的创建命令还保留了另一个旧工作区路径，说明该环境曾被迁移，后续重建和排障会增加歧义。

**建议**：将 Python 3.14 解释器和依赖安装纳入可复现开发环境（例如锁定的容器/脚本），并在 CI 先保持 3.14 主门禁，再增加一个明确目的的兼容性或“不支持版本”检查。不要仅凭本机版本放宽 `requires-python`。

日常验证应固定使用 `\.venv\Scripts\python.exe -m pytest` 或先激活 `.venv`；建议重建一次迁移过的虚拟环境，使 `pyvenv.cfg` 不再引用旧目录。

### P1：巨石规模有治理文档，但缺少可执行增长护栏

当前主要文件规模为：`run_agent.py` 5370 行、`VoidCube_cli/app.py` 4944 行、`VoidCube_app/config.py` 2654 行、`systems/memory/memory_service.py` 3974 行、`tools/skills_hub.py` 2992 行；最大测试文件 `tests/test_supervisor_autonomous_chain_store.py` 为 19479 行。架构测试 [`tests/test_python_architecture.py`](../tests/test_python_architecture.py) 目前只检查导入方向，没有行数、方法复杂度或新增增长阈值。

**影响**：治理方案中的“冻结根规模”主要依赖人工纪律，后续提交仍可能悄悄扩大编排器和测试巨石，增加审查、合并和定位成本。

**建议**：为已收口的根文件建立基线快照，在 CI 中阻断新增超过阈值的行数/字节数和超大函数；允许有审批的基线更新，并把拆分目标按责任域登记，而不是继续堆叠通用 helper。

### P2：宽泛异常捕获与静默失败过多

静态统计显示生产代码约有 570 处 `except Exception`，其中约 241 处紧跟 `pass`。代表性位置包括：

- [`systems/memory/llm_extraction.py`](../systems/memory/llm_extraction.py#L43)：缓存读写或 LLM 解析异常被降级，缓存写入失败完全静默；
- [`VoidCube_app/session_lifecycle.py`](../VoidCube_app/session_lifecycle.py#L366)：会话重开、分支消息复制和标题写入失败被忽略；
- [`systems/gateway/internal_gateway.py`](../systems/gateway/internal_gateway.py#L948)：活动日志持久化失败不向调用者或健康指标暴露。

其中一部分是有意的 best-effort 行为，不能简单全部改成抛错；问题在于缺少统一的分类、日志等级、指标和可观测结果，导致数据持久化失败与“没有需要写入”难以区分。

**建议**：为异常处理建立三类规范：可恢复且降级、可重试、不可恢复；至少记录结构化日志（operation、session/scope、异常类型），关键持久化失败写入健康状态或 trace，并用 lint/评审规则禁止新增无注释的 `except Exception: pass`。

### P2：测试资产本身已经成为维护负担

测试总量大且有效，但单文件极端集中：`test_supervisor_autonomous_chain_store.py` 约 19k 行，另有多个 2k～4k 行测试文件。全量门禁在本机约耗时 6 分钟，失败输出也需要从长日志中定位。

**建议**：按 owner/use case 拆分测试文件，保留稳定的 smoke 子集；将慢测试显式标记并输出 JUnit/耗时排名。拆分应保持 fixture 和断言语义，不要通过减少场景来“缩短测试”。

### P2：依赖没有锁定，发行构建的可复现性不足

仓库只有 `requirements.txt` 对 `pyproject.toml` 的 editable extra 引用，没有 lock/constraints 文件；生产依赖使用宽范围版本（如 `openai>=1,<2`、`httpx>=0.25,<1`）。

**影响**：同一 commit 在不同日期可能解析出不同依赖组合，尤其是 Python 3.14 新版本 wheel、语音和浏览器可选依赖，回归结果难以复现。

**建议**：生成并提交按 Python 3.14/平台区分的 constraints 或 lock 文件，CI 使用锁定解析结果；定期更新锁文件并单独运行依赖审计，而不是扩大主版本范围来“兼容”。

## 已验证的正面能力

- `tests/test_memory_domain_isolation.py`、`tests/test_memory_health_signals.py` 等已覆盖 Tier1→Tier2 bridge、promotion、域隔离和质量门禁；旧报告“这些模块完全没有测试”的结论已纠正。
- 应用层、CLI、Gateway、Supervisor 的边界契约和退役集成均有自动化测试；本次集成/打包相关 37 项通过。
- `compileall` 和 `pip check` 通过，说明当前检出版本没有明显语法错误或已解析依赖冲突。
- Gateway loopback、鉴权、敏感字段脱敏、跨域提升 consent 等设计已有契约测试；但这不等同于完成渗透测试或生产安全认证。

## 优先级路线图

### 本迭代（发布前）

1. 已复测本报告替换后的文档、退役集成和 wheel 契约，确保全量门禁不再因断链失败。
2. 已修复 Tier 2 真实超时和取消语义，并通过挂起请求回归测试。
3. 已在目标 Python 3.14.6 环境重跑完整 `tests` + `Mem/tests` 并通过；后续发布仍应保存测试和构建产物。

### 下一迭代

1. 将 ruff、类型检查、覆盖率报告和 OSV 依赖检查接入 CI。
2. 为巨石文件建立机器可执行的行数/复杂度增长阈值。
3. 清理关键路径的静默异常，先处理会话、Gateway 持久化和 Memory 缓存。

### 持续改进

1. 拆分超大测试文件并输出耗时排名。
2. 建立 Python 3.14 的锁定依赖和可复现开发环境。
3. 对声纹、连续监听、主动提醒等硬件/真实环境能力建立误拒、误唤醒、延迟和资源占用基线；这些指标目前仍属于产品风险而非单元测试覆盖问题。

## 建议的发布判定

满足以下条件后再将版本标记为“可发布”：

- 文档契约、退役集成、wheel 契约、`tests` 与 `Mem/tests` 在 Python 3.14 目标环境全部通过；
- Tier 2 scope 超时测试证明慢请求不会阻塞后续维护；
- CI 至少执行静态检查、覆盖率报告和依赖审计；
- 生产配置使用随机 `GATEWAY_AUTH_TOKEN`，并完成一次备份恢复演练；
- 对 voice/auto/自主链路等需要真实设备或长周期运行的能力，提供实际环境验收记录，而不是只引用 mock 测试。

## 下一步建议

Python 3.14.6 全量门禁已通过，Tier 2 超时修复也已通过定向回归；下一步应把本报告中的 CI 静态检查和巨石增长护栏转成自动化规则。这样下一次质量评估可以直接比较门禁结果和基线变化，而不必重新依赖人工规模统计。
