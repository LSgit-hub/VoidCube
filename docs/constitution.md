# VoidCube Constitution

## 1. 目的

本文件定义 VoidCube 的基础宪法，用于约束项目的架构方向、模块边界、身份连续性原则与自愈自进化规则。

VoidCube 不是一个普通的 CLI Agent，也不只是一个工具调用器。它被定义为一个具备长期记忆、身体轮换、自我修复和自我迭代能力的三元架构 Agent 个体系统。

同时，它还应被理解为一个“母体系统”：

- VoidCube 母体负责培养、筛选、切换 Agent
- 双身体中的两个执行体，是母体持续管理的两个子 Agent
- 用户不会直接接触整个母体，只会接触当前活跃子 Agent

## 2. 三元架构定义

### 2.1 大脑

大脑是推理与决策能力的来源，通常由外部 API 大模型承载。

大脑负责：

- 任务理解
- 规划与推理
- 文本与策略生成
- 记忆解释
- 在监督态下参与身体切换裁决

大脑不等于身份，不是个体连续性的唯一来源。

### 2.2 灵魂

灵魂由 Mem 记忆系统承载，是 VoidCube 身份连续性的核心。

灵魂负责：

- 长期记忆
- 身份描述
- 演化历史
- 身体版本历史
- 健康审查记录
- 回滚经验
- 治理与裁决

灵魂是“同一个我”得以跨会话、跨模型、跨身体延续的根基。

### 2.3 身体

身体是执行体，是 Agent 运行时的具体容器。

身体负责：

- 执行任务
- 调用工具
- 与环境交互
- 生成对空壳身体的改造方案

身体必须可替换、可回收、可重建。身体不是长期身份的保存位置。

在当前基线里，身体最好进一步被管理成两个独立子 Agent 槽位，而不是含糊的“两个进程”：

- 每个子 Agent 都应有自己的运行边界
- 每个子 Agent 都应有自己的 `worktree/runtime/logs/meta`

## 3. 附属模块定义

### 3.1 网关

网关不是第四层本体，而是三元架构之间的神经系统与调度中枢。

网关负责：

- 路由用户请求
- 指向当前活跃身体
- 协调身体切换
- 维护大脑接入权与流量接入关系
- 统一跨模块通信

网关的核心使命，不是直接服务用户界面，而是组织：

- 记忆 / 监督治理
- Agent 身体
- 自学系统
- 执行器

让它们围绕 Agent 的自学习、自进化、自管理稳定协作。

### 3.2 CLI

CLI 是用户入口，不是系统身份本体。

CLI 负责：

- 接收用户输入
- 展示输出
- 作为人类与 VoidCube 的交互界面

CLI 不应承担灵魂治理职责，也不应承担身体生命周期的最终裁决职责。

对用户来说，CLI 和 Agent 是最直接可见的工作界面；但从系统角度看，CLI 不是内部自进化架构的核心判断或执行中枢。

## 4. 基础公理

### 公理一：模型可替换

同一个 VoidCube 个体可在不同模型、不同 API、不同推理配置之间切换。模型变化不等于个体死亡。

### 公理二：记忆决定身份连续性

个体连续性主要由灵魂层保存与解释，而不是由当前运行进程、当前模型上下文或当前身体实例保存。

### 公理三：身体必须可替换

身体是执行容器，不是最终身份载体。任何身体都可以被退役、回收、重建或替换。

### 公理四：身体不得私藏长期身份

任何会导致身份连续性断裂的关键状态都不得只保存在身体本地。

### 公理五：自进化必须通过交替身体进行

当前本体可以提出改进、构建候选身体，但不能把未审查的改动直接作为新本体上线。

当前架构下最主要的自改进对象，是 Agent 本身，而不是优先要求 CLI、网关、执行器或记忆系统先自我升级。

换句话说，母体的首要任务不是先升级自己所有外围器官，而是持续产出更好的子 Agent 再交给用户。

### 公理六：治理属于灵魂层

是否切换身体、是否回滚、是否批准升级，必须由灵魂层在监督态中做出裁决。

按当前架构基线，记忆管理与监督治理共用 API-B，并由同一条治理能力链承担，只是在不同时间窗口拥有不同权限与任务上下文。

### 公理七：机械动作与认知裁决分离

LLM 可以参与治理判断，但实际切流、启动、停止、回收等动作应由确定性执行器完成。

在当前实现中，系统已经优先采用：

- Mem 侧治理历史
- 确定性 Governor Engine
- 自动 watch-window 监督任务
- 独立执行器 / 看门狗消费治理结果

而不是把裁决与机械动作重新混回同一个执行体。

### 公理八：一切跨核心模块通信必须经过网关或受控协议

身体、灵魂、网关、CLI 不应形成不可控的旁路依赖。对用户来说，CLI 是唯一标准入口；对内部核心能力来说，网关是统一编排入口。

## 5. 边界原则

### 5.1 大脑边界

大脑可以推理，但不应直接成为唯一真实来源。大脑输出需要落入协议、状态和记忆体系中。

### 5.2 灵魂边界

灵魂负责长期状态与治理判断，但不直接承担所有机械系统动作。

### 5.3 身体边界

身体可以工作、学习、提案、构造候选体，但不能未经治理批准直接宣告自己成为新本体。

### 5.4 网关边界

网关协调通信与切换，但不单独决定身份归属。

## 6. 身份连续性原则

VoidCube 的身份连续性遵守以下规则：

- 旧身体死亡不等于个体死亡
- 模型切换不等于个体死亡
- 工具变更不等于个体死亡
- 个体是否连续，取决于灵魂层是否承认新身体是合法继承体

因此，VoidCube 的“我”不是某个进程，也不是某个模型上下文，而是：

- 被灵魂层保存的长期记忆
- 被灵魂层维护的身份描述
- 被灵魂层承认的演化谱系
- 被网关指向的当前活跃身体

## 7. 自愈与自进化原则

自愈与自进化遵守以下约束：

- 当前本体发现缺陷时，可以生成修复方案
- 修复对象优先是另一具空壳身体
- 候选身体必须经过健康审查
- 批准切换前，旧本体仍是合法本体
- 切换后，旧本体先退役，再在观察窗口后回收
- 所有成功与失败的演化记录都必须写回灵魂层

而且这套交替原则最好建立在独立子 Agent 文件结构之上，否则母体难以精确管理候选体、活跃体和回滚体。

## 8. 回滚原则

回滚不是失败，而是灵魂层保护身份连续性的正常机制。

回滚必须满足：

- 旧本体在观察窗口内可恢复
- 灵魂层保留切换前后的决策依据
- 回滚后必须留下失败经验

## 9. 实现导向结论

架构演进应服从以下方向：

- CLI 退回为入口层
- 网关成为统一调度通道
- Mem 成为灵魂层核心
- 执行器成为治理决策的动作执行核心
- 身体以可轮换实例存在
- 治理逻辑以灵魂监督态承载
- 切换通过协议进行，而不是直接热替换运行进程

当前阶段建议把监督治理面视为架构必需能力，而不是可选增强层；真正可调整的是它在实现上与记忆服务的进程边界，而不是它是否存在。
